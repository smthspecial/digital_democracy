## Context

ADR-015 decomposed the system into 17 independently deployable services but deliberately left the implementation language unchosen, only constraining polyglot use to "a small approved language/runtime set." That choice can no longer be deferred once actual service code is written. The services split cleanly into two load profiles: a handful sit directly on the national-election-day concurrency spike (100,000+ simultaneous sessions, NFR-009) and/or perform genuinely CPU-bound cryptography (threshold decryption, hash-chaining, biometric matching, blind-signature token issuance); the rest are conventional CRUD and orchestration workloads bound by I/O and developer velocity, not compute.

## Decision

Split the 17 services across two languages by load profile, not by team preference:

**Go** — for services on the concurrency-critical or cryptographic path:
- `voting-service` (SRV-008) — ballot cryptography, threshold decryption, election-day peak concurrency
- `audit-service` (SRV-012) — hash-chained append-only log, highest write fan-in of any service (every service emits to it)
- `auth-service` (SRV-017) — session/token validation on every authenticated request from every other service; biometric match compute
- `delegation-service` (SRV-010) — delegation-chain resolution feeds directly into the voting pipeline's `voting.delegation` queue at vote time

**TypeScript (Node)** — for the remaining 13 services, all I/O-bound CRUD and orchestration: `identity-service`, `jurisdiction-service`, `problem-service`, `proposal-service`, `competency-service`, `deliberation-service`, `budget-service`, `civic-duty-service`, `governance-role-service`, `project-service`, `reputation-service`, `notification-service`, `ai-synthesis-service`.

Go's goroutine model matches the concurrency shape of the four Go services directly; its static binaries and lack of an interpreter/event-loop GC-pause profile suit both the crypto workloads and the autoscaling story in ARCH-006. TypeScript keeps the other 13 services fast to build and staff, and its I/O-bound nature is exactly Node's strength. Both share the frontend/tooling ecosystem (ADR-022) and the same monorepo (ADR-020).

## Consequences

Two language toolchains, two sets of base images, two lint/test conventions to maintain — mitigated by shared per-language base configs (ADR-020) and a single CI pipeline. A service that later turns out to be misclassified (for example, if `problem-service` unexpectedly becomes a hot path) can be rewritten in isolation, since ADR-015 already guarantees service-level deployment and database independence — the language boundary does not leak into the data or deployment layer. This list is the classification of record; changing a service's language is a decision that should update this ADR, not silently diverge from it.
