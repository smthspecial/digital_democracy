## Context

ADR-016 decided on Apache Kafka (or a wire-compatible alternative such as Redpanda) as the backbone for all ~20 named queues in ARCH-005. That decision was made on paper; nothing in this codebase runs Kafka or Redpanda today. Every "async" data process this codebase has actually implemented so far (DP-036 `audit.append` in particular) is either a no-op stub or a synchronous fire-and-forget HTTP call standing in for the queue that was never built -- confirmed by survey: no Kafka/RabbitMQ/NATS/SQS/BullMQ/Redis-pub-sub client exists in any of the 13 TypeScript services' `package.json` or the 4 Go services' `go.mod`, no `docker-compose.yml` exists anywhere in the repo, and `infra/terraform`/`infra/helm` contain zero message-broker references.

Standing up the actual backbone is now in scope. Kafka's operational surface (partition rebalancing, typically a schema registry, and even Redpanda's own topic/partition model) is real weight to take on for a repo with zero broker infrastructure running today, and heavier than this system's current scale needs -- ARCH-005's ~20 named queues, most single-digit-consumer-count, don't need Kafka's horizontal-partition throughput yet. This ADR revisits ADR-016's technology choice under an explicit constraint ADR-016 didn't have: pick something that is not just eventually correct at 10 million citizens, but easy to actually stand up and run today.

## Decision

Adopt NATS with JetStream (persistence layer) as the event backbone for every named queue in ARCH-005, superseding ADR-016's Kafka/Redpanda choice. One JetStream stream per named queue (or a small group of related queues sharing a stream, subject-filtered per consumer), matching ADR-016's one-topic-per-queue granularity.

What carries over unchanged from ADR-016: `audit.append` remains the special case requiring exact ordering (not just at-least-once) -- enforced here via a single durable consumer per stream with `max_ack_pending: 1`, processing strictly in delivery order, one message acked before the next is delivered. All consumers implement at-least-once processing with idempotent writes (dedupe keys derived from the source event id) -- audit-service's existing `idempotency_key` handling in `store.go` already does exactly this and needed no change. Streams use `Limits` retention (not `WorkQueue`), so messages are retained rather than deleted on ack, matching ADR-016's "infinite retention... never deleted" requirement for `audit.append`'s hash chain.

What changes from ADR-016:
- **Technology**: NATS/JetStream instead of Kafka/Redpanda.
- **Operational model**: a single ~15MB static binary (`nats-server`) instead of a Kubernetes-native operator (Strimzi) managing a distributed log cluster. It starts in milliseconds, which is why it fits this codebase's existing test convention (ARCH-009 §2: boot the real dependency as its own process, not a mock) the same way the Go services' own compiled binaries already do in the e2e suites.
- **Partitioning**: NATS JetStream doesn't have Kafka's partition-per-key horizontal-scaling model. Per-entity ordering (jurisdiction/citizen/proposal-scoped) is achieved via subject hierarchies (e.g. `voting.tally.<jurisdiction_id>`) and, where a queue's consumer count grows past one, multiple durable consumers filtered by subject rather than partition assignment. This is a real capability gap against Kafka's clustered-partition throughput ceiling; acceptable because nothing in this codebase is within orders of magnitude of that ceiling, and NATS JetStream can be re-evaluated (or Kafka/Redpanda adopted later, since neither this ADR nor ADR-016's original reasoning is destroyed by trying the lighter option first) if a specific queue's throughput actually demands it.
- **Client libraries**: `packages/go/eventbus` (wrapping `github.com/nats-io/nats.go`) and `packages/event-bus` (wrapping `@nats-io/transport-node` + `@nats-io/jetstream`) give every service the same publish-with-ack / durable-ordered-consume shape, so adopting a queue looks the same in every service regardless of language.

## Consequences

- Standing up the backbone for local dev and CI is a single binary, not a cluster -- the same "spawn the real process" e2e pattern already used for every Go service test in this codebase applies unchanged to a broker for the first time (see `packages/go/eventbus/eventbus_test.go` and `packages/event-bus/src/index.test.ts`).
- `audit.append` (DP-036, the highest write fan-in of any service) is the first queue actually wired end to end: every service can now publish an audit event to a durable stream instead of a synchronous HTTP call that silently drops on failure, and audit-service consumes it with a real at-least-once, ordered, idempotent-write consumer instead of relying on every caller separately retrying (or not) a direct HTTP `POST`. Other services' seams (`ThresholdChecker`, `NotificationEmitter`, `VoteSessionRequester`, etc.) are unaffected by this ADR and remain on their current no-op/HTTP implementations until migrated in their own flow's implementation pass.
- Losing Kafka's proven-at-extreme-scale partition throughput is an explicit, revisitable trade against operational simplicity today. If a specific queue's load genuinely outgrows a single JetStream stream's throughput, that queue (not necessarily the whole backbone) can move to Kafka/Redpanda without contradicting this ADR's reasoning, since the constraint that motivated this choice (near-zero current load, near-zero existing broker infrastructure) is exactly the thing that would have changed.
- Realizes NFR-009 and supports NFR-004 (data integrity and immutability), same as ADR-016 claimed, since JetStream's persistent, replayable log gives the same durability and replay properties Kafka would have for `audit.append`'s hash chain and any future read-replica/DR rebuild.
