## Context

Services now span two languages (ADR-019), so the wire contract between them can no longer rely on being "just TypeScript types" or "just Go structs" — it needs a representation both sides can generate from. gRPC/Protobuf is the natural long-term fit for a mesh-secured (ADR-018), polyglot, high-throughput internal network, but adopting it correctly requires a working `protoc`/`buf` codegen pipeline wired into CI for both languages — infrastructure that does not exist yet on day one of scaffolding, and should be introduced deliberately with real generated-code verification, not assumed into place by hand-written stub files nobody has compiled.

## Decision

Start every service — Go and TypeScript alike — on plain HTTP with JSON bodies, with each service's contract written as an OpenAPI 3.1 document (`openapi.yaml`) living alongside its code. TypeScript's shared `packages/api-client` generates typed clients from those documents (via `openapi-typescript`, an npm-distributed tool with no separate toolchain to install). This is intentionally the same mechanism whether a caller is `apps/web`, `apps/mobile`, or another service — there is no separate "internal" protocol yet.

Migrate a specific service's internal-facing edges to gRPC/Protobuf only when its measured throughput or latency profile actually demands it — `voting-service` and `auth-service` (ADR-019) are the most likely first candidates, since `auth-service` sits on the hot path of every authenticated request. That migration is a follow-up ADR, made once `packages/proto` and its Go/TS codegen are set up and verified in CI, not a thing this ADR half-implements now.

## Consequences

Day-one services are simple to write, test, and debug in both languages using only stdlib-adjacent tooling (Go's `net/http`, Node's `fetch`), with no codegen step that could silently be stale or unverifiable in an environment without `protoc` installed. The cost is paid later: whichever service is the first gRPC migration target absorbs the one-time work of standing up the protobuf toolchain for both languages. Until then, OpenAPI documents are the single source of truth for every service boundary, checked into the repo next to the service they describe.
