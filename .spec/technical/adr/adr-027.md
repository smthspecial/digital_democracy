## Context

ADR-015 decomposed the system into 17 independently deployable services and ADR-020 laid them out as `services/ts/*` plus `services/go/*`. Nothing in that topology is running yet: every service is specified but unwired, and operating 17 separate deployments, CI matrix entries, Dockerfiles, and migration sets before a single request flows is pure overhead at this stage. The language split itself (ADR-019: Go for the concurrency/crypto-critical four, TypeScript for the I/O-bound thirteen) remains correct — only the packaging granularity needs revisiting.

## Decision

One application per runtime, both under `apps/`:

- **`apps/api-go`** — single Go module hosting voting (SRV-008), delegation (SRV-010), audit (SRV-012), and auth (SRV-017). One binary, one port (`5000`), one route prefix per service (`/voting`, `/delegation`, `/audit`, `/auth`). Each service keeps its own package boundary (`internal/<service>`), store, and OpenAPI contract (`openapi/`), so a future split back into independent deployments re-cuts packaging, not domain code.
- **`apps/api-ts`** — single TypeScript package hosting the thirteen I/O-bound services behind their prefixes (`:4000`). Starts as a routing shell (`501 not_implemented` per prefix with its spec id); real implementations land per service as follow-up work.
- Shared code stays shared: `packages/go/eventbus` (ADR-023) is the one NATS JetStream client for every Go queue, consumed over the Go workspace (`go.work`).

`services/` no longer exists. `docker-compose.yml` runs the whole backend from one file: `api-go`, `api-ts`, NATS, Postgres.

## Consequences

- One binary/deployable/CI target per runtime instead of seventeen. The cost is coupled scaling and deployment of the four Go services — acceptable now (single-digit load, one team), and explicitly reversible: package boundaries equal the old service boundaries, so extracting a service later is mechanical.
- ADR-015's *logical* service boundaries (ARCH-005 topology, per-service tables, per-service DP ownership) are untouched; only the deployment unit changed. Database topology follows in ADR-028, persistence in ADR-029.
