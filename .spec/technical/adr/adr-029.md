## Context

No ORM or query layer was ever decided: ARCH-009 keeps Go services stdlib-only, ADR-021 defers codegen toolchains, and ARCH-023/ADR-024 leave migrations as plain SQL with no runner and no live connection. The question is now real — api-go needs durable storage — and the choice is between a runtime ORM, a driver with hand-written queries, or generated code from the SQL that already exists.

## Decision

- **HTTP stays stdlib `net/http`** (ARCH-009, ADR-021 unchanged): no web framework. The existing handlers, router, and OpenAPI contracts are unaffected by this ADR.
- **Persistence is sqlc + pgx/v5.** `apps/api-go/sqlc.yaml` generates type-safe query packages (`internal/sqlc/<service>`) from the migration (schema) plus one query file per service (`db/queries/*.sql`). Generated code is checked in; `sqlc generate` re-runs after schema/query edits. pgx is used as a driver only — there is no runtime ORM, no model layer, no query builder.
- **One `Store` interface per service** with two backends: `MemoryStore` (tests, `DATABASE_URL`-less runs — `go test` stays dependency-free per ARCH-009) and `PGStore` (production path). Method behavior — DP-016 atomic cast (row lock + transaction), DP-025 idempotent issue (`ON CONFLICT DO NOTHING` + re-read), DP-036 advisory-locked ordered append with idempotency-key dedupe — must match across backends; Postgres-backed tests (`TEST_DATABASE_URL`, skipped without it) pin the parity.
- **Migrations run at boot** through the hand-rolled runner (`internal/pg`, tracked in `schema_migrations`), executing the plain numbered SQL ARCH-023 mandates — no migration binary to install.
- Connection posture for now: one shared `pgxpool.Pool` over `DATABASE_URL` (dev: superuser). Role-separated `api_app`/`api_worker` pools are follow-up work; the GRANTs/policies constraining them already exist in the migration.

## Consequences

- Schema stays the single source of truth: SQL first, Go generated, never hand-written row mapping beyond small `pgtype` converters (`internal/pgconv`).
- New dependencies are compile-time only in effect (sqlc emits code; pgx is a driver, not a framework). `go 1.22` pins hold: pgx v5.6.x, nats.go v1.37.x.
- pgx code paths that need cross-process serialization use database primitives, not process mutexes: `SELECT … FOR UPDATE` for token use, `pg_advisory_xact_lock` for audit appends.
