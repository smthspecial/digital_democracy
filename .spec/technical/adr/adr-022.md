## Context

Citizens need to reach the system from both a browser and a phone, and NFR-015 (digital inclusion and accessibility) argues against treating mobile as an afterthought skinned onto a web view. The frontend and mobile clients also need to stay honest to the same 17-service API surface (ADR-021) without hand-maintaining two separate sets of request/response types that silently drift apart from each other and from the services themselves.

## Decision

Web: Next.js (App Router, TypeScript) in `apps/web`. Mobile: Expo (React Native, TypeScript) in `apps/mobile`, chosen over a bare React Native setup for its managed build/update pipeline (EAS build and OTA updates) and faster path to a running app on both iOS and Android from one codebase — bare RN remains an option to eject into later if a specific native-module need outgrows Expo's managed workflow, but nothing in this system's requirements calls for that on day one.

Both clients consume the same generated `packages/api-client` (ADR-021) — typed request functions produced from each service's `openapi.yaml`, so a change to a service's contract surfaces as a type error in whichever client uses it, in both languages of client at once. Neither client talks to a service directly; both go through the API gateway (ARCH-006), which is also where citizen-facing rate limiting and JWT validation live, so the clients never embed service-topology knowledge.

Shared, cross-platform UI primitives are explicitly deferred: `apps/web` and `apps/mobile` do not share a component library yet. Forcing one prematurely (React Native Web, Tamagui, or similar) before either app has enough real screens to reveal which components are actually shared is exactly the kind of upfront abstraction this project avoids elsewhere; that decision is revisited once both apps have a first real feature built out.

## Consequences

Two native-feeling apps instead of one compromise web-view wrapper, at the cost of writing UI twice — accepted because a governance system's legitimacy depends partly on citizens trusting the interface they vote through, which favors platform-native feel over shared-code convenience. The generated API client means contract drift between backend and frontend is a build-time type error, not a runtime surprise discovered in production. Revisit shared UI tooling once `apps/web` and `apps/mobile` both exist and their actual overlap is visible.
