## Context

ADR-027 left `apps/api-ts` as an unwired routing shell; ADR-028/029 fixed the database and persistence approach for `apps/api-go` (sqlc/pgx, one database per app, RLS per ARCH-023 with role names collapsed to `api_app`/`api_worker`) but explicitly left `api_ts` unimplemented. This ADR is the equivalent decision for `api_ts`, scoped to the first four TypeScript services being implemented now: identity (SRV-001), jurisdiction (SRV-002), problem (SRV-003), proposal (SRV-004) — their sync `Operations` only (DP-001, DP-002, DP-003, DP-004, DP-005, DP-006, DP-007, DP-020). Async/cron DPs that depend on services not yet built (DP-024, DP-042, DP-056 depend on multi-approval/SRV-011; DP-029's `development → voting` gate depends on constitutional review/SRV-012) are out of scope and left as follow-up, consistent with ADR-027's "shell now, services land incrementally" posture.

Two gaps surfaced while reading the spec against SRV-002: no DP document (sync, async, or cron) and no AUTH-010 permission anywhere creates a `jurisdiction`, `residency`, or `jurisdiction_membership` row — SRV-002's own `Operations` table lists only three sync reads. ARCH-023 §6 classifies `jurisdiction` as worker-write-only (consistent with "administrative"), but classifies `residency`/`jurisdiction_membership` as citizen-owned (`OWN`), which would normally imply a citizen-facing insert path that simply does not exist in this spec pass.

## Decision

- **Framework**: NestJS (`@nestjs/core` 12.x) with Express, plain `tsc`/`tsx` (no Nest CLI/SWC) — consistent with the repo's general avoidance of heavyweight build tooling (ADR-020, ARCH-009). ESM throughout (`"type": "module"`), matching `packages/tsconfig/service.json`'s `NodeNext` module setting.
- **Persistence**: Prisma (`prisma` + `@prisma/client` 7.x, both pinned off the matched `prev` tag rather than the `prisma` package's `latest` dist-tag, which currently points at an unmatched 8.0.0 release candidate). One `schema.prisma` for `api_ts`, tables named to match `tbl-NNN.md` exactly (`@@map`/`@map` from camelCase Prisma fields to the spec's snake_case columns) so ARCH-023's SQL policies apply unmodified.
- **RLS wiring (realizes ADR-024/ARCH-023/ADR-028 for api_ts)**: the generated migration is hand-augmented with the `api_app`/`api_worker` roles, `current_citizen_id()` helper, `ENABLE`/`FORCE ROW LEVEL SECURITY`, and the exact per-table policies ARCH-023 §6 specifies for TBL-001…010. Unlike ADR-029's interim superuser-for-everything posture for api-go, `PrismaService` here holds **two** Prisma Client instances bound to `api_app` and `api_worker` credentials respectively, because AUTH-010 explicitly assigns `citizen:activate` (the `pending → active` transition inside DP-002) to a worker-only permission even though DP-002 itself is a citizen-triggered sync call: the citizen's own `identity_verification` insert runs under `api_app` (their `citizen_id` set via `SET LOCAL` / `set_config`), and the resulting activation update runs as a second step under `api_worker`. Every other sync operation in this pass (DP-001, DP-003, DP-004, DP-005, DP-006, DP-007, DP-020) is pure `api_app` traffic with the acting citizen's id set per request. `api_worker`'s broad `USING (true)` policies exist per ARCH-023 §4.3 but this pass only exercises them for the DP-002 activation step.
- **Citizen context seam**: no service in this pass can validate a real auth-service session (SRV-017 lives in `api-go`; cross-app session/JWT verification is not part of implementing SRV-001–004). A `CitizenContextResolver` port reads `x-citizen-id` from the request — an explicitly interim, replaceable seam in the same spirit as `api-go`'s `CompetencyChecker`/`AuditEmitter` seams (`apps/api-go/internal/delegation/service.go`) — until real session validation against `api-go`'s auth-service lands.
- **Audit emission**: an `AuditEmitter` port (no-op default, HTTP POST to `AUDIT_SERVICE_URL` when set) fires only where a DP doc explicitly states "Emits DP-036" — DP-002 (on activation), DP-003, DP-005. DP-001 and DP-004/006/007/020 do not emit per their doc text as written; not extended beyond what's specified.
- **Duplicate identity (FR-001 AC, DP-001 scope only)**: DP-001 enforces the "duplicate identity creation attempts are detected and rejected" acceptance criterion synchronously — a same-transaction check plus a partial unique index (`WHERE status <> 'revoked'`) on `citizen.legal_identity_hash`. The full DP-024/DP-056 flag-for-multi-approval-review pipeline is not implemented (needs SRV-011, out of scope); the sweep/detection jobs remain follow-up work, unchanged from before this ADR.
- **Proposal threshold recompute (DP-028 only, not DP-029)**: after a successful DP-004 endorsement, `ProblemService` calls `ProposalService`'s recompute for every proposal linked to that `problem_id`, updating `support_count` from the current `problem_support` count — implemented as a direct in-process call (no queue exists on the TS side yet), matching `api-go`'s established pattern of implementing spec'd async/cron DPs as directly-callable service methods pending real queue infrastructure (e.g. `delegation.ExpireDue`, `ActiveDelegations`). DP-029's status transitions are **not** implemented: `gathering_support → development` has no documented trigger into `gathering_support` anywhere in the DP set as written (every proposal is created in `draft` per DP-005 and nothing moves it out), and `development → voting` needs constitutional review (SRV-012, out of scope). Recording `support_count` is real, spec-backed behavior; inventing the missing transition is not.
- **Jurisdiction module is read-only in this pass**: implements exactly SRV-002's three sync reads (jurisdiction tree, citizen eligibility check, residency verification). `jurisdiction`/`residency`/`jurisdiction_membership` rows are seeded (`prisma/seed.ts`), not created through any HTTP endpoint — there is no spec'd citizen-facing or worker-facing create operation for any of the three tables to implement. This is a spec gap, not an implementation gap; flagged here rather than silently inventing a `POST /jurisdictions` (or residency/membership) endpoint AUTH-010 does not authorize.

## Consequences

- Two live Postgres roles per environment (`api_app`, `api_worker`) with real passwords need provisioning wherever `api_ts` runs — `docker-compose.yml`'s `api_ts` `DATABASE_URL` now points at `api_app`, plus a new `WORKER_DATABASE_URL` at `api_worker`, both created by the migration itself (not `infra/compose/postgres-init.sql`, which only creates the two databases).
- Test suite mirrors `api-go`'s split: dependency-free unit tests run against in-memory repository fakes by default; a second, real-Postgres pass (`TEST_DATABASE_URL`, `TEST_WORKER_DATABASE_URL`) is skipped automatically when unset, and — because it connects as `api_app`/`api_worker` rather than a superuser — is the first test suite in this repo that actually exercises the RLS policies ARCH-023 specifies, not just their SQL text.
- Residency/jurisdiction-membership creation, the full identity duplicate-review workflow, and proposal voting-readiness transitions all stay explicitly open follow-up items tied to services not yet built (SRV-011, SRV-012) or to a spec gap (jurisdiction writes) — tracked here rather than worked around.
