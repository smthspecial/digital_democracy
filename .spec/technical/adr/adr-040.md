## Decision

Identity-service owns civic identity, evidence references, verification results,
duplicate detection and the active/inactive/revoked lifecycle. A trusted
government-credential or assisted-verification adapter submits the decision.
The citizen never chooses their verification outcome. The pilot accepts
HMAC-signed callbacks with a dedicated `IDENTITY_VERIFIER_SHARED_SECRET`;
production transport must protect the callback and its response with TLS.
This provisions a credential account; it does not establish that an external
government verifier has already been integrated.

Auth-service owns passkeys, WebAuthn ceremonies, sessions, refresh rotation and
authentication assurance. After successful verification, identity-service calls
`POST /auth/identities/provision` using its authenticated api-ts service seam.
Auth rechecks active status and issues a random enrollment grant lasting five
minutes. The trusted verifier returns this to the same applicant through its
verified onboarding channel. A citizen identifier alone cannot obtain a grant.

The grant starts exactly one first-passkey registration ceremony. Auth validates
the attestation using the pinned go-webauthn library, requiring user verification,
then stores the public credential and authenticator state. The private key stays
on the authenticator. A subsequent assertion ceremony is required to issue a
session. RP ID and origin are deployment settings, with no implicit defaults.
For local development they may be explicitly set to `localhost` and
`http://localhost:3000`; production must use its actual browser origin.

Ceremonies are server-side Postgres records, addressed by hashes of random
tokens, scoped by purpose and atomically consumed before validation. Restarts
and multiple API instances share the same consumption state. Failed ceremonies
need a new challenge. Credential updates use a conditional write against the
previous authenticator state; a stale concurrent update cannot overwrite a
newer counter. First-passkey uniqueness is enforced in the database.

Verified login issues an opaque access token and a rotating HttpOnly refresh
cookie. API TS validates access tokens with auth-service. Auth validation and
refresh recheck active civic identity. T3 assurance is downgraded after five
minutes, independently of the 15-minute access token TTL. Completing a fresh
passkey login supplies fresh T3 assurance with a new session.

## Authorization ownership

Authentication asserts citizen identity and current assurance, not political
rights. Domain services decide permissions at the time of each action:
active citizenship, ownership, verified residency and membership, competency,
current governance role, assignment, conflict of interest, required assurance
and independent approvals. PostgreSQL RLS provides an additional ownership
boundary. Operator IAM policies are separate from citizen participation rights.
Neither identity verification nor a passkey changes voting weight. Ballots
remain separated from civic identity by the eligibility-token boundary.

## Current limits and follow-up

- The verifier callback is ready, but a real external identity-proofing adapter
  and applicant grant-delivery channel still need integration.
- The pilot supports the first passkey only. Adding credentials and recovering
  a lost credential require separate authenticated/reverified flows; a fresh
  grant cannot replace an existing passkey.
- Placeholder TOTP/facial proofs are confined to legacy test fixtures and their
  public endpoints are disabled. They are not approved runtime alternatives.
- API TS carries assurance context, but the full AUTH-010 assurance/assignment/
  COI catalog is not yet consistently enforced by every domain route. The Go
  voting/delegation/admin surfaces also need their own authorization rollout.
- HMAC authenticates current internal callers. TLS, key rotation and workload
  identity/mTLS remain deployment work; timestamp windows do not provide
  general-purpose callback replay protection.
- Credential recovery must not offer an identifier-only bypass. Reverification,
  revoking old sessions and notification/audit are required before replacement.
- Durable audit delivery and provider validation are outside this change.

## HTTP integration

1. Register a pending identity via `POST /identity/citizens`.
2. The trusted verifier calls `POST /identity/citizens/:id/verifications` with
   `{method,evidenceRef,outcome}`. Signed bytes are the exact request JSON.
3. A verified response includes `enrollment.enrollment_grant` and `expires_in`.
   After an auth outage, the verifier may retry the guarded
   `POST /identity/citizens/:id/enrollment-grant` with JSON body `{}`; verified
   evidence is rechecked.
4. Send the grant as bearer authorization to registration/begin. It returns
   `{ceremony_token,options}`. The browser creates a credential from
   `options.publicKey`, decoding base64url binary fields.
5. Send its WebAuthn JSON to registration/finish with the ceremony token as
   bearer authorization. Registration returns enrolled status, not a session.
6. Login/begin accepts `{citizen_id,device_fingerprint,ip_subnet}` and returns
   assertion options and a ceremony token. Login/finish accepts the assertion
   JSON with that ceremony token and returns the access token and refresh cookie.

Both verifier and api-ts requests use `X-DD-Service`, `X-DD-Timestamp` and
`X-DD-Signature`. The signature is HMAC-SHA256 of method, path, Unix timestamp
and the hex SHA256 of the body, separated by newline characters. Verifier
callbacks use service name `identity-verifier` and the verifier key; api-ts
provisioning uses `api-ts` and `INTERNAL_SERVICE_SHARED_SECRET`. Callback grant
responses carry `Cache-Control: no-store` and must never be logged.
