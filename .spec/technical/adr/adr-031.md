## Context

ADR-030 implemented identity/jurisdiction/problem/proposal (SRV-001..004) in `apps/api-ts` and left every later service as follow-up. A subsequent, undocumented pass added competency/deliberation/budget/governance-role (SRV-005/006/007/011) and the Prisma schema + migration for project/reputation/iam's tables (TBL-016, TBL-029..031, TBL-040..042) without wiring any NestJS module to them yet. This ADR covers the next batch: civic-duty-service (SRV-009), project-service (SRV-013), reputation-service (SRV-014), notification-service (SRV-015), ai-synthesis-service (SRV-016), and iam-service (SRV-018).

Three of these (project, reputation, iam) already had their tables and RLS policies from the prior pass's migration (`20260911065044_add_project_reputation_iam`) — only the NestJS module code was missing. civic-duty-service had neither; its tables (TBL-024, TBL-025) and RLS are new in this pass. Notification-service and ai-synthesis-service own no tables per their own `srv-NNN.md` docs and ARCH-023 §1 explicitly carves them out of any per-service migration ("out of scope for this pass") — a decision this ADR upholds rather than revisits.

## Decision

- **civic-duty-service tables** (`civic_assignment`, `participation_record`): added to `schema.prisma` and a new migration (`20260911120000_add_civic_duty`), following ADR-030/ARCH-023's established shape exactly (camelCase Prisma fields `@map`'d to the spec's snake_case columns, `api_app`/`api_worker` RLS per ARCH-023 §6's `OWN` classification for both tables). `civic_assignment`'s `own_update` policy additionally requires the row's *current* status to be `'assigned'` in its `USING` clause — a real DB-level invariant beyond bare ownership, mirroring `approval_own_role_insert`'s precedent of enforcing more than the minimum where the data supports it.
- **Sync-only scope, same carve-out as ADR-030**: civic-duty-service's own `Operations` table lists nothing but async/cron processes (DP-040/048/049/052/054). Only AUTH-010's citizen-facing sync permissions are implemented — `assignment:accept` (read as *complete*, since TBL-024's status enum has no distinct "offered" state and AUTH-010 defines no separate `assignment:complete` permission despite AUTH-009's combined "Accept / complete" row label — a documented AUTH-009/AUTH-010 naming mismatch, not silently resolved one way), `assignment:abandon`, and `exemption:claim`. `exemption:claim` requires an *existing* `participation_record` row for the target period (DP-048, the cron that creates one, is out of scope) rather than inventing an upsert path RLS doesn't grant; it also transitions every currently-`assigned` assignment to `exempted`, since TBL-024's own status enum carries that value and FR-053 describes exemptions as pausing obligations, not just labeling a score row.
- **project-service**: implements DP-018 (report milestone) and DP-022 (submit outcome evaluation), the only two sync operations in its `Operations` table; DP-053 (the cron trigger) stays out of scope. The `assigned`-scope guard AUTH-009 specifies ("within assigned project") has no supporting data anywhere — `GovernanceRole` carries no project reference — so only the role-*type* half (active oversight/operator for DP-018, auditor/oversight for DP-022) is checked, via the existing `GOVERNANCE_ROLE_CHECKER` port; the per-project assignment half is a documented spec gap, not invented.
  - A spend delta (`spentDelta`) is accepted on the same `PATCH /projects/milestones/:id` call DP-018 already defines, per SRV-013.md's own Key Rules text tying `budget_spent` updates directly to DP-018, rather than inventing a separate, unspecified endpoint. Each reported spend also pushes an outflow `ledger_entry` into budget-service's public ledger via a new `BUDGET_LEDGER` port (`budget/budget-ledger.port.ts`, `BudgetService` implements it, mirrors every other cross-module port in this app) — but only when the project's originating proposal has a non-null `scope_jurisdiction_id` (`ledger_entry.jurisdiction_id` is `NOT NULL`; `proposal.scope_jurisdiction_id` is nullable). When it's null, the spend is still recorded on `project.budget_spent`; the ledger push is skipped and documented, not faked with an invented jurisdiction.
  - A successful outcome evaluation (DP-022) triggers reputation-service's DP-038 via a new `REPUTATION_RECORDER` port, crediting the *proposal's original author* (resolved via a same-database join to `proposal`) with a `successful_proposal` delta. `partial`/`unsuccessful` outcomes do **not** produce a negative delta — reputation-service's own rule requires an upstream authoritative decision (a fraud finding, an upheld challenge) for any negative delta, and an unsuccessful project isn't automatically one. The delta's magnitude (5) isn't specified anywhere in the spec set; a named constant documents this as a judgment call, the same treatment `budget.service.ts`'s `TOTAL_TOLERANCE` already got in the prior pass.
- **reputation-service**: has no sync HTTP operations of its own (DP-038 is async, triggered by other services) and, per its own Key Rules, permits no self-reported negative delta. `ReputationService.recordDelta` is therefore exposed only via a `REPUTATION_RECORDER` in-process port (no HTTP route at all) — the same scope decision ADR-030's pass already made for budget-service's `recordLedgerEntry`/DP-019. Only `project-service` is wired to call it in this pass; SRV-014.md also names `voting-service` (not yet built), `competency-service`, and `deliberation-service` (both already built, but not wired) as DP-038 triggers — left as open follow-up, consistent with ADR-025's own "none of these call sites are wired yet" precedent for a different port.
- **iam-service**: implements all five of SRV-018's sync operations (DP-069 propose-policy, DP-069 propose-attachment, DP-070 endorse, DP-071 evaluate, DP-072 revoke) against ARCH-024's already-specified schema and algorithm. Grant eligibility (proposer/endorser must hold an active `operator`/`platform_operator` role, revoker additionally `auditor`) is checked live against `GOVERNANCE_ROLE_CHECKER` — the same in-process port project-service and budget-service's future wiring will eventually use, never trusted from the request body. One schema/design-doc conflict surfaced and is resolved in favor of the schema: ARCH-024 §5 says generically a rejected endorsement "flips it to rejected," but `policy_attachment`'s own status enum (TBL-041, `pending_approval|active|revoked`) has no `rejected` value — only `access_policy`'s does. A rejected attachment endorsement lands on `revoked` instead, the closest terminal non-active state TBL-041 actually supports; a rejected *policy* endorsement uses the literal `rejected` status TBL-040 does define.
- **notification-service and ai-synthesis-service: no module, no schema, no routes.** ARCH-023 §1 is explicit that both own no tables and are "out of scope for this pass"; neither `srv-NNN.md` lists a single sync operation either. notification-service's role is realized purely as a new `NOTIFICATION_EMITTER` port (`common/notification-emitter.ts`), an exact structural mirror of the existing `AuditEmitter` (no-op by default, HTTP POST to `NOTIFICATION_SERVICE_URL` when set) — called from civic-duty-service, project-service, and reputation-service wherever their own Key Rules explicitly state "Emits to: notification-service." ai-synthesis-service has no footprint in this app at all: it owns no tables, calls nothing here synchronously, and its advisory output store is explicitly "outside the core governance schema" per its own doc — inventing a stub endpoint for it would be inventing scope the spec doesn't ask for.

## Consequences

- A new migration (`20260911120000_add_civic_duty`) was applied to the shared dev database and validated end-to-end against real Postgres (not just its SQL text) — this required truncating that database's core tables as a side effect of running the existing `*.repository.prisma.spec.ts` tier's `truncateAll` against it; it was restored to empty afterward. Anyone running this tier against a shared database should expect the same.
- Every new cross-module dependency follows the established in-process port pattern (`BUDGET_LEDGER`, `REPUTATION_RECORDER`, reuse of `GOVERNANCE_ROLE_CHECKER`) rather than HTTP, since every service in this pass still shares one app/database (ADR-027/028) — no new inter-service HTTP seam was introduced.
- Follow-up items, tracked here rather than worked around: civic-duty's own DP-040/048/049/052/054 cron/async jobs; competency-service's and deliberation-service's DP-038 reputation triggers; iam-service's `/iam/evaluate` having no caller yet (budget-service's `ledger_entry:record`, project-service's `milestone:report`, governance-role-service's own `approval:submit:operator` are all still unguarded by it, exactly as ADR-025 already flagged); project-service's `assigned`-scope guard has no per-project assignment data to check against.
