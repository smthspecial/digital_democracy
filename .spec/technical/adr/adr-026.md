## Context

ADR-015 committed to Kubernetes + Terraform + Helm without naming a cloud provider, and `infra/terraform/README.md` is explicit that this was left open deliberately ("a real open decision, not an oversight... likely worth its own ADR"). ADR-017 targets 3+ region active-active deployment; ADR-018 targets service-mesh-enforced mTLS zero-trust; ARCH-008 targets a full OpenTelemetry-traces + Prometheus-metrics + Loki-logs observability stack. All three are real, correct target-state decisions — and all three assume an operational scale this project doesn't have yet. Nothing in this repo is deployed anywhere: every service still runs an in-memory store (no service has a real database connection), `infra/helm`/`infra/argocd` are scaffolded but never applied to a running cluster, and `infra/terraform`'s modules are intentionally empty. Standing up multi-region cloud infrastructure, a service mesh, and a three-signal observability pipeline before a single real workload exists to justify any of it would be building the second floor before the first.

The user's own constraint for this phase: no paid vendors, and prefer something lighter than the full ADR-017/018/ARCH-008 target stack.

## Decision

For the current build stage, run on a **single self-hosted k3s cluster** — a single ~70MB Kubernetes binary (CNCF-certified, Apache-2.0, Rancher/SUSE-maintained) that runs identically on a laptop, a cheap VPS, or bare metal — instead of provisioning any cloud provider's managed infrastructure. This directly resolves the deferred Terraform provider question for this phase: the answer is not a cloud provider yet, it's none. k3s ships with Traefik and local-path-provisioner built in, so it satisfies `infra/helm/service`'s existing `HTTPRoute`/Gateway API expectations and gives a working ingress path with nothing extra installed (ARCH-025 §1).

Observability starts with **kube-prometheus-stack** only — Prometheus (metrics), Grafana (dashboards), Alertmanager (alerting) — the highest-value, lowest-complexity slice of ARCH-008's target stack, deployed the same way every service already is (a Helm chart + an ArgoCD Application, ARCH-025 §2). Loki (logs) and the OpenTelemetry tracing pipeline ARCH-008 §1 describes are deliberately deferred: distributed tracing earns its complexity once requests actually cross several real services under load, which isn't true of an all-in-memory, undeployed system yet. ARCH-008 §1's reference to Kafka as the trace-context-propagation transport is also stale — ADR-023 replaced Kafka with NATS JetStream after ARCH-008 was written — corrected alongside this ADR.

ADR-017's multi-region and ADR-018's service-mesh mTLS are deferred, not abandoned. The maturity ladder this phase sits on the first rung of: **single-node k3s (now) → multi-node k3s with HA control plane, still self-hosted, still no cloud vendor (next, once there's a reason to need it) → ADR-017's multi-region cloud target (later, once national-election-day scale is a real concern)**. `infra/helm/service`'s existing `NetworkPolicy` default-deny-with-allow-list template is the interim isolation mechanism in place of mesh-enforced mTLS.

## Consequences

Fault tolerance and self-healing come from primitives already scaffolded and essentially free: k3s reschedules failed pods, `infra/helm/service`'s `HorizontalPodAutoscaler` and (new, ARCH-025 §3) `PodDisruptionBudget` keep capacity up under load and voluntary disruption, and ArgoCD's `selfHeal: true` (already in `infra/argocd/applicationset.yaml`) continuously reconciles cluster state back to git. Basic observability (metrics, dashboards, alerting) costs one more Helm release, no new operational skill the team doesn't already need for k3s itself.

Cost: a single k3s node is a single point of failure until the next rung of the ladder; there is no distributed tracing yet (a cross-service bug has to be debugged from logs/metrics alone); there is no mesh-enforced mTLS yet (`NetworkPolicy` is L3/L4, not identity-based). None of this blocks moving up the ladder later — it is the same Helm chart, the same ArgoCD ApplicationSet, and the same ARCH-008 target stack this phase is explicitly building toward, not a different architecture to migrate off of.
