## Context

AUTH-009/AUTH-010 already define a complete, precise permission catalog for every role in the system, including AUTH-006 (operator) and AUTH-011 (platform-operator) — but every one of those rows is static: a fixed table in a markdown spec, requiring a new ADR/spec edit and a code change in whatever service enforces it to add, remove, or reshape a permission. That rigidity is the right default for citizen rights (AUTH-001–005, 007, 008): those are constitutional-grade guarantees this system's whole design (CON-005) treats as something institutions must not casually reshape. It is the wrong default for AUTH-006/AUTH-011: which specific infrastructure actions an operator or platform-operator credential may take is an operational detail that legitimately needs to change as the organization and its tooling evolve, without a spec PR and a redeploy each time.

A fully open, "attach any policy to anyone" system would itself be a governance-capture vector this system's own anti-corruption architecture (CON-005: "no exclusive proposal access... no untouchable institutions") is designed to prevent — the flexibility has to come with the same non-unilateral, audited change control this system already applies to every other powerful action (ADR-001, ADR-011).

Service-to-service authorization (AUTH-012) is deliberately out of scope here — it is already governed by ADR-018's mutual-TLS/mesh `AuthorizationPolicy` mechanism, a network-layer control that doesn't benefit from an application-level policy engine sitting in front of it.

## Decision

A new service, `iam-service` (SRV-018), owns a small, AWS-IAM-shaped policy model — versioned `access_policy` documents (`effect`: allow/deny, `actions`, `resources`, optional `conditions`) attachable to a principal (an individual operator/platform-operator citizen, or role-wide) — and a single evaluation entrypoint other services call to answer "may principal X take action Y on resource Z." Evaluation is default-deny, explicit-deny-overrides-allow, exactly AWS IAM's own algorithm (ARCH-024 §3).

Granting new access (proposing a policy or attaching one to a principal) requires **dual control**: a second, independent citizen holding an active governance role of the *same* role_type as the proposer (operator or platform-operator) must endorse it before it takes effect — modeled directly on DP-068's existing break-glass co-approval pattern, not the heavier three-layer `citizen_supermajority`/`audit_confirmation`/`body_endorsement` process DP-035 already uses for identity revocation and protocol changes (which structurally doesn't apply here: none of those three approval types maps to the `implementation` layer operator/platform-operator roles occupy — see ARCH-024 §2). Revoking access does not require dual control, mirroring DP-068's own asymmetry ("either co-approving platform-operator, or an audit body finding, may revoke... manually"): any citizen holding an active operator, platform-operator, or auditor role may revoke a policy or attachment unilaterally. Granting is hard and non-unilateral; revoking is easy — the fail-safe direction always points toward less standing access, never more.

Every policy and attachment is publicly readable (consistent with `governance_role`'s own PUBLIC classification, ARCH-023 §6, and CON-005's "no hidden... no exclusive access") — anyone can see who has been granted what, and by whom. Every propose/endorse/activate/revoke transition emits to `audit-service` via the existing `AuditEmitter` seam pattern.

## Consequences

Operators and platform-operators get exactly the configurability that motivated this ADR — new permissions or principal grants without a code deploy — while the two things that made a fully open system dangerous are structurally prevented: no single citizen can grant themselves or anyone else new access (dual control), and every grant is public and audit-logged (no exclusive/hidden access). AUTH-010's AUTH-006/AUTH-011 rows are not deleted; they become the seed/default policy set iam-service is bootstrapped with, not a hardcoded enforcement path any service reimplements independently.

Cost: this is a new service and a new dependency in the write path of every operator/platform-operator-gated operation across the codebase (budget-service's `ledger_entry:record`, project-service's `milestone:report`, governance-role-service's own `approval:submit:operator`, and any future ones) — none of those call sites are wired to it yet; that wiring is separate follow-on work, same as every other cross-service integration this codebase currently documents as an open seam (ARCH-010/011/012's pattern). Citizen-facing permissions (AUTH-001–005, 007, 008) and service-to-service authorization (AUTH-012/ADR-018) are explicitly untouched by this decision.
