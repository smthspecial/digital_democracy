## Context

ADR-019 splits 17 backend services across Go and TypeScript, and ADR-022 adds a Next.js web client and an Expo mobile client on top. All of it — services, apps, shared contracts, and infrastructure code — needs to live somewhere a contributor can reason about as one system rather than N unrelated repositories, without adopting a heavyweight polyglot build system (Bazel-class tooling) that would add its own steep operational learning curve to a project already carrying significant domain complexity.

## Decision

One git repository, laid out as:

```
apps/            Next.js web client, Expo mobile client
services/ts/     the 13 TypeScript services (ADR-019)
services/go/     the 4 Go services (ADR-019)
packages/        shared TS: tsconfig base, eslint config, generated api-client
infra/           Helm chart(s), Terraform, Argo CD
.spec/           existing project spec (unchanged)
```

JavaScript/TypeScript workspaces (`apps/*`, `services/ts/*`, `packages/*`) are managed by pnpm workspaces, with Turborepo on top to cache and parallelize `build`/`lint`/`typecheck`/`test` across only the packages a change actually touches. Go services are not part of the pnpm workspace — each is its own Go module (its own `go.mod`), and a root `go.work` file ties them together for local cross-module development, per Go's own multi-module workspace mechanism rather than forcing Go through JS tooling. A root `Makefile` provides the handful of commands that span both ecosystems (`make dev`, `make build`, `make test`), each delegating to `turbo` or `go` underneath. CI (GitHub Actions, since `.github/` already anchors this repo there) runs a TS job via Turborepo and a Go job via a matrix over `services/go/*`.

## Consequences

Turborepo's affected-scope caching keeps CI fast as the number of TS services grows past a dozen; the Go side stays idiomatic (no attempt to make `go build` pretend to be an npm script) at the cost of needing two mental models for "how do I build this repo," addressed by the Makefile as the single entry point that hides which underlying tool runs. Adding a new service means adding a directory and one workspace-glob-matched entry — no central registry file to keep in sync, other than `go.work`'s explicit `use` list for Go modules.
