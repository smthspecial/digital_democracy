## Context

No service in this codebase has a real database yet — every one of the 21 services persists to an in-memory, mutex/Map-guarded store (confirmed: no `.sql`, no migrations, no DB driver dependency, no `DATABASE_URL`-shaped env var anywhere in the repo as of this ADR). ADR-015 already decided the deployment shape (database-per-service, dedicated Postgres cluster, no shared database), and AUTH-009/AUTH-010 already define a precise, scope-typed authorization model (`own`, `jurisdiction:member`, `proposal:author`, `domain:match`, `assigned`, `session:issued`, plus condition tokens like `coi.none`, `role.term`, `token.unused`) — but that model is enforced only in application code today, with no DB-level backstop, and AUTH-010 itself is explicit that "no service may implement ad hoc authorization logic outside this schema."

Two invariants make "just enforce it in app code" an insufficient answer on their own: ADR-002 requires that `ballot` never become joinable back to a citizen even by an operator with direct database access, and FR-060/FR-065/NFR-015 require `audit_log` to be genuinely append-only and hash-chained, not append-only "by convention." A row-security bug in one service's application layer should not be able to leak another citizen's private rows, and no database-level actor — buggy code, a compromised connection, or an operator running an ad hoc query — should be able to rewrite history.

## Decision

Every service's own Postgres database gets Row-Level Security enabled and forced on every table, two roles (`<svc>_app` for the citizen-facing request path, `<svc>_worker` for internal jobs and peer-service HTTP handlers), and a small set of policy templates keyed to AUTH-010's scope types, plus append-only enforcement (`REVOKE` + trigger) on `audit_log`, `ballot`, and `ledger_entry`. The full pattern — roles, session GUCs, policy templates, and a table-by-table classification for all 39 documented tables — is specified in ARCH-023, not repeated here.

The central boundary this decision draws: RLS enforces `own` and other scope checks that are resolvable from data inside the same service database. AUTH-010 scope types that require another service's data (`jurisdiction:member`, `jurisdiction:affected`, most `assigned` cases) cannot be checked by a same-database RLS policy under ADR-015's no-cross-database-join constraint — those stay exactly where they already are, resolved by the calling service over the existing HTTP integration-seam pattern (ARCH-010/011/012's `IdentityChecker`/`JurisdictionClient`/`ApprovalGate` seams) before the write reaches the database. RLS is additive defense-in-depth behind that seam, not a replacement for it, and ARCH-023 §5 documents the boundary explicitly rather than faking a local check that wouldn't actually verify the real condition.

Constraint-level consistency (`NOT NULL`, `CHECK` on enum-shaped columns, `UNIQUE` on invariants like one-legal-identity-per-citizen or one-support-per-citizen-per-problem, `FOREIGN KEY` only within a single service's database) is added in the same migrations as the RLS policies, since both come from the same `tbl-NNN.md` source of truth and are naturally authored together.

## Consequences

Migrations exist per service (`services/<go|ts>/<name>/db/migrations/0001_init.{up,down}.sql`) as schema + policy, ready for whichever service is next wired to a real Postgres connection — this ADR does not itself connect any service's application code to Postgres (every service still runs in-memory today) or choose a migration-runner binary; both are separate follow-on work. `notification-service` and `ai-synthesis-service` own no documented tables and are out of scope.

Cost: two roles and a session-GUC contract (`SET LOCAL app.citizen_id` per transaction) become a hard requirement for whichever future work actually connects a service to its database — that connection code must set the GUC correctly on every request or the `_app` role's policies silently deny everything. This is the same shape of seam this codebase already relies on elsewhere (mTLS workload identity for service calls, ADR-018), not a new category of risk.

Realizes defense-in-depth for AUTH-009/010's `own`-scoped permissions and NFR-001/ADR-002's ballot secrecy at the storage layer; does not by itself close any of the cross-service authorization gaps ARCH-010/011/012 already document as open (those require the HTTP seams themselves, not a DB policy).
