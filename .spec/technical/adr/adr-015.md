## Context

The system is already decomposed into 17 domain services (SRV-001 through SRV-017, see ARCH-005) communicating via sync calls and named async queues, but no runtime or deployment model was ever chosen — the original white paper's technology section was left as an unfilled outline. The system must reach 10 million registered citizens and sustain 100,000 concurrent active citizens (NFR-009) without a single point of failure or single point of control (NFR-011, ADR-001), and must stay open-source per ADR-008 (no blockchain maximalism, no proprietary lock-in).

## Decision

Package each of the 17 domain services as an independently deployable container. Each service gets its own Kubernetes Deployment (or StatefulSet for stateful workers), its own dedicated Postgres database, and its own Kubernetes namespace — no database is ever shared across two services. Service boundaries in ARCH-005's data-process classification are the deployment and database boundaries.

All infrastructure is defined as code: Terraform for cloud and network resources, Helm charts per service. The stack is built entirely from open-source components, deployed on a Kubernetes distribution that avoids single-vendor lock-in.

Cross-service consistency uses the existing async queue/event pattern from ARCH-005 — no distributed transactions.

## Consequences

Each service scales and deploys independently, which matters because load is uneven (voting-service spikes hard on vote-close days; budget-service does not). A failure in one service cannot cascade into another's database.

Cost: operating 17+ independently deployed services requires shared platform tooling — common CI/CD templates, a service mesh, unified observability (see ARCH-006). Polyglot implementation is technically possible but should be constrained to a small approved language/runtime set to keep operational load manageable.

Realizes NFR-009, NFR-011; consistent with ADR-001's anti-capture layering and ADR-008's open-source commitment.
