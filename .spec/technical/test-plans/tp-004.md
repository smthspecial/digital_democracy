## Overview

This flow covers the pipeline from a citizen submitting a problem (FR-015) through public endorsement (FR-016), competing proposal creation against that problem (FR-018), the population-scaled support-threshold gate into development (FR-017, FR-019), and the full proposal lifecycle through the budget/scope/constitutional-review gate into voting (FR-008, FR-037) or into the FR-034 deadlock escape hatch. Both `problem-service` (SRV-003) and `proposal-service` (SRV-004) are real, fully-implemented Fastify services with real HTTP surfaces and in-memory stores — `proposal-service` in particular is the most complete service in the repo (61 unit tests covering its full state machine). The flow crosses the service boundary only through problem-service's `ThresholdChecker` seam (`collaborators.ts`), and that seam is a no-op today (`noopThresholdChecker`) with **no real callable counterpart on proposal-service's side at all** — there is no endpoint on proposal-service that lets problem-service report "problem X's endorsement count is now N" and have it recompute any linked proposal's threshold state. The FR-017 support-threshold gate that actually governs `gathering_support → development` is instead driven entirely by proposal-service's own directly-callable `POST /proposals/:id/support` endpoint, which is a separate per-proposal support mechanism unconnected to problem-level endorsement. This test plan depends on a new `HttpThresholdChecker` implementation (problem-service → proposal-service) and, since no receiving endpoint for it exists yet, a new proposal-service endpoint to go with it; every other seam this flow touches — `ConstitutionalReviewer`, `VoteSessionRequester`, `AuditEmitter`, `AssignmentChecker` (proposal-service's `integrations.ts`) — models a downstream service (audit-service/SRV-012, voting-service/SRV-007, governance-role-service/SRV-011) that doesn't exist as a running service in this codebase either, so those scenarios stay marked `blocked on:` per ARCH-009 §2.

## 2. Preconditions & fixtures

All fixtures are built through each service's real public API — no direct store access, per ARCH-009 §2.

- **A public problem**: `POST /problems` on problem-service with `citizen_id`, `title`, `description`, `affected_area`, `candidate_scope` → `status: "open"`.
- **Endorsements on it**: `POST /problems/:id/support` with a distinct `citizen_id` per call (DP-004; unique per `(problem_id, citizen_id)`).
- **A proposal linked to that problem**: `POST /proposals` on proposal-service with `problem_id` set to the problem's real id (DP-005). Note: proposal-service performs **no existence check** against problem-service — any string is accepted as `problem_id` (see EC-32).
- **Competing proposals**: repeat proposal creation with the same `problem_id`, different `title`/`author_id` (FR-018) — `GET /proposals` has no `problem_id` query filter, so a fixture harness must filter the full list client-side.
- **Proposal at `gathering_support`**: `POST /proposals/:id/advance` from `draft` (always allowed).
- **Proposal at `development`**: from `gathering_support`, first `POST /proposals/:id/scope-assignment` (`scope_jurisdiction_id`, `population` → sets `support_threshold = ceil(population * 0.05)`), then `POST /proposals/:id/support` with enough distinct citizens to reach `support_threshold`, then `POST /advance`.
- **Proposal at `voting`**: from `development`, `PUT /proposals/:id/budget` with all four fields (`cost`, `funding_source`, `maintenance_cost`, `expected_benefits`) non-null, no scope challenge pending, then `POST /advance` (constitutional-review stub clears by default).
- **Proposal at `approved` / `rejected`**: from `voting`, `POST /proposals/:id/resolve` with the outcome.
- **Proposal `archived`**: `POST /proposals/:id/resolve` with `outcome: "archived"` from any non-terminal status.
- **Proposal in the deadlock track**: `POST /proposals/:id/deadlock/enter` from `development` or `voting` only (FR-034).

## 3. Happy path scenarios

### HP-1 — Problem submitted, publicly endorsed, and a proposal created against it
Level: **integration** (two real services, no mocked business logic on either side)

1. `POST /problems` (problem-service, DP-003) → 201, `status: "open"`, publicly readable via `GET /problems/:id` immediately (FR-016).
2. Three distinct citizens each `POST /problems/:id/support` (problem-service, DP-004) → 200, `support_count` 1, 2, 3 in order.
3. `GET /problems/:id` and `GET /problems` (problem-service) confirm the endorsement count is visible (FR-016 auditability).
4. `POST /proposals` (proposal-service, DP-005) with `problem_id` set to the problem's id → 201, `status: "draft"`, `problem_id` matches, `support_count: 0`, `support_threshold: null`.

End state: one `open` problem with 3 endorsements; one `draft` proposal carrying its `problem_id`.

### HP-2 — A single proposal's fully-eligible, uncontested lifecycle from draft to approved
Level: **e2e** (the full citizen-facing proposal journey through proposal-service's real HTTP surface, per ARCH-009 §1's no-UI redefinition)

1. `POST /proposals` (proposal-service, DP-005) with the HP-1 problem's id → `draft`.
2. `POST /proposals/:id/constraints` (DP-006) → 201, constraint recorded, `agreed: false`.
3. `POST /proposals/:id/advance` → `gathering_support`.
4. `POST /proposals/:id/scope-assignment` with `population: 1000` → `support_threshold: 50`, `scope_jurisdiction_id` set (FR-008).
5. 50 distinct citizens `POST /proposals/:id/support` → `support_count: 50`.
6. `POST /proposals/:id/advance` (DP-029, FR-017) → `development`.
7. `PUT /proposals/:id/budget` (DP-007) with all four fields → budget complete (FR-037).
8. `POST /proposals/:id/advance` (DP-029, FR-037, FR-008) → `voting`; `VoteSessionRequester.requestSession` called exactly once.
9. `POST /proposals/:id/resolve` with `outcome: "approved"` → `approved`.

End state: proposal `status: "approved"`, budget complete, scope assigned, one agreed-pending constraint, `support_count === support_threshold`.

## 4. Edge cases

### Input validation

- **EC-1**: `POST /problems` missing a required field → 400, `{error}` body (problem-service, FR-015). Level: integration.
- **EC-2**: `POST /proposals` missing a required field → 400 (DP-005). Level: integration.
- **EC-3**: `POST /problems/:id/status` with an unrecognized status enum value → 400, and this fires from Fastify schema validation *before* the existence check runs (verified even against a real id) (problem-service). Level: integration.
- **EC-4**: `PUT /proposals/:id/budget` with a negative `cost` or `maintenance_cost` → 400 (schema `minimum: 0`) (DP-007, FR-037). Level: e2e.
- **EC-5**: `POST /proposals/:id/scope-assignment` with negative `population` → 400 (FR-008). Level: e2e.

### State-machine violations

- **EC-6**: Every illegal problem status transition — `open→closed`, `open→open`, `proposing→open`, `proposing→proposing`, `closed→open`, `closed→proposing`, `closed→closed` — → 409 (problem-service; SRV-003's `FORWARD_TRANSITIONS`). Level: integration.
- **EC-7**: `POST /proposals/:id/constraints` while status is `voting`, `approved`, `rejected`, or `archived` → 409, constraint list unchanged (DP-006, `CONSTRAINT_ADD_STATUSES` restricts adds to `draft`/`gathering_support`/`development`). Level: e2e.
- **EC-8**: `POST /proposals/:id/advance` from `gathering_support` before `support_count` reaches `support_threshold` → 409 with both values named in the error message (FR-017). Level: e2e.
- **EC-9**: `POST /proposals/:id/advance` from any status with no automatic transition defined (`voting`, `approved`, `rejected`, `archived`) → 409 ("no automatic advance is defined from status X"). Level: e2e.
- **EC-10**: `POST /proposals/:id/resolve` to `approved`/`rejected` attempted from `draft`, `gathering_support`, or `development` (i.e. any non-`voting` status) → 409 (only `voting → approved|rejected` is legal). Level: e2e.
- **EC-11**: `POST /proposals/:id/resolve` to `archived` attempted from an already-terminal status (`approved`, `rejected`, `archived`) → 409. Level: e2e.
- **EC-12**: `POST /proposals/:id/deadlock/enter` from an ineligible status (`draft`, `gathering_support`, or any terminal status) → 409 — only `development`/`voting` are `DEADLOCK_ELIGIBLE_STATUSES` (FR-034). Level: e2e.
- **EC-13**: `POST /proposals/:id/deadlock/enter` twice on the same proposal (double-entry) → 409 the second time. Level: e2e.
- **EC-14**: `POST /proposals/:id/deadlock/advance` before deadlock has been entered → 409. Level: e2e.
- **EC-15**: Normal `POST /proposals/:id/advance` is blocked with 409 while deadlock is active, even from a status/state that would otherwise pass every gate (FR-034 hijacks the normal machine). Level: e2e.
- **EC-16**: Normal `POST /proposals/:id/resolve` is blocked with 409 while deadlock is active, even from `voting` with a valid outcome. Level: e2e.
- **EC-17**: `POST /proposals/:id/deadlock/advance` reaching `final_decision` without supplying `outcome` → 400 (validation error, distinct from the 409s elsewhere in the deadlock machine) (FR-034). Level: e2e.
- **EC-18**: The deadlock escape hatch resolves a proposal that was in `development` (not `voting`) to `approved`, bypassing the normal budget/scope/constitutional-review gates entirely — proves FR-034 can conclude a case regardless of the status it was entered from. Level: e2e.
- **EC-19**: The deadlock escape hatch walks the full 8-stage sequence (`constraint_analysis → alternative_generation → resource_partitioning → compensation_assessment → citizen_assembly_review → escalation_review → constitutional_review → final_decision`) entered from `voting`, resolving to `rejected` — confirms both entry points and either terminal outcome. Level: e2e.

### Authorization / eligibility

- **EC-20**: `POST /proposals/:id/deadlock/advance` by a reviewer the `AssignmentChecker` seam reports as unassigned → 403; the same call with the seam reporting assigned → 200 (FR-034). Level: e2e (single-service, seam-mocked — matches proposal-service's own unit coverage but is worth re-verifying at this level since it's the flow's only authorization gate).
- **EC-21** (blocked on: missing eligibility check): a citizen outside a problem's `candidate_scope`/jurisdiction endorsing it, or supporting a proposal outside its `scope_jurisdiction_id` — neither service performs any jurisdiction/eligibility check on `citizen_id` today (any string is accepted). Documented per ARCH-009 §2 rather than assumed to work.

### Threshold & boundary conditions

- **EC-22**: `support_count` exactly equal to `support_threshold` → `advance` succeeds (boundary — the gate is `<`, not `<=`) (FR-017). Level: e2e.
- **EC-23**: `support_count` exactly one under `support_threshold` → `advance` fails 409 (FR-017). Level: e2e.
- **EC-24**: `population: 0` at scope-assignment → `support_threshold = ceil(0 * 0.05) = 0`, so `gathering_support → development` advances immediately with zero supporters — a real trivial-threshold risk worth flagging against FR-017's interest-group-capture concern (US-012 traceability note). Level: e2e.
- **EC-25**: Threshold rounding at non-exact-multiple populations — `population: 19 → threshold: 1`, `population: 1001 → threshold: 51`, vs. the exact multiple `population: 1000 → threshold: 50` (confirms `Math.ceil`, not floor/round). Level: e2e.
- **EC-26**: `votingGateMissingFields` reports each of the five gate fields (`cost`, `funding_source`, `maintenance_cost`, `expected_benefits`, `scope_jurisdiction_id`) by name in the 409 error, both singly-missing and in combination (FR-037, FR-008). Level: e2e.
- **EC-27**: A problem with zero endorsements and zero linked proposals is still publicly visible and returns an empty `problem_support`/proposal list rather than erroring (FR-016 empty-collection boundary). Level: integration.

### Concurrency & idempotency

- **EC-28**: Duplicate endorsement of the same problem by the same citizen → second call 409, `support_count` unchanged from the first call, `ThresholdChecker.checkThreshold` **not** invoked on the rejected duplicate (problem-service, DP-004's unique-per-citizen constraint). Level: integration.
- **EC-29**: Duplicate support of the same proposal by the same citizen → second call 409, `support_count` unchanged. Level: e2e.
- **EC-30**: Resolving the same scope challenge twice → second call 409 ("already resolved") (DP-020). Level: e2e.
- **EC-31** (blocked on: HttpThresholdChecker + receiving endpoint): DP-028's documented idempotency claim ("multiple concurrent DP-004 events safely collapse") can't be exercised because the worker is only a no-op seam today, not real code — no concurrent-collapse behavior exists to test yet.

### Cross-service failure & degradation

- **EC-32** (blocked on: HttpThresholdChecker implementation + new proposal-service endpoint): endorsing a problem never changes any linked proposal's `support_count`/`support_threshold` today — the seam is a no-op and no receiving endpoint exists on proposal-service to call even if it were implemented.
- **EC-33** (blocked on: new seam + endpoint): `problem.status` is never auto-transitioned by proposal-service lifecycle events (SRV-003's documented `open → proposing` on a linked proposal reaching `development`, `proposing → closed` on approval/all-rejected) — no seam interface exists in problem-service's `collaborators.ts` for proposal-service to call.
- **EC-34**: proposal-service accepts any string as `problem_id` at creation with no existence check against problem-service — creating a proposal against a nonexistent `problem_id` succeeds (201) silently, since proposal-service never calls problem-service either (mirrors EC-32/EC-33: the gap runs in both directions). Level: integration.
- **EC-35** (blocked on: SRV-012 implementation): DP-034's constitutional review is fully synchronous and in-process (`defaultConstitutionalReviewer`) rather than a real call to an audit-service constitutional-review authority that doesn't exist as a running service — a downstream-down/slow/erroring scenario for it can't be exercised for real yet.
- **EC-36** (blocked on: SRV-007, SRV-012 implementations): `VoteSessionRequester.requestSession` and both services' `AuditEmitter.emit` are fire-and-forget no-ops with no live target service — voting-service and audit-service don't exist, so no failure/degradation behavior (fail-closed vs. degrade) can be observed or asserted yet.

### Data integrity & audit

- **EC-37**: Every proposal status transition (`draft→gathering_support`, `gathering_support→development`, `development→voting`, `voting→approved|rejected`, archive-from-any-non-terminal, and both deadlock-track entry/exit transitions) invokes `AuditEmitter.emit("proposal.status_changed", {proposalId, from, to})` exactly once — verified via a spy `AuditEmitter` across each transition (DP-036). Level: e2e.
- **EC-38**: Problem creation and status change invoke problem-service's `AuditEmitter.emit("problem.created" | "problem.status_changed", ...)` — same pattern, verified via spy (DP-036). Level: integration.
- **EC-39**: The deadlock's history array is retained as an immutable audit trail past resolution — `GET /proposals/:id/deadlock` after the case concludes still returns the full 8-entry `history` (stage, `reviewer_id`, notes, timestamp per entry) with `active: false` and `resolved_at` set, not cleared (FR-034). Level: e2e.

## Status update (2026-08-28)

`proposal-service` now has a real `ProblemStatusNotifier` HTTP seam, closing EC-33. `createHttpProblemStatusNotifier` (`integrations.ts`) calls problem-service's already-existing `POST /problems/:id/status`, wired in by `index.ts` when `PROBLEM_SERVICE_URL` is set, no-op by default otherwise. It fires `proposing` when a proposal reaches `development` and `closed` once every proposal linked to a problem is in a terminal status (`approved`, `rejected`, or `archived` — SRV-003's "approved or all rejected/archived" rule collapses into one check, since a single approved proposal already satisfies "every proposal for this problem is terminal" on its own). Fire-and-forget, matching every other cross-service notification in this codebase. Confirmed end-to-end against a real problem-service in the e2e suite, both trigger paths, including the multi-proposal case where a competing proposal being rejected doesn't close the problem until every proposal for it is terminal.

`EC-31`/`EC-32` (the `ThresholdChecker`/DP-028 half of this doc's central gap) remain deliberately blocked, unlike EC-33: DP-028's description specifies the threshold source as the *problem's* endorsement count, which conflicts with proposal-service's actual, heavily-tested implementation where `support_count` is proposal-service's own independent counter with no connection to problem-level endorsements. Building the seam would mean guessing whether DP-028 replaces, feeds into, or runs alongside that existing mechanism — a real architecture decision with no clear enough answer in the spec, unlike EC-33's unambiguous existing receiving endpoint and semantics. Documented per ARCH-009 §2 rather than guessed at.
