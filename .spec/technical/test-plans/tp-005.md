## Overview

This flow covers the full lifecycle a domain-competency claim goes through in `competency-service` (SRV-005) — application, five-stage verification pipeline, expiry, challenge, revocation — plus the conflict-of-interest declaration/auto-exclusion path, and the one cross-service consequence that must never leak: competency and reputation are read-only, advisory signals that cannot alter voting weight or grant veto power (FR-020, FR-023). Both `competency-service` and `reputation-service` (SRV-014) are real, independently bootable Fastify services today, each with a working in-memory store and full unit coverage of their own single-service logic (`applications.test.ts`, `challenges.test.ts`, `conflicts.test.ts`, `assessments.test.ts`, `expiry.test.ts`, `reputation.test.ts`).

What does **not** exist today is any real cross-service wiring between them, or from either of them to their documented collaborators. `competency-service`'s `ExclusionEnforcer` and `NotificationEmitter` (`services/ts/competency-service/src/integrations.ts`) are no-op-by-default seams with no HTTP-calling implementation, and `competency-service` has **no `AuditEmitter` seam at all**, despite SRV-005 documenting an emission to `audit-service` (DP-036). Most significantly, DP-032's mandate that an upheld challenge "triggers DP-038 (negative reputation delta)" has **no seam of any kind** in `competency-service` — `resolveChallenge()` (`services/challenges.ts`) revokes the competency locally and stops; there is no interface, no no-op stub, nothing to swap for an `HttpReputationClient`. `reputation-service` itself is more complete: its `AuditEmitter` and `NotificationEmitter` (`services/reputation.ts`) are wired and exercised, just still no-op. This doc's integration/e2e scenarios exercise what's real today (both services' public HTTP surfaces, called directly) and mark every scenario that depends on a seam that doesn't exist yet as `blocked on:`, per ARCH-009 §2.

## 2. Preconditions & fixtures

All fixtures are built through each service's own real public API — no direct store manipulation, per ARCH-009 §2.

- **A domain**: `POST /competency/domains` on competency-service with `{ name, description }` → `id` used as `domain_id` everywhere below. (`requireDomain()` is checked on every operation that takes a `domain_id`, so an unknown domain 404s before any state changes.)
- **A citizen with `active` competency in a domain**: `POST /competency/applications` (`status=applied`, `stage=application`) → `POST /competency/applications/:id/advance` called exactly 4 times, walking `application → automated_credential_check → public_review_period → domain_review → recorded_approval`. The 4th advance flips `status` to `active`, sets `granted_at = now()` and `expires_at = now() + 365d` (`COMPETENCY_VALIDITY_MS` in `services/competency.ts`).
- **A citizen with an active competency about to expire**: same as above, then advance the system clock (or seed `expires_at` in the past via test-only clock injection, not store access) so `POST /competency/expiry-sweep` will pick it up.
- **A conflict of interest on a domain**: `POST /competency/conflicts` with `{ citizen_id, domain_id, description }` for a citizen (does not require the citizen to already hold competency in that domain — `declareConflict()` only calls `requireDomain()`, not `requireCompetency()`).
- **A resolvable challenge against an active competency**: `POST /competency/challenges` with `{ competency_id, challenger_id, reason, evidence_ref }` against a competency obtained above.
- **A reputation baseline for a citizen**: `GET /reputation/citizens/:id` before any records exist returns `{ citizen_id, total: 0, records: [] }` — this is itself HP material, not a fixture step.
- **A proposal to attach an assessment to**: per ARCH-012, `proposal_id` is accepted by `POST /competency/assessments` as an opaque string — `publishAssessment()` never calls proposal-service to validate it exists or is in any particular status (see EC in §4.6). A realistic fixture still creates a real proposal via proposal-service for e2e scenarios that then check the assessment is visible without affecting that proposal's lifecycle.

## 3. Happy path scenarios

**HP-1 — Full competency acquisition pipeline to `active` (DP-011, DP-031, FR-022).** Level: integration.
1. `POST /competency/domains` creates a domain.
2. `POST /competency/applications {citizen_id, domain_id}` on competency-service → `201`, `status=applied`, `stage=application`.
3. `POST /competency/applications/:id/advance` four times in sequence.
4. Assert: after advance #1–3, `status` stays `applied` and `stage` moves through `automated_credential_check`, `public_review_period`, `domain_review`. After advance #4, `status=active`, `stage=recorded_approval`, `granted_at` set, `expires_at = granted_at + 365d`.
5. `GET /competency/citizens/:citizenId/domains/:domainId` → `{ active: true }`.

**HP-2 — Domain independence: competency in one domain confers nothing in another (FR-021).** Level: integration.
1. Create two domains A and B.
2. Run HP-1's pipeline for a citizen in domain A only.
3. `GET /competency/citizens/:citizenId/domains/:domainA` → `{ active: true }`.
4. `GET /competency/citizens/:citizenId/domains/:domainB` → `{ active: false }`.

**HP-3 — Rejected application halts the pipeline (FR-022).** Level: integration.
1. `POST /competency/applications` → `applied`/`application`.
2. `POST /competency/applications/:id/reject` → `status=rejected`.
3. `GET /competency/citizens/:citizenId/domains/:domainId` → `{ active: false }`.

**HP-4 — Publish an expert assessment as an eligible, undisclosed-conflict-free expert (DP-021, FR-023, ADR-007).** Level: integration.
1. Complete HP-1 to get an `active` competency for citizen E in domain D.
2. `POST /competency/assessments {proposal_id, citizen_id: E, domain_id: D, content, score}` → `201`, `expertId=E`.
3. Assert the assessment is retrievable and carries no authority to change the proposal's status — no call is made to proposal-service to alter it, confirming FR-023's "advisory, cannot block or delay voting" in the strongest available sense (competency-service never talks to proposal-service at all).

**HP-5 — Declare a conflict of interest (DP-010, FR-025).** Level: integration.
1. `POST /competency/conflicts {citizen_id, domain_id, description}` → `201`.
2. Assert the injected `ExclusionEnforcer.exclude(citizen_id, domain_id)` fires exactly once with those arguments (verifiable today against the stub; against a real `governance-role-service` target only once that seam exists — see §1).

**HP-6 — Submit and dismiss a competency challenge (DP-012, DP-032, FR-024).** Level: integration.
1. Complete HP-1 for a citizen.
2. `POST /competency/challenges {competency_id, challenger_id, reason, evidence_ref}` → `201`, `status=open`.
3. `POST /competency/challenges/:id/resolve {result: "dismissed"}` → `status=dismissed`.
4. `GET /competency/citizens/:citizenId/domains/:domainId` → still `{ active: true }` (dismissal does not revoke).

**HP-7 — Submit and uphold a competency challenge, revoking the competency (DP-012, DP-032, FR-024).** Level: integration.
1. Complete HP-1 for a citizen; submit a challenge as in HP-6.
2. `POST /competency/challenges/:id/resolve {result: "upheld"}` → `status=upheld`.
3. `GET /competency/citizens/:citizenId/domains/:domainId` → `{ active: false }` (competency `status=revoked`).
4. **Blocked on:** the missing reputation seam (§1) — DP-038's negative delta on the challenged citizen cannot be asserted end-to-end until competency-service gains a way to call `reputation-service`. Document as e2e once that seam exists: `POST /competency/challenges/:id/resolve {upheld}` → competency-service calls reputation-service → `GET /reputation/citizens/:id` shows a new `undisclosed_conflict` or equivalent negative-polarity record with `source_ref` pointing at the challenge id (required — `recordEvent()` rejects a negative-polarity record with no `source_ref`).

**HP-8 — Record and read back a reputation delta directly (DP-038, FR-027).** Level: integration.
1. `POST /reputation/records {citizen_id, factor_type: "constructive", delta: 5, source_ref: ""}` → `201`.
2. `GET /reputation/citizens/:id` → `total: 5`, one record.
3. `GET /reputation/citizens/:id/records` → the same record, scoped to that citizen only.

**HP-9 — Competency expiry sweep (DP-044, FR-026).** Level: integration.
1. Complete HP-1 for a citizen with a clock/`expiresAt` seeded in the past (via constructor injection, not store access).
2. `POST /competency/expiry-sweep` → `expired_count: 1`.
3. `GET /competency/citizens/:citizenId/domains/:domainId` → `{ active: false }`.
4. Re-run `POST /competency/expiry-sweep` immediately → `expired_count: 0` (idempotent — already covered at unit level in `expiry.test.ts`; the integration angle is confirming the citizen-status read reflects it).

## 4. Edge cases

### 4.1 Input validation
- **EC-1.** `POST /competency/applications` missing `citizen_id` or `domain_id` → `400` (schema `required`/`additionalProperties: false`). FR-022. Level: integration.
- **EC-2.** `POST /competency/applications` against an unknown `domain_id` → `404` (`requireDomain`). FR-021, FR-022. Level: integration.
- **EC-3.** `POST /competency/challenges` with no `evidence_ref` (anonymous, evidence-free challenge) → `400` — schema requires `evidence_ref`, enforcing FR-024's "anonymous, evidence-free accusations are rejected" acceptance criterion at the transport boundary, not just in prose. FR-024, DP-012. Level: integration.
- **EC-4.** `POST /competency/challenges` with an invalid `reason` enum value → `400` (schema `enum: [credentials, conflict, false_claim, misconduct]`). FR-024. Level: integration.
- **EC-5.** `POST /competency/conflicts` against an unknown `domain_id` → `404`. FR-025. Level: integration.
- **EC-6.** `POST /reputation/records` with a positive-polarity `factor_type` (e.g. `constructive`) and `delta <= 0` → `400` ("positive-polarity ... requires delta > 0"). FR-027. Level: integration.
- **EC-7.** `POST /reputation/records` with a negative-polarity `factor_type` (e.g. `fraud`) and `delta >= 0` → `400`. FR-027. Level: integration.
- **EC-8.** `POST /reputation/records` with a negative-polarity `factor_type` and a missing or empty (whitespace-only) `source_ref` → `400` — enforces DP-038's "negative deltas require an upstream authoritative decision" at the API boundary, since a negative delta with no `source_ref` has no traceable authority behind it. FR-027, DP-038. Level: integration.
- **EC-9.** `POST /reputation/records` with an unknown `factor_type` → `400` (schema enum of the 8 defined factor types only — no free-text factor types possible). FR-027. Level: integration.
- **EC-10.** `POST /competency/assessments` with a `proposal_id` that does not correspond to any real proposal in proposal-service → `201` succeeds anyway (no cross-service existence check in `publishAssessment()`). This is a genuine current gap, not a spec-mandated behavior: flag as a scenario to watch, not a defect to silently accept — document expected behavior once/if DP-021 gains a proposal-existence check. FR-023, DP-021. Level: integration, `blocked on: no cross-service validation exists to test against; scenario documents current (permissive) behavior`.

### 4.2 State-machine violations
- **EC-11.** `POST /competency/applications/:id/advance` on a competency already `active` (fully advanced) → `409` ("not in an advanceable state"). FR-022. Level: integration.
- **EC-12.** `POST /competency/applications/:id/advance` on a `rejected` application → `409` (cannot resume past rejection). FR-022. Level: integration.
- **EC-13.** `POST /competency/applications/:id/reject` on an already-`rejected` application → `409`. FR-022. Level: integration.
- **EC-14.** `POST /competency/applications/:id/advance` or `/reject` against an unknown application id → `404`. Level: integration.
- **EC-15.** `POST /competency/challenges/:id/resolve` on a challenge already `upheld` or `dismissed` → `409` ("already resolved") — a challenge cannot be re-resolved to flip its outcome after the fact. FR-024. Level: integration.
- **EC-16.** `POST /competency/challenges` against a `competency_id` that does not exist → `404`. FR-024. Level: integration.
- **EC-17.** A challenge upheld against a competency that has already `expired` (not `active`) still transitions it to `revoked` — `revokeCompetency()` has no status-precondition check, so `expired → revoked` succeeds unconditionally. Worth asserting explicitly since it means expiry and revocation are not mutually exclusive terminal states in this implementation. FR-024, FR-026. Level: integration.
- **EC-18.** `POST /competency/expiry-sweep` run against a store with no `active` competencies (empty and non-empty-but-all-non-expired cases) → `expired_count: 0`, no error. FR-026. Level: integration.

### 4.3 Authorization / eligibility
- **EC-19.** `POST /competency/assessments` from a citizen with no competency (any status, including `applied`/`rejected`/`expired`/`revoked`) in the target domain → `403` ("no active competency in this domain") — only `status === "active"` passes `hasActiveCompetency()`; a merely-applied or previously-revoked citizen is rejected the same as a citizen with none at all. FR-023. Level: integration.
- **EC-20.** `POST /competency/assessments` from a citizen with `active` competency in domain D but who has a declared conflict of interest in domain D → `403` ("undisclosed conflict of interest") — `hasConflictOfInterest()` treats *any* declared COI in that domain as disqualifying for assessment-writing, not just an "undisclosed" one at the data-model level (the check itself is what makes it effectively "undisclosed" from the platform's perspective: once declared, it's disclosed to the platform and self-excluding). FR-025, DP-021. Level: integration.
- **EC-21.** `POST /competency/assessments` from a citizen with `active` competency in domain A publishing against `domain_id: B` where they hold no competency → `403`, proving domain independence is enforced on the write path too, not just the read path (HP-2). FR-021, FR-023. Level: integration.
- **EC-22.** A citizen declares a COI in a domain, then attempts to publish an assessment in that same domain *after* first also completing the acquisition pipeline there (active competency + COI both true) → still `403`, since `hasConflictOfInterest()` is checked unconditionally after the competency check passes, independent of order of operations. FR-025. Level: integration.
- **EC-43** (ABUSE-REP-1/2, TP-001): `POST /reputation/records` has no caller authentication of any kind — DP-038 says records should only originate from an authorized upstream service after a real event, but the route enforces none of that. `delta` also has no magnitude cap: one unauthenticated call can set an enormous positive delta for any `citizen_id` (self-boosting) or an enormous negative delta against a named rival (defamation), the latter needing only a non-empty (not authentic) `source_ref` to pass the existing negative-polarity check (EC-8). FR-027, DP-038. Level: integration. Proven by `reputation.test.ts`'s `"ABUSE-REP-1/2: unauthenticated, unbounded reputation writes"` suite.

### 4.4 Threshold & boundary conditions
- **EC-23.** A competency's `expires_at` exactly equal to "now" at expiry-sweep time — `sweepExpiredCompetencies()` compares `expiresAt < now()`, so a competency expiring at exactly the sweep instant is **not yet** swept (strict `<`, not `<=`); assert the boundary explicitly since a one-off error here would silently extend or shorten every citizen's validity window by one sweep cycle. FR-026, DP-044. Level: integration.
- **EC-24.** One millisecond after `expires_at` → swept (`status=expired`). One millisecond before → not swept. Pairs with EC-23 to pin the exact boundary. FR-026. Level: integration.
- **EC-25.** `abs(delta)` on a reputation record exactly equal to `SIGNIFICANT_DELTA_THRESHOLD` (10) → notification fires (`>=`, not `>`); `abs(delta) = 9` → does not fire. Already unit-tested in `reputation.test.ts`; restated here because it is the boundary DP-039's downstream notification-service call depends on once that seam is real. FR-027, DP-038. Level: integration.
- **EC-26.** `GET /competency/citizens/:citizenId/domains/:domainId` for a citizen/domain pair with zero competency records at all → `{ active: false }`, not a `404` — absence of a record is a valid "not competent" answer, not an error. FR-021. Level: integration.
- **EC-27.** `GET /reputation/citizens/:id` for a citizen with zero records → `{ total: 0, records: [] }`, not `404` — same "empty is valid" contract as EC-26, and important because a citizen who has never triggered a reputation event must display as neutral (0), not absent. FR-027. Level: integration.

### 4.5 Concurrency & idempotency
- **EC-28.** Two concurrent `POST /competency/applications/:id/advance` calls against the same application at the same stage — both read `status=applied` before either writes; the in-memory `Map`-backed store has no optimistic-lock/version check in `advanceCompetency()`, so a race can double-advance a competency past a stage (e.g. skip straight from `automated_credential_check` to `domain_review`) or double-apply the final `active` transition. Document as `blocked on: no concurrency control exists in the current single-process in-memory store to assert against meaningfully — this scenario documents a real correctness gap rather than a testable guarantee`. FR-022. Level: integration.
- **EC-29.** Two concurrent `POST /competency/challenges/:id/resolve` calls on the same open challenge with different `result` values — the second call's `status !== "upheld" && status !== "dismissed"` guard depends on the first write having landed first; under true concurrency (not just sequential `await`s in a test) this has the same unguarded-race characteristic as EC-28. Same `blocked on:` caveat. FR-024. Level: integration.
- **EC-30.** Re-running `POST /competency/expiry-sweep` twice in immediate succession is safe and idempotent (already asserted at unit level in `expiry.test.ts`; restated at integration level as HP-9 step 4, not duplicated as its own EC).
- **EC-31.** Two `POST /competency/conflicts` calls for the same `citizen_id`/`domain_id` pair both succeed and both create separate `conflict_of_interest` rows (no uniqueness constraint) — `enforcer.exclude()` fires twice with identical arguments. Once a real `ExclusionEnforcer` exists, its target must itself be idempotent to a repeated exclude call; document the expectation now so it isn't missed when that seam is built. FR-025, DP-033. Level: integration, `blocked on: real ExclusionEnforcer target (§1)`.

### 4.6 Cross-service failure & degradation
- **EC-32.** competency-service's `ExclusionEnforcer.exclude()` throws or times out mid-`declareConflict()` (once a real `HttpExclusionEnforcer` exists) — does the COI row still get persisted, or does the whole request roll back? Current code calls `store.conflicts.set()` **before** `enforcer.exclude()`, so the disclosure is durable even if the downstream exclusion call fails; assert this fail-open-on-persistence-but-report-the-downstream-failure behavior once the real seam exists, since a fail-closed COI declaration would let a conflicted citizen claim "I tried to disclose but it errored" as an excuse. FR-025, DP-033. Level: integration, `blocked on: real ExclusionEnforcer implementation (§1)`.
- **EC-33.** reputation-service's `AuditEmitter.emit()` or `NotificationEmitter.notifySignificantDelta()` throws (once real `Http*` implementations exist) — `recordEvent()` calls `store.addRecord()` **before** either emitter, so the reputation record is durable regardless of downstream audit/notification failure; the record must not be lost or rolled back just because audit-service or notification-service is unreachable. FR-027, DP-038. Level: integration, `blocked on: real AuditEmitter/NotificationEmitter implementations`.
- **EC-34.** competency-service has no seam at all to reach reputation-service (§1) — an upheld challenge (HP-7) today produces a locally-consistent revocation with **zero** cross-service side effect, silently diverging from DP-032's spec ("triggers DP-038"). This is the single most important gap this document surfaces: until the seam is added, a citizen whose competency is revoked for cause pays no reputation cost, contradicting FR-027's "penalizing ... undisclosed conflicts" intent for at least the challenge-driven path. `blocked on: seam does not exist (§1)` — flagged here as a finding, not a testable scenario yet.
- **EC-35.** competency-service has no `AuditEmitter` at all (§1) — every state-changing operation in this flow (application, advance, reject, revoke, COI declaration, assessment publish, challenge resolution) currently produces **no** audit trail entry, contradicting DP-036's expectation and this doc's own §4.7 category below being largely unfillable for competency-service until that seam exists. `blocked on: seam does not exist (§1)`.

### 4.7 Data integrity & audit
- **EC-36.** Every `POST /reputation/records` call — success or schema-rejected — is checked against whether `AuditEmitter.emit("reputation.record_created", record)` fires exactly once per successful write and zero times per `400`-rejected write (schema validation runs before `recordEvent()` is ever called). FR-027, DP-038. Level: integration.
- **EC-37.** competency-service currently cannot produce this category's evidence for any operation (applications, challenges, COI, assessments) because it has no `AuditEmitter` (see EC-35). Document as `blocked on: seam does not exist` rather than omitting the category — the absence itself is the finding SRV-005's "Emits to: audit-service (DP-036)" line promises and the code does not yet deliver.
- **EC-38.** The five-stage pipeline (HP-1) leaves no intermediate audit record of *why* each stage passed (e.g. what the "automated credential check" actually verified) — `advanceCompetency()` is a bare stage-pointer increment with no evidence payload captured anywhere in `Competency`. FR-022's "Approval records all evidence and reasoning" acceptance criterion has no field to record it in today. `blocked on: no evidence/reasoning field exists on the Competency type to assert against`.

### 4.8 Advisory-only boundary (competency/reputation never affect voting weight — FR-020, FR-023, FR-027)
This category is specific to this flow doc, alongside ARCH-009 §3's seven shared categories, because EPIC-004's acceptance criteria explicitly single it out ("Competency grants visibility and review authority, never voting power or veto").
- **EC-39.** Neither `competency-service` nor `reputation-service` source exposes any field, endpoint, or outbound call capable of influencing a vote's weight or a proposal's tally — grep-level static verification: no reference to "weight", "tally", "ballot", or "veto" exists anywhere in either service's `src/` tree, and neither service's public API accepts a `proposal_id` for any purpose except `POST /competency/assessments`' purely-informational `content`/`score` fields, which are never read by proposal-service or voting-service (no such inbound call exists in either of those services today). FR-020, FR-023. Level: integration (a source-tree assertion run as part of the integration suite, not a runtime HTTP scenario).
- **EC-40.** `POST /competency/assessments` accepts a `score` of any number (schema only requires `type: "number"`, no range) — even so, nothing reads `score` outside `GET`-style retrieval of the assessment itself; assert that publishing an assessment with an extreme `score` (e.g. `-1e9` or `1e9`) has zero observable effect on a real proposal's `status` fetched from proposal-service before and after. FR-023, ADR-007. Level: e2e (spans competency-service + proposal-service).
- **EC-41.** A citizen with `active` Level-0-through-4 competency in a domain and a citizen with none both retain identical voting eligibility/weight as determined by voting-service — this is voting-service's own invariant (owned by ARCH-016), but this doc records the negative-space requirement on the competency-service side: `hasActiveCompetency()` and `GET /competency/citizens/:citizenId/domains/:domainId` are read-only lookups with no side effect on any other service's state, so nothing here could alter weight even if voting-service asked. FR-020. Level: integration.
- **EC-42.** An upheld challenge (HP-7) revokes competency and (once EC-34's seam exists) posts a negative reputation delta, but does **not** retroactively alter any vote already cast, any proposal outcome already certified, or any assessment already published (assessments remain visible/immutable in `store.assessments`, `revokeCompetency()` never touches `store.assessments`). FR-023, FR-024. Level: integration.

## Status update (2026-08-27)

EC-34's "biggest gap" finding is resolved: competency-service now has a real `ReputationEmitter` seam (`integrations.ts`), wired into both events this doc's ground-truthing pointed at. `declareConflict` (services/conflicts.ts) emits a positive `disclosure` delta; `resolveChallenge` (services/challenges.ts), on an upheld result, emits a negative delta against the competency holder (not the challenger), mapped from the challenge's `reason` (`conflict`→`undisclosed_conflict`, `false_claim`→`misinformation`, `misconduct`→`manipulation`, `credentials`→`fraud`). The real HTTP implementation calls reputation-service's `POST /reputation/records` directly, wired in via `REPUTATION_SERVICE_URL`.

Still open: competency-service still has no `AuditEmitter` seam at all (unlike every other service in this codebase), so DP-036 audit emission from this service remains unimplemented, not just stubbed.

## Status update (2026-09-04)

EC-43 (new — unauthenticated, unbounded reputation writes) is added and proven by two real tests in `services/ts/reputation-service/src/reputation.test.ts`, ground-truthed in TP-001 as ABUSE-REP-1/2: a single call sets a +1,000,000 delta for an arbitrary citizen, and another sets a -1,000,000 delta against a named "rival" using only a non-empty `source_ref`.
