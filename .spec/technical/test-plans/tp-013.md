## Overview

This flow covers the three services EPIC-012 assigns as System Integrity & Anti-Capture's backbone: `audit-service`'s append-only hash-chained log (FR-060, FR-066), `governance-role-service`'s multi-approval coordination and role rotation (FR-061, FR-062, FR-065, FR-067), and `identity-service`'s one-person-one-identity duplicate detection (FR-001, DP-024, DP-056). All three are fully real, independently running services (`audit-service` in Go on port 5003, the other two in TypeScript/Fastify on ports 4009 and 4001) with their own in-memory stores and existing unit suites — this doc does not restate what those suites already cover, only what is visible when the services are driven together, or driven at their real HTTP surface, the way a real caller would.

Ground-truthing the code surfaced this flow's central gap: every cross-service seam that should carry these guarantees end to end is wired to a no-op or always-permissive in-process default in production code today. `identity-service`'s and `governance-role-service`'s `AuditEmitter`s never reach `audit-service`'s real `POST /audit/log`; `governance-role-service`'s `ProtocolGateChecker` never reaches `audit-service`'s real `POST /audit/protocol-changes/gate`; `governance-role-service`'s `COIChecker` never reaches `competency-service`; `identity-service`'s `ApprovalGate` (gating suspend/revoke) never reaches `governance-role-service`'s real approval status; and `governance-role-service`'s `ReplacementRequester`/`NotificationEmitter` never reach `civic-duty-service`/`notification-service`. Per ARCH-009 §2, closing each of these requires new production code (`HttpAuditEmitter`, `HttpProtocolGateChecker`, `HttpCOIChecker`, `HttpApprovalGate`, etc.); scenarios that depend on one are marked `blocked on:` below rather than assumed to work.

A second grounding note: DP-062 (role acceptance handshake), DP-063 (operator appointment), and DP-064 (protocol council election) each describe multi-step business orchestrations — `pending_acceptance`/accept/decline, appointment-proposal → multi-approval → delay → credential issuance, candidacy → election → certification. None of these exist as distinct endpoints in `governance-role-service` today: `POST /governance-roles/roles` is a single generic create-and-immediately-active call with no `status` field and no accept/decline routes. Scenarios below build on the generic role/approval/execution primitives the service actually exposes, and call out where a DP's specific orchestration has no corresponding code (§4.2 EC-20).

## 2. Preconditions & fixtures

Every scenario builds its starting state through each service's own real API, per ARCH-009 §2 — never by writing into any service's in-memory store directly:

1. **Governance role** — `POST /governance-roles/roles` (`citizen_id`, `role_type` ∈ `{auditor,reviewer,oversight,operator,platform_operator,review_body}`, `layer` ∈ `{protocol,implementation,audit,citizen}`, `randomized`, `term_start`/`term_end` ISO-8601, `term_end` after `term_start`) → `201`. Use a distinct `citizen_id` per role to obtain "independent" approvers for §4.3 scenarios.
2. **Fully-approved action** — create three active roles for three distinct citizens, then `POST /governance-roles/approvals` once per role against the same `action_ref`, one of `citizen_supermajority`/`audit_confirmation`/`body_endorsement` each → `GET /governance-roles/actions/:actionRef/status` returns `fully_approved: true`.
3. **Executed action** — from step 2, `POST /governance-roles/actions/:actionRef/execute` with `delay_elapsed: true`, `publicly_visible: true` → `executed: true` (the happy path needs no external dependency since `protocolGateChecker` defaults to always-confirmed).
4. **Rotation sweep clock control** — `POST /governance-roles/rotation/sweep` accepts an optional `now` field (ISO-8601); pass a fixed instant so "within 7 days of `term_end`" scenarios don't depend on wall-clock time.
5. **Audit log entries** — `POST /audit/log` directly (`action_type`, `actor_ref`, `payload`, `idempotency_key`), since no producer service calls it automatically today (§1). This is the only way to get entries into the chain for read/verify scenarios.
6. **Constitutional rights substrate** — `POST /audit/rights` (`name`, `description`, `protected: true`) before `POST /audit/proposals/{id}/constitutional-review`.
7. **Citizen identity** — `POST /identity/citizens` (`public_handle`, `raw_legal_identifier`) → `pending`; `POST /identity/citizens/:id/verifications` (`evidence_ref`, `outcome: "verified"`) → `active`.
8. **Cross-service wiring** — because no live HTTP call connects any two of these three services today (§1), a fixture needing "an audited approval" or "a suspended citizen with a real audit trail" is built by the test client issuing both calls itself (e.g. `POST` the approval to `governance-role-service`, then separately `POST` the equivalent record to `audit-service`'s `/audit/log`) — client-orchestrated, not service-to-service; scenarios are labeled accordingly.

## 3. Happy path scenarios

**HP-1 — Audit log append chains sequentially and verifies.**
1. `POST /audit/log` five times with distinct `action_type`/`payload` values, no `idempotency_key`.
2. `GET /audit/log` → `200`, 5 entries in append order, each entry's `prev_hash` equal to the previous entry's `payload_hash`.
3. `GET /audit/verify` (not `/audit/log/verify` — route corrected) → `200`, `{ valid: true }`.
Cites: FR-060, DP-036. Level: integration.

**HP-2 — Multi-approval unlocks a real action (redesigned as ADR-034's 2-of-2, not the original 3-of-3 + generic execute).**
The `protocol-change-1` + three-approval-types + generic `/execute` design this scenario originally described has no equivalent post-ADR-027 (§4.1 EC-9, §4.3 EC-22). The real, current version of this journey is: `audit_confirmation` + `body_endorsement` approvals from two distinct citizens holding distinct role types (ADR-034 D1) → `GET /governance-role/actions/:actionRef/status` reports `{ fullyApproved: true }` → the one real consumer of that gate, `identity-revocation.service.ts`'s `execute()`, succeeds. Proven end-to-end by `identity-revocation.controller.e2e.spec.ts`'s fully-approved execute test plus `governance-role.controller.e2e.spec.ts::"GET /governance-role/actions/:actionRef/status reflects a real 2-of-2 approval (ADR-034 D1)"`.
Cites: FR-061, FR-065, FR-067, DP-023, DP-035. Level: e2e.

**HP-3 — Re-executing an already-executed action.**
No longer testable as originally worded (no generic execute endpoint, §4.1 EC-9). The real, current equivalent — `identity-revocation`'s `execute()` — is **not** idempotent the way this scenario expected: a second call on an already-`executed` revocation throws `InvalidStateDomainError` (`422`), not a silent `already_executed: true`. Proven by `identity-revocation.service.spec.ts::"rejects executing an already-executed revocation"`.
Cites: FR-061. Level: integration.

**HP-4 — Rotation sweep.**
**No longer testable**: no rotation-sweep endpoint or concept exists anywhere in the current `governance-role` module (§4.4 EC-31, §4.6 EC-45).
Cites: FR-062, DP-050. Level: integration (documents the gap).

**HP-5 — Exact-legal-identity duplicate registration is blocked at the point of registration.**
1. `POST /identity/citizens` with `legalIdentifier: "X"` (field renamed from `raw_legal_identifier`) → `201`.
2. `POST /identity/citizens` again with the same `legalIdentifier: "X"` (different `publicHandle`) → `409`.
Cites: FR-001. Level: integration.

**HP-6 — Duplicate-identity sweep catches a fuzzy signal match the hash check wouldn't.**
1. `POST /identity/citizens` twice with two different `legalIdentifier` values but `publicHandle`s that differ only by case/whitespace (e.g. `"Jane Doe"` / `"jane doe"`) → both `201`.
2. `GET /identity/duplicates/scan` (not a POST — route corrected) → `200`, an array containing the pair (`citizenIdA`/`citizenIdB`/`distance`).
Cites: FR-001, DP-024, DP-056. Level: integration.

**HP-7 — Redundant independent audit bodies read the same log concurrently and consistently.**
1. Append 10 entries via `POST /audit/log`.
2. Issue concurrent `GET /audit/log` reads (simulating independent audit bodies, FR-066) alongside concurrent `POST /audit/log` appends.
3. No lost/duplicated entries; a following `GET /audit/verify` returns `valid: true`.
Cites: FR-066. Level: integration.

- **EC-30.** Approver role's term ends exactly `now` → still active, accepted; a role whose term already ended → rejected. Cites: FR-061. Level: integration.
- **EC-31.** Rotation sweep boundary. **No longer testable**: no rotation-sweep endpoint exists anywhere in the current `governance-role` module (§4.6 EC-45). Cites: FR-062,DP-050. Level: integration (documents the gap).
- **EC-32.** `GET /governance-role/actions/:actionRef/status` for an `actionRef` with zero approvals → `{ fullyApproved: false }` — the response shape changed (no `satisfied_approval_types` breakdown in the current endpoint), but the boundary itself holds. Cites: FR-061. Level: integration.
- **EC-33.** Adapted to ADR-034's 2-of-2 (not the old 3-of-3): once `audit_confirmation` + `body_endorsement` from distinct citizens/role types are recorded (`fullyApproved: true`), a further approval from a third citizen duplicating an already-satisfied type still succeeds (`201`) with no regression. Cites: FR-061. Level: integration.
- **EC-34.** The first entry ever appended to a fresh chain has `prev_hash` equal to the genesis constant; `GET /audit/verify` on a single-entry chain → `valid: true`. Cites: FR-060. Level: integration.

### 4.5 Concurrency & idempotency

- **EC-35.** Two `POST /audit/log` calls with the same `idempotency_key` but different `payload` values → the second call returns the **same** entry as the first (first payload wins); exactly one entry is stored. Cites: FR-060, DP-036. Level: integration.
- **EC-36.** Twenty concurrent `POST /audit/log` calls against the live HTTP server all succeed with no lost or duplicated entries, and `GET /audit/verify` afterward still returns `valid: true`. Cites: FR-060. Level: integration.
- **EC-37.** Two concurrent `POST /governance-role/approvals` calls for the same citizen+`actionRef` — deterministically one succeeds (`201`) and the other is rejected (`409`). Cites: FR-061. Level: integration.
- **EC-38.** Two concurrent execute calls on the same fully-approved `actionRef`. **No longer testable at the governance-role layer** (no execute endpoint there, §4.1 EC-9). `identity-revocation`'s own `execute()` has no equivalent idempotency guard at all — re-executing an already-`executed` revocation throws `InvalidStateDomainError` (`422`) rather than returning `already_executed: true`; two genuinely concurrent calls both past the `status !== "pending"` check before either writes would be a real, undocumented race, but that's a different claim than this EC originally made and is left as a fresh finding rather than force-fit here. Cites: FR-061, FR-065. Level: integration (documents the gap).
- **EC-39.** `linkEntry` and the `store_test.go`/`nats.go` files this scenario cites **do not exist anywhere in the current codebase** (confirmed by repo-wide search) — the premise references code from before the ADR-027 collapse that was never carried over. The current NATS consumer (`consumer.go`'s `StartAuditConsumer`) calls the same `Service.Append` the HTTP handler does, which always computes `prev_hash` from the current tip; there is no out-of-order-buffering code path to test. Moot. Cites: FR-060, DP-036. Level: n/a (premise no longer applies).
- **EC-40.** Every append is server-computed and self-consistent by construction — `GET /audit/verify` on a chain built entirely through `POST /audit/log` always returns `valid: true`. Documented as a **positive integrity property**. Cites: FR-060, ADR-005. Level: integration.

- **EC-42.** COI-checker-down degradation. **No longer testable**: no `coiChecker` concept exists at all (§4.3 EC-22). Cites: FR-063. Level: integration (documents the gap).

- **EC-44.** A live `audit-service` being down, slow, or erroring has zero effect on the caller — `HttpAuditEmitter.emit()` catches every fetch failure (network error or non-2xx) and never throws or blocks the action that triggered it. Cites: FR-060. Level: integration.

Level: integration (documents the gap).

### 4.7 Data integrity & audit

- **EC-46.** `POST /audit/protocol-changes/{id}/release` failing (delay not elapsed, approvals incomplete, or not publicly visible) writes **no** audit-log entry — `ReleaseChange` only appends on the success path. Cites: FR-060, FR-065, DP-043. Level: integration.
- **EC-47.** The `keywordMatchAssessor` this scenario describes **does not exist anywhere in the current codebase** (confirmed by repo-wide search for "keyword"/"change_summary") — `TriggerReview` takes `affected_right_ids` directly from the caller with zero independent content verification of any kind. This is a strictly *larger* gap than the original "evadable by rephrasing" framing: a caller doesn't need to rephrase anything, only decline to declare the right as affected. The `abuse_test.go` file this scenario's traceability row previously cited (`TestAbuseAudit3ConstitutionalReviewEvadedByRephrasing`) **does not exist in this repository** — that citation was stale, carried over from the pre-ADR-027 codebase and never actually reproven here. Re-created against the real endpoint. Cites: FR-060, FR-067. Level: integration.
- **EC-52** (ABUSE-AUDIT-1, TP-001): `POST /audit/log`'s `actor_ref` is a self-declared string with no caller authentication behind it — the hash chain proves entry *sequence* is unbroken, not entry *authorship*. Re-created against the real endpoint. Cites: FR-060, DP-036. Level: integration.
- **EC-48.** Concurrent `GET /audit/log` reads while a writer concurrently appends all observe a consistent, monotonically-growing log with no torn reads; the chain still verifies afterward. Cites: FR-066. Level: integration.
- **EC-49.** **Was a real gap, now fixed here.** `DuplicateDetectionService.scanForDuplicateSignals` previously emitted **zero** audit events (the pre-ADR-034 `scanForDuplicates`/`duplicates_flagged` verb this scenario names doesn't exist in the current Levenshtein-based implementation) — worse than the original "one aggregate event, not per-pair" finding, which at least assumed an event fired at all. Now emits exactly one `identity.duplicate_signals_flagged` event when a scan finds any signals, none when it finds nothing. Cites: FR-001, FR-060, DP-024, DP-056. - **EC-50.** **Finding was understated; corrected here.** `audit-service` has no HMAC at all, generated or persisted — `Signature` (`store.go`/`pgstore.go`) is `"sig:" + sha256(hash + ".audit-service")`, a deterministic hash of a public constant computable by anyone who can compute the entry's `Hash` (itself derived entirely from fields already in the request/response). This is weaker than "an unpersisted key" implies: there is no secret material anywhere in the signing path today. Cites: FR-060, ADR-005. Level: integration.
- **EC-51.** Nothing inside `audit-service` inspects `payload` content — NFR-001's "ballot content is never logged" is caller-discipline only. Cites: FR-060, DP-036. Level: integration.

## Status update (2026-08-27)

**EC-26 is resolved.** `submitApproval` now checks the approver role's `layer` against a fixed `REQUIRED_LAYER_BY_APPROVAL_TYPE` mapping (`citizen_supermajority`→citizen, `audit_confirmation`→audit, `body_endorsement`→protocol) using the `Layer` field ADR-001's four accountability layers already model on `GovernanceRole` — a role outside the required layer is rejected with 403.
