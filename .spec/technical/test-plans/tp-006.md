## Overview

This flow covers evidence-linked structured deliberation with a hard structural separation between agreement and disagreement stances (FR-028, FR-033), preference declaration ahead of any specific proposal (FR-030), constraint-before-solution governance (FR-029, ADR-012), advisory-only AI policy synthesis that never gains write access to governance state (FR-031, ADR-007), and the eight-stage deadlock resolution framework that guarantees no proposal stays blocked forever (FR-034, US-025). `deliberation-service`, `ai-synthesis-service`, `proposal-service`, and `governance-role-service` are all real, fully implemented Fastify servers today; `audit-service` and `voting-service` are real Go `net/http` servers. But every cross-service seam these four TS services declare (`AuditEmitter` and `SynthesisTrigger` in `deliberation-service`; `ConstitutionalReviewer`, `VoteSessionRequester`, `AuditEmitter`, `AssignmentChecker` in `proposal-service`) is currently a local no-op or permissive in-process stub — no `fetch()` call exists between any of these services in the codebase today. This plan therefore depends on new production code that doesn't exist yet: an `HttpSynthesisTrigger` (plus a composition step that reads `deliberation-service`'s live arguments/preferences before calling `ai-synthesis-service`, since `/ai-synthesis/synthesize` takes those arrays inline rather than pulling them itself), an `HttpConstitutionalReviewer` calling `audit-service`'s real `POST /audit/proposals/:id/constitutional-review` (DP-034), an `HttpVoteSessionRequester` calling `voting-service`'s real `POST /voting/sessions`, an `HttpAuditEmitter` for all TS-side audit emission (DP-036), and an `HttpAssignmentChecker` — the last of which is additionally blocked on `governance-role-service` not yet exposing any proposal-scoped "is this reviewer currently assigned" concept (see §1).

FR-032 (multi-option decision framework) and FR-035 (outcome-based governance) are only partially in this flow's lane. FR-032's actual multi-option tally mechanics live in `voting-service` and are TP-008's scope; this doc covers only the `proposal-service`-visible precondition that competing proposals on the same problem share `problem_id` (already covered by that service's own lifecycle, not re-tested here). FR-035's pre-commitment half (objectives, cost, timeline declared before voting) is covered here via the voting-gate budget-completeness check; post-implementation outcome comparison against those promises is `project-service`/TP-009's scope.

## 2. Preconditions & fixtures

- **Proposal fixtures**: `POST /proposals` (`proposal-service`) creates a `draft` proposal. `POST /proposals/:id/constraints` records constraints before any solution debate (FR-029). `PUT /proposals/:id/budget` and `POST /proposals/:id/scope-assignment` (which also sets `support_threshold = ceil(population * 0.05)`) complete the voting-gate fields. `POST /proposals/:id/support` (once per distinct citizen) crosses the support threshold. `POST /proposals/:id/advance`, called repeatedly, walks `draft → gathering_support → development → voting`, exactly as `advanceTo()` does in `proposal-service`'s own unit tests — each gate is enforced server-side, not assumed.
- **Deliberation fixtures**: `POST /deliberation/arguments` and `POST /deliberation/preferences` (`deliberation-service`) use the real `proposal_id`/`problem_id` returned by `proposal-service`'s create response — no reaching into `proposal-service`'s store.
- **AI synthesis fixture**: because `ai-synthesis-service`'s `/synthesize` takes `arguments`/`preferences` inline rather than pulling them by `proposal_id`, a test must first `GET /deliberation/proposals/:id/arguments` and `GET /deliberation/problems/:id/preferences` from `deliberation-service`, then pass those exact response bodies into `POST /ai-synthesis/synthesize`.
- **Deadlock fixture**: advance a proposal to `development` or `voting`, then `POST /proposals/:id/deadlock/enter`.
- **Reviewer-assignment fixture for the deadlock track**: blocked (see §1). Until an `HttpAssignmentChecker` and a proposal-scoped assignment endpoint exist on `governance-role-service`, integration tests exercise the 403/200 branches of `deadlock/advance` by injecting a test-double `AssignmentChecker` at `buildServer()` construction — the same technique `proposal-service`'s own unit tests use (`vi.fn().mockReturnValue(false)`), not a real end-to-end call.
- No fixture reaches into another service's in-memory store directly; every precondition is built through that service's own public API.

## 3. Happy path scenarios

**HP-1: Evidence-linked structured deliberation with agree/disagree separation** (FR-028, FR-033, DP-008) — level: integration (`deliberation-service`)
1. `POST /proposals` (`proposal-service`) → `draft`, note `id`.
2. `POST /deliberation/arguments` with `stance:"agreement"`, a non-empty `evidence_ref`, `proposal_id` from step 1 → 201, `locked:false`.
3. `POST /deliberation/arguments` with `parent_id` = step 2's id, `stance:"agreement"` → 201 (threaded reply on an open branch).
4. `POST /deliberation/arguments` with `stance:"disagreement"`, its own `evidence_ref` → 201.
5. `POST /deliberation/arguments/:id/lock` on step 2's argument → 200, `locked:true` (only agreement-stance arguments can be locked, structurally marking settled facts apart from contested methods).
6. `GET /deliberation/proposals/:proposalId/arguments` → 200, flat list of 3 sorted by `created_at`, the locked entry shows `locked:true`.

End state: three arguments exist, every one carries `evidence_ref`, the agreement branch is locked against re-litigation, the disagreement branch is untouched.

**HP-2: Constraint-based governance precedes solution debate** (FR-029, ADR-012) — level: integration (`proposal-service`)
1. `POST /proposals` → `draft`.
2. `POST /proposals/:id/constraints` while `status=draft` → 201, constraint recorded.
3. `POST /proposals/:id/advance` → `gathering_support`.
4. `POST /proposals/:id/constraints` again while `gathering_support` → 201 (still allowed pre-solution).
5. `GET /proposals/:id` → `constraints` array has 2 public entries.

End state: constraints exist and are publicly visible before the proposal can ever reach `voting`, where solution selection actually happens.

**HP-3: Preference declaration ahead of any specific proposal** (FR-030, DP-009) — level: integration (`deliberation-service`)
1. `POST /deliberation/preferences` with `problem_id`, `citizen_id`, `description` → 201. No proposal need exist yet — preferences attach to `problem_id`, not a proposal.
2. Repeat for a second citizen, same `problem_id`, a different `description`.
3. `GET /deliberation/problems/:problemId/preferences` → 200, 2 entries sorted by `created_at`.

End state: desired-outcome declarations exist against the problem itself, independent of any solution proposal.

**HP-4: AI synthesis stays advisory-only, correctly labeled, and human-reviewable** (FR-031, ADR-007, DP-037) — level: integration (`deliberation-service` ↔ `ai-synthesis-service` boundary)
1. Create a proposal/problem fixture pair.
2. `POST` 3 arguments to `deliberation-service` — mixed stances, real `evidence_ref`s, opposite-stance pair sharing ≥3 lowercase word tokens so a conflict is detectable.
3. `POST` 2 preferences to `deliberation-service` with the same (case/whitespace-normalized) `description`, crossing the shared-objective count of 2.
4. `GET` those arguments and preferences back from `deliberation-service`.
5. `POST /ai-synthesis/synthesize` with those exact arrays → 200; `label` === `"AI-generated analysis — advisory only, subject to human review."`; `model_provenance.model_name` === `"rule-based-synthesis-v1"`; `shared_objectives` has one entry with `count:2`; `conflicts` has ≥1 entry citing both opposite-stance argument ids.
6. `GET /ai-synthesis/outputs/:id` → 200, same labeled output persisted in `ai-synthesis-service`'s own store.
7. Confirm no route in `ai-synthesis-service`'s route table writes to `deliberation-service` or `proposal-service` state — the advisory output lives only in its own store, never back in governance tables.

End state: a labeled advisory analysis exists, was never written back to governance tables, and stays open to a later human flag/review action.

**HP-5: Full eight-stage deadlock resolution, entry through `final_decision`** (FR-034, US-025) — level: integration (`proposal-service`; reviewer assignment exercised via test-double per §2)
1. Build a proposal to `status=voting` via the normal lifecycle (create → constraints → budget → scope-assignment → support → advance ×3).
2. `POST /proposals/:id/deadlock/enter {reason}` → 200, `deadlock.active:true`, `deadlock.stage:"constraint_analysis"`, `history` length 1.
3. `POST /proposals/:id/deadlock/advance {reviewer_id, notes}` seven times → stage moves, in fixed order, `alternative_generation → resource_partitioning → compensation_assessment → citizen_assembly_review → escalation_review → constitutional_review → final_decision`; every call 200, `active` stays `true` throughout.
4. `POST /proposals/:id/deadlock/advance {reviewer_id, notes, outcome:"rejected"}` while `stage="final_decision"` → 200; `deadlock.active:false`, `deadlock.resolved_at` set, `proposal.status` becomes `"rejected"`; `history` length stays 8 (the concluding call appends no new history row — only the 8 stage entries from entry + the 7 stage-advances).
5. `GET /proposals/:id/deadlock` → reflects the final closed state.
6. `GET /proposals/:id` → `status` equals the outcome given in step 4.

End state: the proposal reaches a definitive outcome through the escape hatch; no proposal that enters deadlock is left blocked indefinitely.

**HP-6: End-to-end citizen journey — deliberation and AI synthesis alongside a proposal moving toward voting** (FR-028, FR-029, FR-030, FR-031, DP-008, DP-009, DP-037) — level: e2e (`deliberation-service`, `ai-synthesis-service`, `proposal-service`; the `voting-service`/`audit-service` legs of the final `advance` call are still local no-ops today, see §1)
1. `POST /proposals` → `draft`.
2. `POST /proposals/:id/constraints` (constraint before solution, FR-029).
3. `POST /proposals/:id/advance` → `gathering_support`; `POST /proposals/:id/support` to threshold; `POST /proposals/:id/advance` → `development`.
4. `POST /deliberation/preferences` ×2 against the proposal's `problem_id` (FR-030, DP-009).
5. `POST /deliberation/arguments` ×5 against the `proposal_id`, mixed stances, each with `evidence_ref` (FR-028, DP-008) — the 5th post crosses the default synthesis threshold of 5.
6. `GET` `deliberation-service`'s arguments and preferences for this proposal/problem.
7. `POST /ai-synthesis/synthesize` with those bodies → labeled advisory output (FR-031, DP-037).
8. `PUT /proposals/:id/budget` to completeness; `POST /proposals/:id/scope-assignment`.
9. `POST /proposals/:id/advance` → `voting` (the constitutional-review and vote-session-request seams are still local no-ops today — see §1's "blocked on" notes).

End state: a proposal reaches `voting` having gone through constraint-first deliberation, evidence-linked structured argument, and an advisory (never authoritative) AI synthesis pass.

## 4. Edge cases

### Input validation

- **EC-1**: `POST /deliberation/arguments` missing `evidence_ref` → 400 (FR-028, DP-008) — integration.
- **EC-2**: `POST /deliberation/arguments` with an empty-string `evidence_ref` → 400 (FR-028) — integration.
- **EC-3**: `POST /deliberation/arguments` with a `stance` outside `agreement`/`disagreement` (e.g. `"neutral"`) → 400 (FR-033) — integration.
- **EC-4**: `POST /deliberation/preferences` missing `description` → 400 (FR-030, DP-009) — integration.
- **EC-5**: `POST /ai-synthesis/synthesize` with a malformed body (missing `arguments`/`preferences`) → 400 (FR-031) — integration.
- **EC-6**: `POST /ai-synthesis/synthesize` with an argument `stance` outside `agreement`/`disagreement` → 400 (FR-031) — integration.
- **EC-7**: `POST /proposals/:id/deadlock/advance` missing `reviewer_id` or `notes` → 400 (FR-034) — integration.

### State-machine violations

- **EC-8**: `POST /deliberation/arguments` with `parent_id` referencing a non-existent argument → 404 (FR-028) — integration.
- **EC-9**: `POST /deliberation/arguments` replying anywhere under a locked agreement branch — both a direct child and a deeper descendant reply are rejected → 409 (FR-033) — integration.
- **EC-10**: `POST /deliberation/arguments/:id/lock` on a disagreement-stance argument → 400, only agreement-stance arguments can be locked (FR-033) — integration.
- **EC-11**: `POST /deliberation/arguments/:id/lock` on an unknown id → 404 — integration.
- **EC-12**: `POST /proposals/:id/deadlock/enter` from an ineligible status (`draft`, `gathering_support`, or `approved` — anything outside `development`/`voting`) → 409 (FR-034) — integration.
- **EC-13**: `POST /proposals/:id/deadlock/enter` twice on the same proposal (double-entry) → 409 (FR-034) — integration.
- **EC-14**: `POST /proposals/:id/deadlock/advance` before `deadlock/enter` was ever called → 409 (FR-034) — integration.
- **EC-15**: `POST /proposals/:id/advance` while `deadlock.active=true` → 409; the normal lifecycle is fully blocked while deadlock resolution is active (FR-034) — integration.
- **EC-16**: `POST /proposals/:id/resolve` while `deadlock.active=true` → 409; the normal terminal-outcome path is blocked the same way (FR-034) — integration.
- **EC-17**: `POST /proposals/:id/deadlock/advance` at `stage="final_decision"` without an `outcome` → 400 — the one deadlock-track violation the code reports as a validation error rather than a conflict, since `reviewer_id`/`notes` are present but the required `outcome` to conclude is missing (FR-034) — integration.
- **EC-18**: `POST /proposals/:id/resolve` with `outcome` `approved`/`rejected` from a status other than `voting` → 409, the normal (non-deadlock) resolution gate (FR-035 pre-conditions) — integration.

### Authorization / eligibility

- **EC-19**: `POST /proposals/:id/deadlock/advance` from a `reviewer_id` the `AssignmentChecker` reports as not assigned → 403 (FR-034) — integration, exercised via the injected test-double per §2; **blocked on** a real HTTP-backed assignment source (see §1).
- **EC-20**: `POST /deliberation/arguments/:id/lock` has no actor/role check in current code — any caller can lock any agreement-stance argument today, regardless of citizen identity. This is a coverage gap to assert explicitly (so a future authorization gate is caught by a changed test, not silently missed), not an invented check (FR-033) — integration.

### Threshold & boundary conditions

- **EC-21**: DP-037's `SynthesisTrigger` fires exactly once when the argument/preference count crosses the configurable threshold (default 5), not before, and not again on the very next post — then fires again only once the next threshold multiple is crossed (FR-031, DP-037) — integration, `deliberation-service` only (the trigger call itself, not the full HTTP hop to `ai-synthesis-service`, since `SynthesisTrigger` is still a local seam).
- **EC-22**: The threshold counter is tracked independently per `proposal_id` (arguments) and per `problem_id` (preferences) — crossing the threshold on one proposal does not fire for another (FR-031, DP-037) — integration.
- **EC-23**: `ai-synthesis-service`'s `shared_objectives` requires ≥2 citizens with the same normalized (case/whitespace-insensitive) `description`; a single unique preference produces zero shared objectives (FR-031) — integration.
- **EC-24**: `conflicts` requires ≥3 overlapping lowercase word-tokens between two opposite-stance arguments; two opposite-stance arguments sharing 0–2 tokens produce no conflict entry (FR-031) — integration.
- **EC-25**: `GET` arguments/preferences for a proposal/problem with zero rows returns an empty array (`[]`), not 404 (FR-028, FR-030) — integration.

### Concurrency & idempotency

- **EC-26**: Two `POST /deliberation/arguments/:id/lock` calls on the same argument — the second call is a redundant no-op 200 (still `locked:true`), not an error (FR-033) — integration.
- **EC-27**: `POST /proposals/:id/deadlock/advance` is not idempotent per call — a client that retries an already-succeeded advance call (e.g. after a timeout, without first re-checking the current stage via `GET /proposals/:id/deadlock`) will advance the stage a second time rather than replaying the original result, since no idempotency key exists on the endpoint (FR-034) — integration.
- **EC-28**: `POST /ai-synthesis/outputs/:id/flag` called repeatedly by different citizens accumulates `flag_reasons` rather than overwriting the prior flag (FR-031) — integration.

### Cross-service failure & degradation

- **EC-29**: `ai-synthesis-service` toggled disabled (`POST /ai-synthesis/toggle {enabled:false}`) — `/synthesize` returns 200 `{disabled:true}` and persists nothing; this is the "AI can be turned off by protocol-layer decision without affecting the governance process" guarantee (SRV-016 key rules, FR-031) — integration.
- **EC-30**: `HttpConstitutionalReviewer` / `audit-service` down or slow during a `development → voting` advance — **blocked on**: `HttpConstitutionalReviewer` doesn't exist yet (today's default seam always returns `blocked:false` locally), so this failure-mode scenario cannot be exercised until that real HTTP-calling implementation exists; documented per ARCH-009 §2 rather than assumed to work.
- **EC-31**: `HttpVoteSessionRequester` / `voting-service` down during a `development → voting` advance — same **blocked on** treatment; `voting-service`'s `POST /voting/sessions` is real and reachable but nothing in `proposal-service` calls it yet.
- **EC-32**: `HttpAssignmentChecker` / `governance-role-service` unreachable during `deadlock/advance` — same **blocked on** treatment, compounded by `governance-role-service` having no proposal-scoped assignment concept to call in the first place (see §1).

### Data integrity & audit

- **EC-33**: Every AI synthesis output — including one later flagged as biased — always carries the mandatory label and model provenance; `serializeSynthesisOutput` unconditionally overwrites both fields on every code path, so a caller cannot forge or omit them (ADR-007, FR-031) — integration.
- **EC-34**: `POST /deliberation/arguments` emits `"deliberation.argument.posted"` to `AuditEmitter` (no-op today; `HttpAuditEmitter` is new prerequisite work, DP-036). `POST /deliberation/preferences` emits no equivalent audit event in current code — an asymmetry between DP-008 and DP-009 worth asserting explicitly rather than assuming symmetric audit coverage (DP-008, DP-009, DP-036) — integration.
- **EC-35**: `POST /proposals/:id/deadlock/enter` emits `"proposal.deadlock_entered"`; the concluding `deadlock/advance` call at `final_decision` emits `"proposal.status_changed"` (the same event normal `advance`/`resolve` transitions emit) — but appends no new `deadlock.history` row, only the status-change audit event (FR-034) — integration.
- **EC-36**: The escape hatch's final status transition bypasses `resolveProposal`'s normal gate entirely — a proposal entered into deadlock from `development` (not `voting`) can conclude with `outcome:"approved"` even though the ordinary `POST /proposals/:id/resolve` endpoint only allows `approved`/`rejected` from `status=voting`. This asymmetry is intentional per FR-034 ("no governance process can remain permanently blocked") and must be asserted explicitly as expected behavior, not treated as a bug (FR-034) — integration.
