## Overview

This flow covers two independently real, independently HTTP-driven services: `budget-service` (SRV-007, port 4007) — categories, participatory allocation votes, the public ledger, and reconciliation (DP-013, DP-019, DP-051, DP-055) — and `proposal-service` (SRV-004, port 4004)'s funding-completeness gate that blocks `development` → `voting` until `cost`, `funding_source`, `maintenance_cost`, and `expected_benefits` are all set (FR-037, DP-007). Both services are fully implemented, run real `Fastify` instances, and already carry comprehensive per-service unit coverage (`categories.test.ts`, `allocations.test.ts`, `ledger.test.ts`, `reconcile.test.ts` in budget-service; the `advance()`/`/budget` suites in `proposal-service/src/routes/proposals.test.ts`). This doc does not restate that coverage; it defines what integration/e2e tests must add on top of it.

**Ground-truth finding, load-bearing for this entire doc: no code-level connection exists between the two services.** `srv-007.md` documents budget-service as "Read by: proposal-service (funding gate before voting)", and `TBL-010`'s spec defines a `funding_category_id` FK from `proposal_budget` to `budget_category`. Neither is implemented: `proposal-service`'s `ProposalBudget` type (`src/domain/types.ts`) has only `cost | fundingSource | maintenanceCost | expectedBenefits` — no category link — and `upsertBudget`/`votingGateMissingFields` (`src/services/proposals.ts`) never call out to budget-service. There is not even a no-op stub interface for this dependency in `proposal-service/src/integrations.ts` (unlike `ConstitutionalReviewer`, `VoteSessionRequester`, `AuditEmitter`, `AssignmentChecker`, which are all real seams there today, just unrelated to budget). Relatedly, `TBL-010` also defines a `long_term_cost` column that `ProposalBudget` never implements — FR-040's "maintenance and recurring costs are itemized" collapses to the single `maintenanceCost` field in code.

**New HTTP seam implementations this test plan depends on that don't exist yet:**
- `HttpFundingCategoryValidator` (would live in `proposal-service`, calling budget-service's real `GET /budget/categories/:jurisdictionId/tree`) — additionally blocked on a schema gap: `proposal-service` has no `funding_category_id` field to validate in the first place.
- `HttpProposalBudgetReader` (would live in `budget-service`'s reconciliation service, calling proposal-service's real `GET /proposals`, which already returns the full `budget` object per proposal) — technically buildable today since the source endpoint exists, but useless without the same `funding_category_id` link to know which category a given proposal's cost rolls up into.

Because both seams are blocked on the same root cause, this doc's cross-service scenarios are marked `blocked on:` per ARCH-009 §2's third bullet. Scenarios that are testable today either exercise one named primary service's full real HTTP surface, or (§3 below) drive both services' real APIs from a single test process and assert consistency at the orchestration level — which is the only form of "cross-service" verification possible until the seams above are built.

## 2. Preconditions & fixtures

All fixtures are built through each service's own real API — nothing reaches into `Store` directly (that pattern appears once in `proposal-service`'s own unit suite, deliberately, to isolate an otherwise-unreachable branch; see EC-11 below, and it is exactly the kind of shortcut ARCH-009 §2 rules out for integration/e2e tests).

- **budget-service fixtures**: `POST /budget/categories` (`jurisdiction_id`, `name`, optional `parent_id`) to build a category tree; `POST /budget/allocations` (`citizen_id`, `period`, `allocations[]`) for citizen preference votes; `POST /budget/allocations/aggregate` (`period`, `total_pool`) to close a period; `POST /budget/ledger` (`category_id | null`, `type`, `amount`, `description`, `recorded_by`) for inflow/outflow entries; `POST /budget/reconcile` to run DP-055 on demand (its cron trigger is a scheduling detail, not part of the HTTP contract under test).
- **proposal-service fixtures**: `POST /proposals` → draft; `POST /proposals/:id/advance` → `gathering_support`; `POST /proposals/:id/scope-assignment` (`scope_jurisdiction_id`, `population`) sets `support_threshold = ceil(population * 0.05)`; `POST /proposals/:id/support` (`citizen_id`) per supporter; `POST /proposals/:id/advance` again → `development` once threshold is met; `PUT /proposals/:id/budget` (any subset of the four fields, mergeable incrementally) to populate `proposal_budget`; `POST /proposals/:id/advance` → `voting` once the gate clears.
- Both servers are booted via `buildServer({ store, ...depOverrides })` on ephemeral ports for integration-style tests; overriding `auditEmitter`/`alertEmitter` with a spy is supported by both services' `Deps` and is the only way to assert audit-adjacent side effects, since neither service persists an audit trail of its own.

## 3. Happy path scenarios

**HP-1 — Real-time public ledger reflects inflows and outflows immediately** (FR-036, DP-019). Level: integration [budget-service, single-service scope — see Overview].
1. `POST /budget/categories` → category `C` in jurisdiction `J`.
2. `POST /budget/ledger` inflow, no category (general revenue), amount 50000, `recorded_by: "operator-1"`.
3. `POST /budget/ledger` outflow tied to `C`, amount 12000, `recorded_by: "operator-1"`.
4. `GET /budget/ledger` → both entries present immediately, no separate publish step.
5. `GET /budget/ledger?category_id=C` → only the outflow entry.
Expected end state: ledger entries are publicly queryable the instant they're recorded (FR-036 AC "visible in real time" / "publicly accessible").

**HP-2 — Budget partitioning and participatory allocation aggregation** (FR-038, FR-039, DP-013, DP-051). Level: integration [budget-service].
1. `POST /budget/categories` → build a hierarchical tree in jurisdiction `J`: root "Public Services" with children "Healthcare" and "Education".
2. `GET /budget/categories/J/tree` → nested hierarchy returned correctly (FR-039 "budgets are divided into defined categories").
3. Citizens A, B, C each `POST /budget/allocations` for period `2026-Q3`, percentages summing to exactly 100 across Healthcare/Education.
4. `POST /budget/allocations/aggregate` `{period, total_pool}` → weighted-average percentage per category, `allocatedAmount` written to `budget_category`.
5. `GET /budget/categories/J/tree` → `allocatedAmount` now reflects the aggregation (FR-038 AC "allocation results are public").
Expected end state: `allocatedAmount = total_pool * averagePercentage / 100` per category, computed only within each category (no cross-category competition, FR-039).

**HP-3 — Ledger reconciliation confirms allocated vs. spent within tolerance** (FR-036, DP-055). Level: integration [budget-service].
1. Build on HP-2's aggregated category (`allocatedAmount` known).
2. `POST /budget/ledger` outflow(s) against that category summing to exactly `allocatedAmount`.
3. `POST /budget/reconcile` → `discrepancy: 0` for that category, `alertEmitter.emit` not called.
Expected end state: reconciliation confirms spend matches the participatory allocation exactly.

**HP-4 — Proposal funding-completeness gate: full citizen journey from draft to voting** (FR-037, FR-040, DP-007). Level: integration [proposal-service].
1. `POST /proposals` → `draft`.
2. `POST /advance` → `gathering_support`.
3. `POST /scope-assignment` (sets `support_threshold`).
4. `POST /support` from enough citizens to meet the threshold.
5. `POST /advance` → `development`.
6. `PUT /budget` with `{cost, funding_source}`, then a second `PUT /budget` with `{maintenance_cost, expected_benefits}` — confirms partial `PUT`s merge incrementally rather than overwrite (ground truth: "merges partial updates incrementally").
7. `POST /advance` → `voting`; response body's `budget` object shows all four fields (FR-037 AC "cost, funding source, maintenance cost, expected benefits are shown"); `VoteSessionRequester.requestSession` invoked exactly once.
Expected end state: the proposal cannot reach `voting` until every field is non-null, and once it does, all four are visible together with the policy itself (FR-037 AC "citizens vote on both policy and spending together").

**HP-5 — Cross-service consistency: a proposal's declared cost is independently reconcilable against the jurisdiction's ledger** (FR-036, FR-037, FR-040; conceptual cross-service — no direct RPC exists, see Overview). Level: e2e [drives both services' real HTTP surfaces from one test process; consistency is asserted by the test orchestrator, not by either service calling the other].
1. `budget-service`: `POST /budget/categories` → category "Roads" in jurisdiction `J1`.
2. `proposal-service`: build a proposal through `development` (HP-4 steps 1–5), then `PUT /budget` `{cost: 12000, funding_source: "Roads capital fund", maintenance_cost: 500, expected_benefits: "..."}`, then `POST /advance` → `voting`.
3. `budget-service`: `POST /budget/ledger` outflow of 12000 tied to "Roads", `description` referencing the proposal by title/id (the only correlation available, since no `proposal_id`/`funding_category_id` FK exists anywhere in either service — see Overview).
4. Test asserts `GET /budget/ledger?category_id=Roads` total equals `GET /proposals/:id`'s `budget.cost`.
Expected end state: the two independently-owned numbers agree — but only because the test performed the correlation a human auditor (or the not-yet-built `HttpProposalBudgetReader` seam) would have to perform manually today.

## 4. Edge cases

### Input validation
- **EC-1**: `POST /budget/categories` missing `jurisdiction_id` or `name` → 400. FR-039. Level: integration[budget-service].
- **EC-2**: `POST /budget/allocations` with percentages summing to ≠100 (e.g. 80) → 400, error message contains the actual sum ("80"). FR-038. Level: integration[budget-service].
- **EC-3**: `POST /budget/allocations` referencing a nonexistent `category_id` → 400. FR-038/FR-039.
- **EC-4**: `POST /budget/allocations` with a duplicate `category_id` within one submission → 400 `"duplicate category_id X in allocation set"`. FR-038.
- **EC-5**: `POST /budget/ledger` with `category_id` referencing a nonexistent category → 400. FR-036.
- **EC-6**: `POST /budget/ledger` with `type` outside `{inflow, outflow}` → 400 (schema enum). FR-036.
- **EC-39** (ABUSE-FIN-2, TP-001): `POST /budget/ledger`'s `amount` has no minimum/sign constraint in the request schema, and the service layer never derives or checks a sign from `type` either — a negative `amount` is accepted on both `inflow` and `outflow`, corrupting the public ledger and any reconciliation built on top of it (a negative outflow nets as money appearing rather than leaving, and vice versa). `recorded_by` is also never verified as belonging to an authorized operator, so this is reachable by any caller with no privilege. FR-036. Level: integration. Proven by `ledger.test.ts`'s two `ABUSE-FIN-2` cases (negative outflow, negative inflow).
- **EC-7**: `PUT /proposals/:id/budget` with `cost` or `maintenance_cost` negative → 400 (schema `minimum: 0`). FR-037/FR-040.
- **EC-8**: `PUT /proposals/:id/budget` with `funding_source` or `expected_benefits` as an empty string → 400 (schema `minLength: 1`). FR-037.
- **EC-9**: `PUT /proposals/:id/budget` with an unrecognized field (e.g. `funding_category_id`, which the schema has never defined) → 400 (`additionalProperties: false`) — directly confirms the Overview's schema-gap finding: there is no way to set a category link even if a client tries. FR-037.
- **EC-10**: `PUT /proposals/:id/budget` on a nonexistent proposal id → 404. FR-037.

### State-machine violations
- **EC-11**: `development`→`voting` attempted with every budget field set but `scope_jurisdiction_id` unset → 409 listing only `scope_jurisdiction_id`. **Ground-truth caveat**: through the real HTTP sequence this is unreachable, because `gathering_support`→`development` requires `support_threshold` to be set, which only happens via `POST /scope-assignment` — so by the time a proposal is in `development`, scope is always already set. The proposal-service unit suite only reaches this branch by mutating the in-memory store directly, which ARCH-009 §2 explicitly forbids for integration/e2e fixtures. **This scenario cannot be reproduced as a real integration/e2e test without a new way to unset scope via the API — flagging as dead code from any real client's perspective**, worth raising with the proposal-service owner rather than testing. FR-037/FR-008.
- **EC-12**: `development`→`voting` attempted with each single-field, and each pairwise, partial completion of `{cost, funding_source, maintenance_cost, expected_benefits}` → 409 in every case, error listing exactly the still-missing field names and excluding every field actually set. FR-037 (explicitly required: "each partial-completion edge case"). Concretely: missing `cost` only; missing `funding_source` only; missing `maintenance_cost` only; missing `expected_benefits` only; missing all four; missing exactly two (e.g. `cost` + `expected_benefits`).
- **EC-13**: `development`→`voting` blocked while a scope challenge is pending (`scopeChallengePending`). FR-037/DP-020.
- **EC-14**: `development`→`voting` blocked when `ConstitutionalReviewer.review()` returns `{blocked: true}` even though budget/scope/challenge gates all clear — an orthogonal seam (owned by the constitutional-layer test plan, TP-012), included here only because it sits on the same `advance()` path as the budget gate and must not be conflated with a budget-gate failure in error messages.
- **EC-15**: `gathering_support`→`development` attempted below the support threshold → 409, `support_count` unchanged — precondition for ever reaching the budget gate. FR-017.
- **EC-16**: `/advance` called again once already at `voting` → 409 `"no automatic advance is defined from status voting"`.

### Authorization / eligibility
- **EC-17**: `PUT /proposals/:id/budget` succeeds for **any** caller — `upsertBudget` performs no author/role check at all, so a citizen who is not the proposal's `authorId` can set its funding fields. Expected result documents current behavior (200), not invented behavior; flagged as a gap against FR-037's implicit intent. FR-037.
- **EC-18**: `POST /budget/ledger` accepts any `recorded_by` string with no verification the caller is a real operator — DP-019's actor is "operator" but the code enforces nothing. FR-036.
- **EC-19**: `POST /budget/allocations` accepts any `citizen_id` with no eligibility/active-citizen check — DP-013's actor is "citizen (active)" but the code enforces nothing. FR-038.

### Threshold & boundary conditions
- **EC-20**: allocation percentage sum exactly at the `SUM_TOLERANCE` boundary (`1e-9`) — a sum of `100 + 1e-9` passes (`Math.abs(sum-100) > SUM_TOLERANCE` is false at equality), a sum of `100 + 1e-8` fails. FR-038.
- **EC-21**: `POST /budget/allocations` with exactly one allocation entry (schema `minItems: 1` boundary, minimum valid set) → 201.
- **EC-22**: `POST /budget/allocations` with an empty `allocations` array → 400 (schema `minItems: 1`).
- **EC-23**: `POST /budget/reconcile` with zero categories and zero ledger entries in the store → `[]`, no alert. FR-036.
- **EC-24**: a category with `allocatedAmount: 0` and `spent: 0` → `discrepancy: 0`, no alert — the zero/zero boundary, distinct from the already-unit-tested zero-vs-nonzero mix. FR-036.
- **EC-25**: `support_count === support_threshold` exactly → `/advance` succeeds (`<` is the failure condition, so equality passes); `support_count === support_threshold - 1` → 409. FR-017.
- **EC-26**: `PUT /budget` with `cost: 0` exactly → counts as *present*, not missing, since `votingGateMissingFields` checks `=== null`, not truthiness — a proposal can legitimately reach `voting` declaring a literal $0 cost. Worth a dedicated regression test since `!== null` vs. falsy is an easy bug to introduce later. FR-037.
- **EC-27**: same as EC-26 for `maintenance_cost: 0`.

### Concurrency & idempotency
- **EC-28**: two `PUT /proposals/:id/budget` requests with disjoint field sets, dispatched concurrently — since Node/Fastify serialize handler execution and `upsertBudget` mutates synchronously with no `await` before the write, no interleaving is possible; both partial updates apply regardless of arrival order, converging to the same final state as sequential calls. FR-037.
- **EC-29**: two concurrent `POST /proposals/:id/support` requests from the same `citizen_id` — exactly one returns 201 (`support_count` +1), the other 409 `"already supported"`; `support_count` never double-increments. FR-017 (adjacent precondition to the budget gate).
- **EC-30**: two concurrent `POST /budget/allocations` submissions for the same `citizen_id`+`period` — delete-then-insert is synchronous, so the final state holds exactly the last-processed submission's votes, never a union of both. FR-038.
- **EC-31**: `POST /budget/allocations/aggregate` called twice in a row for the same period (DP-051 is cron-triggered, so re-runs are plausible) — `aggregateAllocations` doesn't delete/consume votes, so both calls recompute from the same underlying data and produce identical results (idempotent by construction). FR-038.
- **EC-32**: `POST /budget/reconcile` called twice in a row (DP-055 is a daily cron) — the read+report itself is idempotent (no store mutation), but `alertEmitter.emit` has no de-duplication guard, so a genuine discrepancy fires the alert a second time on the second call. Flagging this as a real replay/idempotency gap per §3's own description ("replay of an already-processed request"). FR-036.

### Cross-service failure & degradation
- **EC-33**: `blocked on: HttpFundingCategoryValidator` (does not exist). If `proposal-service` validated `funding_source`/a category link against `budget-service` before allowing `development`→`voting`, a `budget-service` outage or slow response would need a documented fail-open/fail-closed policy. Today the gate is unaffected by `budget-service`'s availability — but only because it performs no such check at all. FR-037.
- **EC-34**: `blocked on: HttpProposalBudgetReader` (does not exist) + the `funding_category_id` schema gap (Overview). If DP-055 reconciliation were extended to cross-check proposal-level cost claims, a `proposal-service` outage during the daily reconciliation cron would need a documented degrade path (e.g. skip the cross-check, still complete the category-vs-ledger reconciliation). Undefined today since no such call exists. FR-036/FR-040.

### Data integrity & audit
- **EC-35**: every `advance()` status transition (`draft`→`gathering_support`→`development`→`voting`) invokes `AuditEmitter.emit("proposal.status_changed", {proposalId, from, to})` with correct arguments — verifiable via an injected spy `AuditEmitter` (the code's `Deps` supports overriding it), but since the default is a no-op and no real `audit-service` exists, only the call itself is assertable, not a persisted record. FR-037 (transition into `voting` specifically).
- **EC-36**: `ledger_entry` immutability — no `PUT`/`DELETE` route is registered for `/budget/ledger/:id` (404/405) — reinforces FR-036/DP-019's append-only, no-corrections-without-a-new-entry rule as a structural regression check, not just a unit nicety. FR-036.
- **EC-37**: `budget_category.allocatedAmount` can only ever be written by `POST /budget/allocations/aggregate` — the category-creation schema doesn't accept an `allocated_amount` field at all, so allocation results cannot be forged or set directly, only produced by the participatory process (FR-038's integrity guarantee).
- **EC-38**: `ReconciliationResult`s are never persisted by `budget-service` — each `POST /budget/reconcile` response is the only record of a given run. If `AlertEmitter` stays the default no-op (as it is unless explicitly overridden), a surfaced discrepancy is lost the instant the HTTP response is sent, with no durable trail anywhere in this service — worth flagging against SRV-007's own "alerts for the audit pool" claim. FR-036.
