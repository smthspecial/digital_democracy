## Overview

This flow covers assigning an impact scope to a proposal, deriving citizen eligibility from verified residency and jurisdiction membership, and challenging/escalating a scope assignment before a proposal is allowed into voting. Both `jurisdiction-service` (SRV-002, port 4002 default) and `proposal-service` (SRV-004, port 4004 default) are fully implemented, real Fastify HTTP services with their own in-memory stores and their own unit suites — this doc does not restate what those suites already cover, only the behavior visible when the two are driven together as a real client would.

Ground-truthing the code surfaced the central gap this test plan exists to expose: **no HTTP call from `proposal-service` to `jurisdiction-service` exists today.** `POST /proposals/:id/scope-assignment` accepts `scope_jurisdiction_id` and `population` as trusted client input — it never checks the jurisdiction exists, and `jurisdiction-service` has no `population` field to source that number from at all. `jurisdiction-service`'s `GET /jurisdiction/eligibility` endpoint has zero callers anywhere in this codebase (`voting-service` takes `eligible_citizen_ids` as client-supplied input rather than deriving it). Per ARCH-009 §2, closing this gap requires new production code — a `JurisdictionClient`-shaped HTTP seam in `proposal-service` (and, out of this doc's primary scope but relevant as corroborating evidence, an eligibility-calling seam in `voting-service`, tracked under ARCH-016) — that does not exist yet. Scenarios that depend on it are marked `blocked on:` below rather than assumed to work.

A second grounding note: FR-014/ADR-004/TBL-003 describe a **six**-level scope model (`property`, `street`, `municipality`, `regional`, `national`, `constitutional`), but `jurisdiction-service`'s actual `SCOPE_LEVELS` enum implements only **four** (`neighborhood`, `city`, `region`, `national`). Scenarios below use the four levels the running code actually accepts; the two-level gap is called out as a finding, not silently worked around.

## 2. Preconditions & fixtures

Every scenario builds its starting state through each service's own real API, per ARCH-009 §2 — never by writing into either service's in-memory store directly:

1. **Jurisdiction tree** — `POST /jurisdiction/jurisdictions` once per level, each with the previous level's `id` as `parent_id`, e.g. `national` → `region` → `city` → `neighborhood`, each with a distinct `boundary_ref` string (jurisdiction-service never dereferences it — see EC-6.3).
2. **Residency** — `POST /jurisdiction/residencies` with `citizen_id`, `jurisdiction_id`, and a `start_date` far enough in the past to clear whatever `min_residency_days` a scenario needs (default 30 if unspecified).
3. **Membership** — `POST /jurisdiction/memberships` with `citizen_id` + `jurisdiction_id`, one call per jurisdiction level the citizen belongs to (FR-013 permits several simultaneously).
4. **Proposal** — `POST /proposals` (problem_id, title, description, author_id) to get a `draft` proposal, then drive it through `POST /proposals/:id/support`, `PUT /proposals/:id/budget`, and `POST /proposals/:id/advance` calls to reach whichever status a scenario needs — the same sequence `proposal-service`'s own `advanceTo()` test helper uses. `POST /proposals/:id/scope-assignment` is one of the fixture-building calls, not solely a scenario under test, since nothing else in the API sets `scope_jurisdiction_id`.
5. **Cross-service wiring** — because no live HTTP call connects the two services (§0), a fixture that needs "a proposal scoped to a real jurisdiction" is built by the test client: call `jurisdiction-service` to create/read the jurisdiction, then pass its `id` into `proposal-service`'s `scope-assignment` call. This is client-orchestrated, not service-to-service, and scenarios are labeled accordingly in §5.

## 3. Happy path scenarios

**HP-1 — Smallest-competent-jurisdiction scope assignment with population-scaled threshold.**
1. Jurisdiction-service: build `national → region → city` tree (§2.1).
2. Proposal-service: create a proposal, advance to `gathering_support`.
3. Proposal-service: `POST /proposals/:id/scope-assignment` with the `city` jurisdiction's `id` (smallest competent level for a municipal-scope problem) and `population: 1000`.
4. Expect `200`, `scope_jurisdiction_id` = city id, `support_threshold` = `ceil(1000 * 0.05)` = `50`.
Cites: FR-008, FR-014, DP-030. Level: integration (client-orchestrated).

**HP-2 — Assigned scope is publicly visible on the proposal.**
1. Continue from HP-1's proposal.
2. `GET /proposals/:id` (unauthenticated, as any citizen would read it).
3. Expect `200` with `scope_jurisdiction_id` and `support_threshold` both present and matching HP-1.
Cites: FR-009. Level: integration. Note: the response carries no separate "rationale" or eligibility-explanation text — FR-009's AC that "eligibility criteria for the proposal are explained to citizens" is not implemented by either service; this scenario asserts only what the real response actually contains.

**HP-3 — Verified residency + membership yields eligibility.**
1. Jurisdiction-service: create a jurisdiction, a membership, and a residency for one citizen with `start_date` 60 days in the past.
2. `GET /jurisdiction/eligibility?citizen_id=...&scope_jurisdiction_id=...` (default `min_residency_days=30`).
3. Expect `200`, `{ eligible: true, reasons: [] }`.
Cites: FR-012. Level: integration (single-service; included because it is the fixture every downstream eligibility scenario depends on).

**HP-4 — Multi-jurisdiction simultaneous membership, evaluated per proposal.**
1. Jurisdiction-service: build `national → region → city`. Create memberships and residencies for one citizen at both `city` and `national` (FR-013 — simultaneous nested memberships).
2. Proposal-service: create Proposal A scoped to `city`, Proposal B scoped to `national`.
3. `GET /jurisdiction/eligibility` once against `city`, once against `national`.
4. Expect both calls return `eligible: true` independently — eligibility is per-jurisdiction, not a single global flag.
Cites: FR-013, FR-014. Level: integration (client-orchestrated).

**HP-5 — Support threshold gates gathering_support → development, end to end.**
1. Proposal-service: create a proposal, advance to `gathering_support`.
2. `scope-assignment` with `population: 20` → `support_threshold: 1` (`ceil(20*0.05)`).
3. `POST /proposals/:id/support` once.
4. `POST /proposals/:id/advance` → `200`, status `development`.
Cites: FR-008, DP-030 (support_threshold rule owned by SRV-004, cited here since it is what scope assignment feeds). Level: e2e (full support-gated lifecycle segment).

**HP-6 — Scope challenge blocks, then unblocks, the voting gate.**
1. Advance a proposal to `development` with budget complete and scope assigned (HP-1-style).
2. `POST /proposals/:id/scope-challenges` with a citizen id and reason → `201`, `scope_challenge_pending: true`.
3. `POST /proposals/:id/advance` → `409` (blocked by pending challenge).
4. `POST /proposals/:id/scope-challenges/:challengeId/resolve` → `200`, `scope_challenge_pending: false`.
5. `POST /proposals/:id/advance` → `200`, status `voting`.
Cites: FR-008, FR-010, FR-011, DP-020, DP-030. Level: e2e (full challenge-to-voting-readiness journey).

## 4. Edge cases

### 4.1 Input validation

- **EC-1.** `POST /jurisdiction/jurisdictions` with `scope_level` outside the four implemented values (e.g. `"planet"`, or one of the spec's missing `"property"`/`"constitutional"` levels) → `400`. Cites: FR-014. Level: integration.
- **EC-2.** `POST /jurisdiction/jurisdictions` with an unknown `parent_id` → `400` "parent jurisdiction not found". Cites: FR-014. Level: integration.
- **EC-3.** `POST /jurisdiction/residencies` with `end_date` before `start_date`, or an unparsable date string, or an unknown `jurisdiction_id` → `400` in each case. Cites: FR-012. Level: integration.
- **EC-4.** `POST /proposals/:id/scope-assignment` with `population` negative or missing → `400` (schema: `minimum: 0`, required). Cites: FR-008. Level: integration.
- **EC-5.** `POST /proposals/:id/scope-assignment` with a `scope_jurisdiction_id` that does not exist in `jurisdiction-service` (or is an arbitrary string) → currently `200`, silently accepted. **Gap, not a passing scenario**: `assignScope()` has no cross-service existence check. `blocked on: JurisdictionClient seam in proposal-service does not exist.` Cites: FR-008, FR-014. Level: integration (documents current, arguably-wrong behavior; becomes a real negative-test candidate once the seam exists).
- **EC-6.** `POST /jurisdiction/eligibility` with an unknown `scope_jurisdiction_id` → `400` "jurisdiction not found" (thrown by `checkEligibility` before candidate traversal). Cites: FR-012. Level: integration.

### 4.2 State-machine violations

- **EC-7.** `POST /proposals/:id/scope-assignment` succeeds (`200`) regardless of the proposal's current status — it can be re-run against a proposal already in `voting`, `approved`, or `archived`. Nothing in `assignScope()` gates on status. Cites: FR-008 (whose intent — "recorded before the voting phase opens" — implies assignment is a one-time, pre-voting act this doesn't enforce). Level: integration.
- **EC-8.** `POST /proposals/:id/scope-challenges` succeeds regardless of proposal status — a challenge can be filed against a `draft`, `voting`, `approved`, or `archived` proposal; `fileScopeChallenge()` has no status check. Only the `development → voting` `advance()` gate actually reads `scope_challenge_pending`, so a challenge filed post-voting has no blocking effect. Cites: FR-010. Level: integration.
- **EC-9.** `POST /proposals/:id/scope-challenges/:challengeId/resolve` on an already-resolved challenge → `409` "already resolved". Cites: FR-010. Level: integration.
- **EC-10.** `POST /proposals/:id/scope-challenges/:challengeId/resolve` with an unknown `challengeId` → `404`. Cites: FR-010. Level: integration.
- **EC-11.** Two scope challenges are filed on the same proposal (both `201`, both unresolved); resolving only the first sets `scope_challenge_pending: false` for the whole proposal even though the second challenge's own `resolved` field is still `false`. This is a deliberate simplification documented in `domain/types.ts` ("a single flag over all challenges... a resolved challenge clears progression for the proposal as a whole"), not a bug, but it means `development → voting` can proceed while an unresolved challenge still exists in `scope_challenges`. Cites: FR-010, FR-011. Level: integration.
- **EC-12.** `gathering_support → development` attempted below `support_threshold` → `409` citing current count and threshold; proposal stays `gathering_support`. Cites: FR-008/SRV-004 support-threshold rule. Level: integration.
- **EC-13.** `development → voting` attempted with `scope_jurisdiction_id` unset → `409`, error lists `scope_jurisdiction_id` and omits budget fields when only scope is missing (and vice versa when only budget is missing). Cites: FR-008. Level: integration.

### 4.3 Authorization / eligibility

- **EC-14.** `GET /jurisdiction/eligibility` when the citizen has membership but no *current* residency (e.g. residency `end_date` in the past) → `eligible: false`, reason `"no current residency in a member jurisdiction"`. Cites: FR-012. Level: integration.
- **EC-15.** `GET /jurisdiction/eligibility` when residency duration is below `min_residency_days` → `eligible: false`, reason `"residency duration below minimum required days"`. Cites: FR-012. Level: integration.
- **EC-16.** `GET /jurisdiction/eligibility` when membership is in one branch of the tree and residency is in an unrelated branch (not the scope jurisdiction or any of its ancestors/descendants) → `eligible: false`. Cites: FR-012, FR-013, FR-014. Level: integration.
- **EC-17.** `GET /jurisdiction/eligibility` when membership + residency are held at a *descendant* of the scope jurisdiction (e.g. neighborhood-level residency satisfying a city-level scope check) → `eligible: true` — confirms the smallest-competent-jurisdiction interpretation extends eligibility upward through the tree, not just at the exact scope node. Cites: FR-013, FR-014. Level: integration.
- **EC-18.** `POST /proposals/:id/scope-challenges/:challengeId/resolve` performs no actor/role check whatsoever — any caller can resolve any proposal's challenge with no verification that the caller is (or represents) an "independent review body" separate from the proposal's authors. **Gap**: FR-011 requires disputes be "resolved by bodies independent of the proposal's authors," but the endpoint has no authorization model at all. `blocked on: no governance-role-service integration for review-body identity/authorization exists in this codebase.` Level: integration.
- **EC-19.** `POST /proposals/:id/scope-challenges` accepts any `citizen_id` string with no check that the citizen is real, active, or eligible in the proposal's scope jurisdiction — DP-020's trigger actor is "citizen (active)" but nothing enforces that. Cites: FR-010. Level: integration.

### 4.4 Threshold & boundary conditions

- **EC-20.** `population: 0` on scope-assignment → `support_threshold: 0` (`ceil(0*0.05)`), so `gathering_support → development` succeeds immediately with zero support gathered — a zero-population jurisdiction never actually gates. Cites: FR-008/SRV-004 threshold rule. Level: integration.
- **EC-21.** `population: 19` → `support_threshold: 1`; `population: 1000` → `50`; `population: 1001` → `51` (ceil rounding confirmed at both an exact multiple and one over it). Cites: FR-008. Level: integration.
- **EC-22.** Support count exactly at threshold (`supportCount == threshold`) advances; one under (`threshold - 1`) is rejected with `409`. Cites: FR-008. Level: integration.
- **EC-23.** Scope is re-assigned (EC-7) after support has already been gathered under the prior threshold — the new `support_threshold` can land above or below the already-collected `support_count`, and nothing recomputes or re-validates prior support against the new number. Cites: FR-008, FR-014. Level: integration.
- **EC-24.** `GET /jurisdiction/jurisdictions/:id/tree` on a leaf jurisdiction (no children created) returns `children: []`, not an error — empty-collection boundary. Cites: FR-014. Level: integration.

### 4.5 Concurrency & idempotency

- **EC-25.** Two `POST /jurisdiction/memberships` calls with the same `citizen_id`+`jurisdiction_id` → second call `409`. Cites: FR-013. Level: integration.
- **EC-26.** Two `POST /proposals/:id/support` calls from the same `citizen_id` → second call `409`, `support_count` unchanged. Cites: FR-008/SRV-004. Level: integration.
- **EC-27.** Two concurrent `POST .../scope-challenges/:id/resolve` calls racing on the same challenge — one succeeds (`200`), the other observes it already resolved (`409`); no double-clear side effects. Cites: FR-010. Level: integration.
- **EC-28.** Two concurrent `scope-assignment` calls against the same proposal with different `population` values — `store.save`/in-memory object mutation has no version/optimistic-lock field, so the result is last-write-wins with no conflict signaled to either caller. Cites: FR-008. Level: integration. Gap, not enforced today.
- **EC-29.** Two concurrent `POST .../scope-level` calls on the same jurisdiction (both pre-approved) — same last-write-wins outcome, `store.jurisdictions.update` unconditionally overwrites. Cites: FR-014. Level: integration.

### 4.6 Cross-service failure & degradation

- **EC-30.** `proposal-service`'s `scope-assignment` endpoint should validate `scope_jurisdiction_id` against `jurisdiction-service` and behave predictably (fail closed) when `jurisdiction-service` is down or slow. `blocked on: JurisdictionClient HTTP seam does not exist in proposal-service` — there is no call to fail against. Cites: FR-008, FR-014. Level: integration (once unblocked).
- **EC-31.** A scope-level change (`POST /jurisdiction/jurisdictions/:id/scope-level`) should be gated by governance-role-service's real approval decision; today `ApprovalGate` is purely in-process (`defaultApprovalGate = () => true`), so there is no downstream call whose failure/timeout could be exercised. `blocked on: no governance-role-service HTTP surface exists anywhere in this codebase.` Cites: FR-014 (DP-035). Level: integration (once unblocked).
- **EC-32.** `voting-service` should derive `eligible_citizen_ids` at session-open by calling `jurisdiction-service`'s eligibility endpoint per citizen and degrade predictably if that call fails; today it takes the list as direct caller input. `blocked on: eligibility-calling seam does not exist in voting-service` (belongs to ARCH-016, noted here as the other side of the same gap this doc opens with). Cites: FR-012. Level: e2e (once unblocked).
- **EC-33.** DP-030's "review body" routing/confirmation step for scope assignment and scope-challenge resolution doesn't exist as a service call at all — `assignScope`/`resolveScopeChallenge` apply caller input directly with no routing hop to fail against. `blocked on: DP-030 routing target service does not exist.` Cites: FR-011, DP-030. Level: integration (once unblocked).
- **EC-34.** DP-058's daily cron — escalating scope disputes that have exceeded their SLA without resolution — has no implementation anywhere in `proposal-service`: `ScopeChallenge` carries no SLA/deadline field (only `createdAt`, `resolved`, `resolvedAt`), and no scheduled job exists in the service's source. A challenge filed and never resolved leaves `scope_challenge_pending: true` indefinitely with nothing to escalate it, which is exactly the "remains indefinitely blocked" outcome DP-058 exists to prevent. `blocked on: DP-058 cron and an SLA field/config do not exist in proposal-service.` Cites: FR-010, FR-011, DP-058. Level: integration (once unblocked).

### 4.7 Data integrity & audit

- **EC-35.** `POST /jurisdiction/jurisdictions` and `POST /jurisdiction/jurisdictions/:id/scope-level` each invoke `AuditEmitter` with `jurisdiction.created` / `jurisdiction.scope_level_changed` and the jurisdiction id — confirmed by `jurisdiction-service`'s own unit test; worth a cross-service assertion once a real audit sink exists, since the production wiring today is `noopAuditEmitter`. Cites: FR-014 (SRV-002 "emits to audit-service on any structural change" rule). Level: integration.
- **EC-36.** `POST /jurisdiction/residencies` and `POST /jurisdiction/memberships` — both **structural changes** per SRV-002's stated rule — call no `AuditEmitter` at all; neither service function accepts one. **Gap**: residency and membership creation produce no audit trail, contradicting SRV-002's "emits to audit-service on any structural change." Level: integration.
- **EC-37.** `assignScope()`, `fileScopeChallenge()`, and `resolveScopeChallenge()` in `proposal-service` call no `AuditEmitter` at all, unlike `createProposal`/`advance`/`resolveProposal`/`enterDeadlock`, which do. **Gap**: scope assignment and scope-challenge filing/resolution — the exact actions FR-010/FR-011 require to be publicly trackable with a recorded outcome and rationale — leave no audit trace today, even a no-op-logged one. Cites: FR-010, FR-011. Level: integration.
- **EC-38.** `POST /jurisdiction/jurisdictions` accepts any `boundary_ref` string with no existence or reachability check — `jurisdiction-service` stores a pointer, never the boundary itself (SRV-002, ADR-004). If the referenced boundary is later found not to exist or not to resolve, nothing in this codebase detects or flags it; there is no boundary-resolution call anywhere. This is consistent with the documented design ("never stored as mutable data") but means a dangling `boundary_ref` is structurally invisible — no scenario here can assert detection because nothing attempts it. Cites: FR-014 (ADR-004 boundary-immutability rule). Level: integration — documents an intentional non-scenario (there is nothing to test against because the design deliberately never dereferences the pointer).
