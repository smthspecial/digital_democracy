## Overview

This flow covers an approved proposal becoming a publicly tracked `project`, milestone reporting against it, real-time citizen visibility into timeline/budget/contractor, and the outcome-evaluation cycle that compares promised vs. measured results (FR-045 through FR-048, EPIC-008). `project-service` (SRV-013) is fully real: every endpoint in the table below exists and is unit-tested. `budget-service` (SRV-007) and `reputation-service` (SRV-014) are also real, independently callable services, but **no HTTP seam connects them to project-service today, and — unlike every other cross-service relationship in this codebase — project-service does not even define a no-op stub for reaching budget-service or reputation-service.** Its only seams (`integrations.ts`) are `AuditEmitter` and `AssignmentRequester`, both no-op by default. Concretely: `POST /:id/budget-spent` is a manual, independent write with no call to budget-service's real public ledger (`GET/POST /budget/ledger`), and no code path anywhere calls reputation-service's `POST /reputation/records` when an outcome evaluation is submitted, even though SRV-014 lists project-service as an upstream trigger for DP-038. Likewise, **proposal-service has no seam at all — not even a stub — for turning an approved proposal into a project**; `POST /proposals/:id/resolve` with `outcome: "approved"` only flips the proposal's own status field. This test plan therefore documents happy paths and edge cases against what is implemented, and calls out each missing seam as `blocked on:` per ARCH-009 §2, so the prerequisite production code is visible before any test can be written against it.

## 2. Preconditions & fixtures

All fixtures are built through each service's own public API — no reaching into another service's store directly, per ARCH-009 §2.

1. **Get a proposal to `approved`** entirely through proposal-service's real lifecycle: `POST /proposals` → `POST /proposals/:id/constraints` / budget fields via the update endpoint → `POST /proposals/:id/scope` → accumulate `POST /proposals/:id/support` to the computed threshold → `POST /proposals/:id/advance` through `gathering_support` → `development` → `voting` → `POST /proposals/:id/resolve {outcome:"approved"}`. `GET /proposals/:id` after resolution exposes `budget.cost`, `budget.expected_benefits`, `title`, `description` — the fields this flow's fixtures read to seed a project.
2. **Because no seam creates the project automatically**, the fixture then calls project-service directly: `POST /` with `proposal_id` = the approved proposal's id, `contractor` (test-supplied — the operator's implementation choice, not derived from proposal data, per FR-045), `budget_allocated` = the approved proposal's `budget.cost`, `promised_outcome` = the approved proposal's `budget.expected_benefits` (or `description`), and a `milestones[]` array (also operator-authored). This step is manual orchestration standing in for the missing seam from §1 — it does not exist as an automatic consequence of `/resolve` in the current codebase, and this test plan cannot assert that it does.
3. Where a scenario needs budget-service state (e.g. to demonstrate the disconnect between project-service's `budget_spent` and budget-service's public ledger), fixtures create `budget_category` and `ledger_entry` rows independently through budget-service's own endpoints — there is no cross-service call that does this for a project automatically.
4. Where a scenario needs reputation-service state, fixtures call `POST /reputation/records` directly on reputation-service, standing in for the DP-038 trigger that project-service does not yet emit.
5. To reach a `completed` project deterministically, complete every milestone returned at creation via `POST /:id/milestones/:milestoneId/complete` in any order; the project flips to `completed` automatically once no milestone remains `pending` (no separate "mark project complete" call exists).
6. To reach evaluation-eligibility, call `POST /outcome-evaluations/sweep` with an explicit `now` far enough past `completed_at` (default delay is `DEFAULT_EVALUATION_DELAY_DAYS = 180`, overridable via `evaluation_delay_days` in the request body) rather than relying on wall-clock time.

## 3. Happy path scenarios

**HP-1 — Approved proposal becomes a tracked public project (decision/execution separation)**
1. proposal-service: drive a proposal to `approved` (§2 step 1).
2. project-service: `POST /` seeded from the approved proposal (§2 step 2) — `contractor`, `milestones[]` ordering, and implementation details are operator-supplied, never citizen-voted, per FR-045.
3. Assert: `201`, response `status: "active"`, `budget_spent: 0`, milestones returned `status: "pending"` in `order_index` order, and an `outcome_evaluation` sub-object with `promised_outcome` set and `measured_outcome: null`.
Level: integration (proposal-service + project-service, manual hand-off per §2).

**HP-2 — Milestone reporting updates the visible timeline and the project stays active until the last one**
1. project-service: complete the first of two milestones via `POST /:id/milestones/:milestoneId/complete` (DP-018).
2. Assert: `200`, `milestone.status: "done"`, `project.status` still `"active"`; `GET /:id/milestones` reflects the one `done` / one `pending` split in real time (FR-047).
Level: integration.

**HP-3 — Completing the final milestone flips the project to completed and emits an audit event**
1. project-service: complete the remaining milestone.
2. Assert: `200`, `project.status: "completed"`; a follow-up `GET /:id` independently confirms `status: "completed"` and a non-null `completed_at`; the injected `AuditEmitter` recorded a `project.completed` event (DP-018's "public update" requirement, verifiable only via the injected fake today — see EC-D1).
Level: integration.

**HP-4 — Budget spend is recorded and visible in real time**
1. project-service: `POST /:id/budget-spent {amount, description}` twice.
2. Assert: `200` each time, `budget_spent` accumulates additively (`2500` then `3500`), and `GET /:id` reflects the running total without any additional step (FR-047's "cost changes... in real time").
Level: integration.

**HP-5 — Outcome-evaluation sweep requests an audit-pool assignment once the delay has passed**
1. project-service: complete all milestones on a project (→ `completed`).
2. `POST /outcome-evaluations/sweep {now: <completed_at + 200 days>, evaluation_delay_days: 180}` (DP-053).
3. Assert: `requested_project_ids` includes the project id, and the injected `AssignmentRequester` was called exactly once with that id — standing in for civic-duty-service's real `audit_review` assignment creation, which is not wired yet (§1).
Level: integration (project-service only, against a fake `AssignmentRequester` — true e2e is `blocked on:` the missing HTTP seam).

**HP-6 — Outcome evaluation is submitted and published**
1. project-service: `POST /outcome-evaluations/:id/submit {measured_outcome}` (DP-022) against the evaluation created alongside the project in HP-1.
2. Assert: `200`, `measured_outcome` set, `evaluated_at` non-null, and the result is readable via the same evaluation object returned from project creation — no additional auth is required to read it (FR-048's "public" requirement).
Level: integration.

**HP-7 — Full journey: approval through milestone completion to outcome evaluation**
1. Chain HP-1 → HP-2 → HP-3 → HP-5 → HP-6 end to end across proposal-service and project-service (with a fake `AssignmentRequester`/`AuditEmitter` standing in for the two unimplemented downstream services).
2. Assert final state: proposal `approved`, project `completed` with full `budget_spent` history, all milestones `done`, evaluation carries both `promised_outcome` and `measured_outcome`.
Level: e2e (proposal-service → project-service chain; the civic-duty-service, budget-service, and reputation-service legs of the same journey are `blocked on:` the missing seams noted in §1 and cannot be exercised end-to-end today).

## 4. Edge cases

### Input validation
- **EC-1**: `POST /` missing any required field (`proposal_id`, `contractor`, `budget_allocated`, `promised_outcome`, `milestones`) → `400` (schema `required` + `additionalProperties: false`). FR-046. Level: integration.
- **EC-2**: `POST /` with `budget_allocated` negative → `400` (schema `minimum: 0`); `budget_allocated: 0` is accepted (boundary — see EC-9). FR-046. Level: integration.
- **EC-3**: `POST /:id/budget-spent` with `amount: 0` or negative → `400` (schema `exclusiveMinimum: 0`, confirmed by existing unit test). FR-046. Level: integration.
- **EC-4**: `POST /outcome-evaluations/:id/submit` with empty `measured_outcome` → `400` (`minLength: 1`). FR-048. Level: integration.
- **EC-5**: Milestone `due_date` accepts any non-empty string — the schema has no date-format validation, so a garbage value (e.g. `"not-a-date"`) is accepted and stored verbatim; nothing downstream (sweep, milestone ordering) currently parses it as a date, so this passes silently rather than surfacing as a data-quality problem. FR-046. Level: integration.
- **EC-6**: `POST /` with an unexpected extra body field → `400` (`additionalProperties: false` on both the top-level body and each milestone object). FR-046. Level: integration.

### State-machine violations
- **EC-7**: Complete a milestone on an unknown `project_id` → `404` (`getProject` throws before the milestone is even looked up). DP-018. Level: integration.
- **EC-8**: Complete a milestone id that exists but belongs to a different project → `404` ("milestone not found on project"). DP-018. Level: integration.
- **EC-9**: Complete an already-`done` milestone → `409` (confirmed by existing unit test). DP-018. Level: integration.
- **EC-10**: `POST /:id/budget-spent` against a project already `completed` — the code applies **no status guard**: `recordBudgetSpent` unconditionally increments `budget_spent` regardless of `project.status`. A test should assert this actual (surprising) behavior — spend can still post-date completion — and flag it as a gap against the implied "project lifecycle" model. FR-046. Level: integration.
- **EC-11**: `POST /outcome-evaluations/:id/submit` against a project that is still `active` (not `completed`) — `submitOutcomeEvaluation` checks only whether the evaluation was already submitted, never the parent project's `status`. A measured outcome can be recorded before the project is actually finished. DP-022, FR-048. Level: integration.
- **EC-12**: Submit the same outcome evaluation twice → `409` (confirmed by existing unit test). DP-022. Level: integration.
- **EC-13**: There is no endpoint to add, remove, or reorder milestones after project creation — the milestone set is fixed at `POST /` time. A scenario that expects the implementer to add a milestone mid-project (a realistic real-world need) has no API to exercise; this is a functional gap against FR-046's "milestone reporting," not just an untested path. Level: integration (documents the gap; no automatable positive case exists).

### Authorization / eligibility
- **EC-14**: No endpoint in project-service performs any actor/role check today — `POST /`, `POST /:id/milestones/:milestoneId/complete`, `POST /:id/budget-spent`, and `POST /outcome-evaluations/:id/submit` all execute for any caller. This contradicts DP-018 (`actor: "operator or oversight role"`) and DP-022 (`actor: "auditor or oversight role (active term)"`). `blocked on:` authorization middleware/role enforcement in project-service — until it exists, these are gap-documentation scenarios, not currently-failing tests to write. FR-045, DP-018, DP-022. Level: integration.
- **EC-15**: Unlike proposal-service's `AssignmentChecker` (which gates deadlock-review actions to the assigned reviewer), project-service has no equivalent seam to verify that whoever calls `POST /outcome-evaluations/:id/submit` is the citizen actually assigned the `audit_review` civic duty for that project. `blocked on:` an `AssignmentChecker`-style seam plus the civic-duty-service integration from §1. FR-048, DP-022. Level: integration.

### Threshold & boundary conditions
- **EC-16** (ABUSE-FIN-3, TP-001): `budget_allocated: 0` at creation, then any positive `budget-spent` entry — no overspend guard exists anywhere (`recordBudgetSpent` never compares `budgetSpent` to `budgetAllocated`), so `budget_spent` can exceed `budget_allocated` arbitrarily with no error, no flag, and no audit event. This is the clearest concrete gap against FR-046's "budget consumption is tracked against the approved budget." Level: integration. Proven directly (spend 50x the allocation with zero rejection) by `projects.test.ts::"ABUSE-FIN-3: records spend far beyond budget_allocated with no ceiling check"`.
- **EC-17**: `milestones: []` (empty array) at creation is accepted by the schema (no `minItems`). Such a project can **never** reach `completed` — the only path to `status: "completed"` is `completeMilestone`'s "no incomplete siblings" check, and with zero milestones there is nothing to complete and no other endpoint sets project status. This is a dead-end state: the outcome-evaluation sweep (DP-053) can never fire for it either, since it requires `status === "completed"`. FR-046, DP-053. Level: integration.
- **EC-18**: `POST /outcome-evaluations/sweep` exactly at the delay boundary (`now - completed_at === delayMs`) — the guard is `< delayMs` (strict), so a project is **included**, not skipped, at exactly the threshold; only one-under is excluded. DP-053. Level: integration.
- **EC-19**: `evaluation_delay_days: 0` — schema allows it (`minimum: 0`); a project becomes evaluation-eligible immediately upon completion. DP-053. Level: integration.
- **EC-20**: Duplicate `order_index` values across milestones in one `POST /` — the schema doesn't enforce uniqueness; the sort is stable but two milestones can carry the same index, making "published order" ambiguous. FR-046. Level: integration.

### Concurrency & idempotency
- **EC-21**: Two `POST /:id/milestones/:milestoneId/complete` calls against the same milestone — the second is rejected `409` regardless of ordering (single in-memory store, request-scoped check), giving idempotent-by-rejection behavior rather than idempotent-by-no-op. DP-018. Level: integration.
- **EC-22**: Two concurrent `POST /outcome-evaluations/sweep` calls after the same project becomes eligible — `evaluationRequestedAt` is set inside the loop before the response returns, so a second sweep run correctly excludes the project (confirmed by existing unit test: "does not call the assignment requester a second time"). DP-053. Level: integration.
- **EC-23**: `POST /:id/budget-spent` has no idempotency key in its schema (`amount`, `description` only). A client that retries after a timeout (e.g. proxy/network failure between citizen-facing client and project-service) will double-record the spend with no way for the server to detect the retry was a duplicate. FR-046. Level: integration.

### Cross-service failure & degradation
- **EC-24**: An approved proposal never becomes a project because the seam described in §1 doesn't exist — `blocked on:` a `ProjectCreator` seam in proposal-service (or an orchestrating caller) with a defined fail-open/fail-closed behavior for when project-service is unreachable. EPIC-008, FR-045, FR-046. Level: e2e (documents the gap).
- **EC-25**: `project-service`'s `sweepOutcomeEvaluations` has **no per-project error isolation** — `assignmentRequester.request(project.id)` is called synchronously inside a `for...of` loop with no `try/catch`; once a real HTTP-calling implementation exists, a single downstream failure (civic-duty-service down/erroring for project A) would throw uncaught and abort processing for every other eligible project in the same sweep run, not just A. This should be fixed before civic-duty-service integration ships, and this test plan flags it now so the fix is visible before the HTTP seam is written. DP-053. Level: integration (`blocked on:` the HTTP seam; documented against current in-memory code today).
- **EC-26**: `budget-service` unreachable while recording project spend — moot today, since no seam calls budget-service from project-service at all (§1); `blocked on:` the `BudgetLedgerReader`/reconciler seam plus a documented fail-open-vs-fail-closed policy once it exists. FR-046, FR-047. Level: integration (documents the gap).
- **EC-27**: `reputation-service` unreachable while submitting an outcome evaluation — moot today for the same reason; `blocked on:` the `ReputationNotifier` seam. Once built, note that reputation-service's `POST /reputation/records` itself rejects a `positive`-polarity `factor_type` (`successful_proposal` is the only outcome-shaped one) unless `delta > 0`, and rejects any negative-polarity submission without a non-empty `source_ref` — so a "the project fell short of its promise" evaluation has **no positive factor to report honestly**, and none of reputation-service's four negative factor types (`misinformation`, `undisclosed_conflict`, `manipulation`, `fraud`) represent an honest, non-fraudulent shortfall. The seam cannot be built as a straightforward pass-through; it needs either a new factor type or a documented decision that only clearly successful/fraudulent outcomes generate a reputation signal. DP-038, FR-048. Level: integration (documents the gap; blocks writing EC-27 as a runnable test until resolved).

### Data integrity & audit
- **EC-28**: `completeMilestone`'s `AuditEmitter.emit()` and `resolveProposal`'s status-change emissions are both no-op by default; SRV-013's "All updates are public and emitted to the audit log" (DP-018) is unverifiable against a real audit trail today — only the injected fake emitter in a test can confirm the call happened, not that anything durable/hash-chained was produced. `blocked on:` a real `HttpAuditEmitter` and audit-service (TP-013 territory). FR-046. Level: integration.
- **EC-29**: TBL-031 (spec) defines `objective` and an `evaluation` enum (`successful | partial | unsuccessful`); the implemented `OutcomeEvaluation` type has neither field — only free-text `promisedOutcome`/`measuredOutcome`. A "measured outcome fell short of the promise" scenario is accepted and published **identically** to a fully successful one; there is no automated success/failure/partial classification anywhere in the code for this test plan to assert against. FR-048 ("Results are compared against the promised objectives") is satisfied only insofar as both texts are published side by side for a human reader — the comparison itself is not a system behavior. Level: integration (documents the gap rather than asserting a classification that doesn't exist).
- **EC-30**: TBL-029 (spec) defines `timeline_start`/`timeline_end` and `planned | in_progress | cancelled` project statuses; the implemented `Project` type only has `createdAt`/`completedAt` and `active | completed`. FR-046's "published timeline" has no explicit start/end date fields to assert on — the only real timeline signals available via the API are `created_at`, each milestone's `due_date`, and `completed_at`. Level: integration.
- **EC-31**: TBL-028 (spec) defines a nullable `project_id` on `ledger_entry`, implying budget-service's public ledger can be filtered/joined per project; the actual `LedgerEntry` type and `POST /budget/ledger` schema carry no `project_id` field at all. There are therefore two disconnected "money spent" pictures in the running system — project-service's manually-POSTed `budget_spent` counter, and budget-service's real public ledger — with no field, seam, or reconciliation process linking them, despite SRV-013 asserting DP-055 performs that reconciliation. This is the most significant data-integrity gap surfaced by this flow. FR-046, FR-047. Level: integration.
- **EC-32**: A project can silently "stall" (an incomplete milestone whose `due_date` has long passed) with no distinguishable system state — `MilestoneStatus` only models `pending`/`done` (TBL-030's spec'd `delayed` status is unused in code, per an explicit comment in `domain/types.ts`), and no cron or read-path logic compares `due_date` to the current date anywhere in project-service. `GET /:id` and `GET /:id/milestones` report the same `"pending"`/`"active"` regardless of how overdue the milestone is; citizens can only infer staleness by comparing `due_date` to today client-side — the system itself never flags it, contradicting DP-018's "Delays surface as audit events for the oversight pool." FR-047. Level: integration.

## Status update (2026-08-27)

Two of this doc's findings are resolved:

1. **The budget↔project reconciliation gap is closed, in the direction that's actually implemented.** budget-service's `LedgerEntry` now has `projectId` (TBL-028), and `POST /budget/ledger` accepts/filters on `project_id`. project-service's `recordBudgetSpent` still increments `project.budget_spent` locally (the fast path this service's own reads depend on) but now also pushes a project-tagged outflow into budget-service's ledger via a new `LedgerRecorder` seam, wired to the real endpoint via `BUDGET_SERVICE_URL`. This is a direct push at write time, not SRV-013's originally-stated DP-055 cron-reconciliation-pull (which stays scoped to `budget_category.allocated_amount`) -- SRV-013's key rule was corrected to describe this simpler, actually-implemented flow instead. EC-28/EC-30/EC-31 (project↔budget consistency scenarios) can now be written against a real cross-service link instead of two disconnected records.
2. **FR-048's outcome comparison is no longer uncomputed.** `OutcomeEvaluation` gained `objective` (TBL-031) and `evaluation` (`successful`/`partial`/`unsuccessful`), submitted explicitly by the auditor/oversight actor at evaluation time (DP-022's actor), not derived from text. A `successful` evaluation now triggers DP-038: project-service resolves the proposal's author via a new `ProposalAuthorLookup` seam (a real read against proposal-service, since project-service only stores `proposal_id`) and credits their reputation via `ReputationEmitter`. EC-29 can now be written for real.

Both new seams (`ProposalAuthorLookup`, `ReputationEmitter`) plus `LedgerRecorder` have real HTTP-calling implementations wired in by `index.ts`, falling back to no-ops when unconfigured.
