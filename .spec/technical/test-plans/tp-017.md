## Scope and entry criteria

Qualify the exact production candidate defined by REL-002. Run static review
first, followed by bounded active tests on the designated synthetic staging
cluster. TASK-006 supplies target, owners and load/recovery scope; the protocol
ADR and real implementation, mesh/TLS, backups and release Jobs must exist
before claiming their corresponding checks passed.

Use fresh synthetic citizens/elections and independent test trustees. Keep
separate issuer/redemption/tally access and exercise the real cryptographic
implementation, public gateway, both runtimes, trusted verifiers, Postgres and
NATS. Test doubles may support unit tests but cannot satisfy release evidence.
Production observations use only separately agreed safe checks; active attacks,
load drills and synthetic secret/key manipulation stay in isolated staging.

## Phase 1 — static review and artifact checks

1. Trace FR-003/004, NFR-001/003, AUTH-012 and current two-runtime boundaries to
   protocol, client, verifier, tally, policy, database and broker implementation.
2. Review the cryptographic design/assumptions, anonymous credential scheme,
   trustee independence, metadata/receipt risks, proof and tally verification.
3. Review all runtime manifests/identities/allow-lists, certificate issuers,
   hostname/CA validation, secret custody and restricted DB roles.
4. Review migration order, signing-format compatibility, old audit provenance,
   replay/spend durability, backups, restore/rollback and operational runbooks.
5. Scan source dependencies, Go and exact container images; verify lockfile patch
   hashes, non-root execution, secret exclusions and exception expiry/ownership.
6. Run complete lint/typecheck/build, Go vet and required application/browser/
   broker/database tests. Record counts, actual execution and skipped tiers.

A blocking static finding is ticketed and fixed before the affected active
scenario. Preserve evidence for both the failure and its retest.

## Phase 2 — staging matrix

| Area | Positive control | Negative/failure controls | Passing evidence |
|---|---|---|---|
| Eligibility/privacy | Eligible citizen obtains and anonymously spends one real credential | Ineligible/duplicate issuance, forged/stolen/wrong-election credential, concurrent double spend, issuer/caster metadata joins | Real protocol and DB results; independent linkage analysis |
| Client/proof | Required-method ciphertext and proof accepted | Bad encoding/proof, modified election/options, absent verifier, fixture bypass, plaintext choice | Genuine encrypted HTTP/client flow; failures closed |

| Inclusion/receipt-freeness | Voter verifies inclusion; public verifier reproduces tally | Artifact substitution/omission, transferable receipt attempts, client/operator coercion and metadata attacks | Independent reviewer conclusions against NFR-001/NFR-003 |
| Citizen authorization | Valid T2/T3 sessions and physical/browser passkeys exercise required operations | Invalid/missing sessions, weak tier, citizen-header forgery, ownership/revocation bypass | Real gateway/auth/router and database results |
| Workload identity | Expected accounts and producer claims communicate | Plaintext/unmeshed/wrong-account caller, forged producer, valid workload calling forbidden path | Live denial and authenticated control traffic |
| Gateway/TLS | Owned-domain HTTPS, verified DB/broker TLS, certificate renewal | Wrong host/CA, expired cert, plaintext fallback, public internal-write access | Connection/renewal tests with exact cert/policy versions |

## Evidence and exit criteria

Create `testing/production-readiness/` during execution with commands, UTC times,
synthetic fixture labels, image digests, schema versions, policy/config hashes,
public election manifests/proofs, scanner versions/database timestamps and
sanitized results. Record each case's expected/observed outcome and the exact
positive control. Exclude voter identity/choice associations, credentials,
private trustee shares and private keys.

Every blocking finding gets a ticket, correction and retest. Preserve raw
version-based advisory notices alongside exact patch mitigation evidence;
scanner errors or stale exception approvals fail the relevant gate. Provide
independent crypto review and operator/trustee sign-off evidence where required
by the accepted design. Keep tests and reviewers independent of self-reported
application success.

TASK-020 completes only when the matrix and intended-scope soak/load/recovery
criteria pass. TASK-021 then rehearses and authorizes the target-specific
promotion with abort checkpoints and operational handover. Missing protocol,
receipt-freeness, live workload/TLS, safe migrations or trusted audit-history
verification remains a release blocker.
