## Scope and boundaries

Assess the current working tree, including existing uncommitted passkey work.
Read requirements, backlog and technical documents first; historical TP-001
findings must be revalidated against the current two-app implementation.
Test only locally started disposable services, never a deployed environment.
Use synthetic citizens and bounded payloads; no load/flood testing or real data.
This is an assessment, not an authorization redesign or production certification.

## Phase 1 — static assessment

1. Inventory routes, trust boundaries, frontend clients and deployment exposure.
2. Review session issuance, passkeys, refresh, cookies, verifier/service signatures,
   revocation and active-identity checks against ADR-040 and AUTH-010.
3. Review citizen ownership, assurance, governance roles, system-only mutations,
   voting integrity, delegation and audit authorship.
4. Review input handling, SQL/command/HTML injection surfaces, secret handling,
   resource limits, database privilege boundaries and infrastructure controls.
5. Run available dependency advisories, Go vet and relevant automated suites.
   Record scanner/version/network limitations instead of assuming a clean result.

## Phase 2 — local penetration tests

After static review, start isolated local services with disposable storage.

- Anonymous and forged-token access to privileged voting operations; token
  issuance for arbitrary citizens; casting, replay and option mutation.
- Forged audit authorship and protocol approvals; verify chain behavior.
- Delegation impersonation and revocation using publicly readable citizen IDs.
- Legacy login/MFA bypass, unsigned internal provisioning/revocation, invalid
  passkey assertions, malformed authorization and session privacy.
- TS route authorization and assurance checks using the real runtime where
  dependencies permit; test harness results must be labeled as such.
- Bounded oversized input, untrusted headers and observable hardening controls.

## Evidence and delivery

Keep a reproducible local runner, machine-readable sanitized results and a report
under `testing/security/`. For each finding record severity, source references,
request/response evidence, impact, spec traceability and a minimal remediation.
Distinguish confirmed runtime exploits, static findings, defended controls and
untested deployment assumptions. Preserve pre-existing edits. Shut down services
started for this assessment. Re-run confirmed exploit cases after remediation.

## Remediation verification — 2026-10-08

BUG-005 through BUG-014 cover all assessment observations. Repeat confirmed
attacks with `testing/security/regression.py` against the fixed disposable
runtimes; retain the original probe/report as historical evidence.

Run the complete Go/TS suites with required database/browser/broker tiers,
dependency patch regressions and scans, lint/typecheck/build, rendered Helm and
real broker restrictions, fresh database CONNECT isolation, and container builds
and loopback smoke checks. Use a fresh synthetic audit chain between suites
that use ephemeral keys and the runner with its stable fixture key; do not
re-sign old untrusted rows. Evidence and production prerequisites are recorded
in `testing/security/remediation-validation.json` and `REMEDIATION.md`.
