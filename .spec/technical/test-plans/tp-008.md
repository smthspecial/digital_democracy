## Overview

This flow covers a vote session's full life: `proposal-service` requesting a session as a proposal advances `development`→`voting`, `voting-service` scheduling it, opening it (cooling-off clearance + batch eligibility-token issuance), accepting encrypted ballots, closing it, tallying it under all four supported methods, and certifying (or failing to certify) the result. `voting-service` (Go, SRV-008) is the only service in this flow with a real, complete HTTP surface today — every endpoint named below exists and is exercised by its own unit/router tests. `proposal-service` (TS) is real but its `VoteSessionRequester` seam toward voting-service is still the no-op default (`defaultVoteSessionRequester`); no `HttpVoteSessionRequester` exists yet, so the proposal→voting-service trigger in this doc is the one genuine "two real services over HTTP" integration scenario, and it is currently blocked on that seam implementation being written. `delegation-service` and `audit-service` do not exist as running services at all — voting-service's `DelegationResolver` and `AuditEmitter` interfaces (`service.go`) have only no-op defaults, so DP-041 and DP-036 scenarios are documented but marked `blocked on:` per ARCH-009 §2. `jurisdiction-service` is not called by the real code at all: `POST /voting/sessions/{id}/open` takes eligibility as a caller-supplied `eligible_citizen_ids` list rather than computing it, so FR-041's "eligibility is computed from the proposal's impact scope" and "eligibility decisions are explainable to citizens" acceptance criteria have no implementation surface to test against here. Likewise, FR-043 (complete voting package: problem, solution, budget, expert analysis, alternatives) has no corresponding endpoint anywhere in voting-service or proposal-service today, so it is linked for traceability but not covered by any scenario below. DP-046/DP-047/DP-057 are specified as cron sweeps, but are implemented as directly-callable, synchronous admin transitions (`POST .../open`, `POST .../close`); this doc's fixtures invoke them as such rather than waiting for a scheduler that does not exist in this codebase.

## 1. Services & seams in scope

| Service | Role in this flow | Real HTTP call today or seam-stub today |
|---|---|---|
| voting-service (SRV-008, Go) | Owns `vote_session`, `vote_option`, `eligibility_token`, `ballot`; implements DP-016, DP-017, DP-025, DP-026, DP-027, DP-046, DP-047, DP-057 | Real — full surface implemented: `POST /voting/sessions`, `POST /voting/sessions/{id}/options`, `GET /voting/sessions/{id}`, `POST /voting/sessions/{id}/open`, `POST /voting/sessions/{id}/close`, `POST /voting/ballots`, `GET /voting/ballots/verify` |
| proposal-service (TS) | Advances a proposal `development`→`voting`; on success calls the `VoteSessionRequester` seam | Seam-stub — `defaultVoteSessionRequester.requestSession()` (`src/integrations.ts`) is a fire-and-forget no-op; no `HttpVoteSessionRequester` implementation exists to actually POST `/voting/sessions` |
| delegation-service (SRV-010) | Target of DP-041 delegation-chain resolution, invoked when a ballot is cast under an active delegation | Seam-stub, unreachable — voting-service's `DelegationResolver` interface (`service.go`) has only `noopDelegationResolver`; delegation-service does not exist as a callable process in this codebase |
| audit-service (SRV-012) | Target of DP-036 emission on session certification | Seam-stub, unreachable — voting-service's `AuditEmitter` interface has only `noopAuditEmitter`; audit-service does not exist as a callable process |
| jurisdiction-service | Nominally supplies eligibility population per SRV-008's spec `Dependencies` list | Not called at all by the real code — `POST /voting/sessions/{id}/open` accepts `eligible_citizen_ids` directly in the request body; there is no jurisdiction lookup in `service.go` or `store.go` |

Given that voting-service's real external dependencies (delegation-service, audit-service, jurisdiction-service) are all unreachable stubs, every scenario that stays entirely within voting-service's own HTTP surface is classified `e2e` below — it is the full citizen-facing journey through every boundary that is actually crossable today, per ARCH-009 §1's note that "some flows are narrow enough that every scenario is e2e." The one scenario that genuinely crosses a live service boundary (proposal-service calling voting-service) is classified `integration`.

## 2. Preconditions & fixtures

- **Scheduled session**: `POST /voting/sessions` with `proposal_id`, `jurisdiction_id`, `method` ∈ {`ranked_choice`,`approval`,`preference_score`,`comparative`}, `threshold_rule` ∈ {`simple_majority`,`majority_plus_quorum`,`supermajority`}, `min_participation` ∈ (0,1], `cooling_off_until`, `opens_at`, `closes_at` with `closes_at` after `opens_at` and `opens_at` at/after `cooling_off_until`. Response: `status=scheduled`.
- **Options**: `POST /voting/sessions/{id}/options` (one call per option) while `status=scheduled`.
- **Proposal reaching `voting` status** (for HP-1 only): build through proposal-service's own real lifecycle endpoints the same way its unit tests' `advanceTo()` helper does — create proposal, add support to threshold, advance to `development`, fill the voting-gate budget fields (`cost`, `funding_source`, `maintenance_cost`, `expected_benefits`) and `scope_jurisdiction_id`, clear any pending scope challenge, then call `advance()` again. Never insert directly into proposal-service's store.
- **Opening a session in tests**: since DP-046/DP-057 are cron sweeps with no scheduler running here, fixtures set `cooling_off_until` and `opens_at` in the past relative to test "now" (as the router tests' `createTestSessionViaHTTP` helper does) and then call `POST /voting/sessions/{id}/open` directly with an `eligible_citizen_ids` list built by the test, standing in for the eligibility computation no real service performs.
- **Token secrets**: captured only from the `/open` response's `issued_tokens[].token_secret` — the one place a token secret exists in plaintext. Never read out of the store.
- **Casting ballots**: `POST /voting/ballots` with `session_id`, `token_secret`, and a `choice` string whose format is method-specific: `approval` = comma-separated approved option IDs; `preference_score` = comma-separated `optionId:score` pairs; `ranked_choice`/`comparative` = comma-separated option IDs in preference order.
- No fixture reaches into another service's (or voting-service's own) store directly; every precondition is built through real public endpoints, per ARCH-009 §2.

## 3. Happy path scenarios

**HP-1 — proposal advance triggers a vote session request (integration, blocked)**
1. proposal-service: build a proposal to `development` status with all voting-gate fields set (per §2) and no pending scope challenge.
2. proposal-service: `advance()` transitions `development`→`voting`; on success it calls `VoteSessionRequester.requestSession(proposalId)`.
3. Expected once `HttpVoteSessionRequester` exists: voting-service receives a real `POST /voting/sessions` call and a `scheduled` session appears with the matching `proposal_id`.
- Blocked on: `HttpVoteSessionRequester` is not implemented; today `requestSession()` is a no-op, so step 3 cannot be observed. Document the scenario now so the gap is visible before the seam is built (ARCH-009 §2).
- Level: integration.

**HP-2 — approval method, local scope, simple majority (e2e)**
1. voting-service: `POST /voting/sessions` (`method=approval`, `threshold_rule=simple_majority`, `min_participation=0.5`) → 201, `status=scheduled`.
2. voting-service: `POST /voting/sessions/{id}/options` ×2 → 201 each (option A, option B).
3. voting-service: `POST /voting/sessions/{id}/open` with 2 eligible citizens (DP-046 + DP-025) → 200, `status=open`, `issued_tokens` has 2 entries.
4. voting-service: `POST /voting/ballots` ×2 (DP-016), both citizens approve option A → 201 each, distinct `verification_code`s.
5. voting-service: `GET /voting/ballots/verify?session_id=&code=` (DP-017) for each code → `{"found": true}`.
6. voting-service: `POST /voting/sessions/{id}/close` (DP-047 → DP-026 → DP-027) → 200, `status=certified`, `tally.winner_option_id` = option A, `tally.quorum_met=true`, `tally.certified_at` set.
- Level: e2e.

**HP-3 — preference_score method, national scope, majority plus quorum (e2e)**
1. `POST /voting/sessions` (`method=preference_score`, `threshold_rule=majority_plus_quorum`, `min_participation=0.75`).
2. Add 2 options.
3. Open with 4 eligible citizens (DP-046 + DP-025).
4. Cast exactly 3 ballots (DP-016) with `optA:90,optB:20`-style choices so option A's average score is higher — participation rate lands exactly at `3/4 = 0.75`, i.e. exactly at `min_participation`.
5. Verify all 3 (DP-017) → `found:true`.
6. Close (DP-047 → DP-026 → DP-027) → `status=certified`, `tally.quorum_met=true` (participation rate `>= min_participation`, boundary satisfied), winner = option A.
- Level: e2e.

**HP-4 — ranked_choice (Instant-Runoff) method, local scope, simple majority (e2e)**
1. `POST /voting/sessions` (`method=ranked_choice`, `threshold_rule=simple_majority`, `min_participation=0.5`).
2. Add 3 options (A, B, C).
3. Open with 5 eligible citizens.
4. Cast 5 ranked ballots (DP-016) such that no option has a first-round majority, forcing a runoff-elimination round (lowest-count option(s) eliminated, ballots' next-remaining choice counted) before a majority winner emerges.
5. Close (DP-047 → DP-026 → DP-027) → `status=certified`, `tally.winner_option_id` is the IRV winner, `tally.counts` reflects the final round's counts only.
- Level: e2e.

**HP-5 — comparative (Condorcet/Copeland) method, constitutional scope, supermajority (e2e)**
1. `POST /voting/sessions` (`method=comparative`, `threshold_rule=supermajority`, `min_participation=0.6`).
2. Add 3 options (A, B, C).
3. Open with 6 eligible citizens.
4. Cast 6 ranked ballots (DP-016) such that option A beats every other option pairwise (a genuine Condorcet winner) by a margin whose `WinnerShare` (winning votes / (winning + opposing votes) in A's pairwise contests) is `>= 2/3`.
5. Close (DP-047 → DP-026 → DP-027) → `status=certified`, `tally.winner_option_id` = option A (the Condorcet winner is picked without falling back to Copeland scoring since `beatsEveryone[A]` is true), supermajority check passes.
- Level: e2e.

## 4. Edge cases

### Input validation

- **EC-1**: `POST /voting/sessions` missing `proposal_id` or `jurisdiction_id` → 400 (`ErrValidation`). FR-042. Level: e2e.
- **EC-2**: `POST /voting/sessions` with an invalid `method` string → 400. FR-042. Level: e2e.
- **EC-3**: `POST /voting/sessions` with an invalid `threshold_rule` string → 400. FR-042. Level: e2e.
- **EC-4**: `POST /voting/sessions` with `min_participation` = 0, negative, or > 1 → 400 (`(0,1]` is enforced strictly). FR-042. Level: e2e.
- **EC-5**: `POST /voting/sessions` with `closes_at` not after `opens_at` → 400. FR-044. Level: e2e.
- **EC-6**: `POST /voting/sessions` with `opens_at` before `cooling_off_until` → 400. FR-044, DP-057. Level: e2e.
- **EC-7**: `POST /voting/sessions/{id}/options` missing `label` → 400. FR-043. Level: e2e.
- **EC-8**: `POST /voting/ballots` missing `session_id` or `token_secret` → 400. DP-016. Level: e2e.
- **EC-9**: Malformed JSON body on any POST endpoint → 400 (`invalid JSON body`). Level: e2e.

### State-machine violations

- **EC-10**: `POST /voting/sessions/{id}/options` after the session leaves `scheduled` (open, closed, or certified) → 409 (`ErrSessionNotScheduled`). FR-043. Level: e2e.
- **EC-11**: `POST /voting/sessions/{id}/open` on a session that is already `open`, `closed`, or `certified` (double-open) → 409 (`ErrSessionNotScheduled`). DP-046. Level: e2e.
- **EC-12**: `POST /voting/sessions/{id}/close` on a session that is still `scheduled`, or already `closed`/`certified` → 409 (`ErrSessionNotOpen`). DP-047. Level: e2e.
- **EC-13**: `POST /voting/ballots` against a session that is `scheduled` (not yet open) or `closed`/`certified` (casting after close) → 409 (`ErrSessionNotOpen`). DP-016, FR-044. Level: e2e.
- **EC-14**: `GET /voting/sessions/{id}` tally lookup before the session has closed → 404 (`ErrTallyNotAvailable`) — note the tally is only reachable via `GetTally`, exercised through the close-response body or a direct call; there is no standalone `GET tally` HTTP route today, so this is an internal-service-level check. FR-004. Level: e2e.

### Authorization / eligibility

- **EC-15**: `POST /voting/ballots` with a `token_secret` that was never issued for that session → 404 (`ErrTokenNotFound`). DP-016, FR-003. Level: e2e.
- **EC-16**: `POST /voting/ballots` using an eligibility token secret that was issued for a *different* session → 404 (`ErrTokenNotFound`) — tokens are indexed per-session by hash (`store.tokens[sessionID].byHash`), so a hash valid in session A is simply absent from session B's map. DP-016, FR-041. Level: e2e.
- **EC-17**: Double-cast — the same `token_secret` used a second time on the same session after a first successful cast → first call 201, second call 409 (`ErrTokenUsed`). DP-016, FR-003. Level: e2e.
- **EC-18** (ABUSE-VOTE-3/4, TP-001): A citizen omitted from `eligible_citizen_ids` at open time has no token issued and thus no way to cast — there is no endpoint that accepts an unissued citizen's credentials. Coverage gap: because eligibility is caller-supplied rather than computed from the proposal's sphere of impact, this doc cannot exercise FR-041's "eligibility is computed from the proposal's impact scope" or "eligibility decisions are explainable to citizens" acceptance criteria against real code — flagged rather than invented. The same gap has a fabrication half, proven alongside the omission half by the same test: `/open` accepts a caller-supplied list of 100 entirely fabricated citizen ids with zero cross-check against any authority, issues each a real, usable token, and one of those tokens successfully casts a real counted ballot — whoever can call `/open` controls the electorate outright, in both directions. FR-041. Level: e2e. Proven by `abuse_test.go::TestAbuseVote3And4OpenAcceptsFabricatedElectorateWithNoJurisdictionCheck`.

### Threshold & boundary conditions

- **EC-19**: `POST /voting/sessions/{id}/open` exactly at `cooling_off_until`/`opens_at` (`now == opens_at`) succeeds (`After(now)` is a strict comparison), one moment before either boundary fails with 409 (`ErrOpenPreconditionFailed`). DP-057, FR-044. Level: e2e.
- **EC-20**: `POST /voting/sessions/{id}/open` when cooling-off has cleared but `opens_at` is still in the future → 409 (`ErrOpenPreconditionFailed`). DP-046, DP-057. Level: e2e.
- **EC-21**: `POST /voting/sessions/{id}/close` attempted before `closes_at` is reached → 409 (`ErrCloseNotEligible`). DP-047. Level: e2e.
- **EC-22**: Participation rate exactly equal to `min_participation` → `quorum_met=true` (`>=` comparison); one ballot fewer → `quorum_met=false`, session stays `closed` rather than reaching `certified`. DP-026, DP-027, FR-042. Level: e2e.
- **EC-23**: Supermajority — winner's share exactly at `2/3` vs. one ballot short of it: at-or-above leaves `winner_option_id` set, below nulls it out (`outcome.WinnerShare < 2.0/3.0`). FR-042. Level: e2e.
- **EC-24**: Session closed with zero ballots cast (issued tokens exist but none used) — the tally still names a deterministic "winner" (the lexicographically smallest option ID) with a count of 0 for every option, since `pickMaxByCount` breaks the all-zero tie rather than returning no winner; `quorum_met=false` unless `min_participation` is somehow 0 (impossible, validated `>0`). Explicitly worth asserting because a naive reader would expect "no ballots → no winner." DP-026, FR-004. Level: e2e.
- **EC-25**: Tally tie between two or more options with equal counts/scores → resolved deterministically by lexicographically-smallest option ID, for every method (approval, preference_score via `pickMaxByCount`; ranked_choice's final round likewise; comparative's Copeland fallback on a preference cycle, e.g. a 3-way rock-paper-scissors ranking). DP-026. Level: e2e.
- **EC-26**: Session closed with zero vote options ever added → tally has empty `counts` and `winner_option_id=null` (no forced winner, unlike EC-24's zero-ballots-but-some-options case). DP-026. Level: e2e.

### Concurrency & idempotency

- **EC-27**: Concurrent double-spend — many simultaneous `POST /voting/ballots` calls with the same `token_secret` against the same session → exactly one succeeds (201), all others fail with 409 (`ErrTokenUsed`); the store's single-mutex, whole-operation-atomic `CastBallot` guarantees this. DP-016, FR-003. Level: e2e.
- **EC-28**: Concurrent ballot casts by distinct citizens against the same open session → all succeed, every ballot gets a unique `verification_code`, no lost updates. DP-016. Level: e2e.
- **EC-29**: Idempotent token issuance — `POST /voting/sessions/{id}/open` called twice (or DP-025 re-delivered per its at-least-once guarantee) with an overlapping `eligible_citizen_ids` list → citizens already issued a token are silently skipped (`issued_tokens` on the replay omits them), never receiving a second token or overwriting the first. DP-025, FR-041. Level: e2e.
- **EC-30**: Duplicate close — `POST /voting/sessions/{id}/close` called twice in quick succession (racing or sequential) → only the first call, while `status=open`, succeeds and computes the tally exactly once; the second call sees `status` already advanced past `open` and fails with 409 (`ErrSessionNotOpen`), so DP-026's "exactly-once" guarantee is achieved here via the status-transition guard rather than a literal idempotency key. DP-026, DP-047. Level: e2e.

### Cross-service failure & degradation

- **EC-31**: `DelegationResolver.ResolveAndEnqueue` errors or is unreachable during `CastBallot` → the already-committed ballot is not rolled back (fire-and-forget by design; the store transaction for DP-016 completes before the resolver is ever called). Blocked on: delegation-service is not implemented, so this can only be exercised today against an in-process fake, not a real unreachable HTTP target. DP-041, DP-016. Level: e2e (blocked).
- **EC-32**: `AuditEmitter.Emit` errors or is unreachable during certification → `CloseSession`'s returned session/tally are unaffected (the emit error is discarded, `_ = s.audit.Emit(...)`); certification stands even if the audit event is lost. Blocked on: audit-service is not implemented. DP-027. Level: e2e (blocked).
- **EC-33**: proposal-service's `VoteSessionRequester` target (voting-service) is down or the call errors when a proposal advances `development`→`voting` → today's no-op default swallows this unconditionally (`requestSession` returns `void`, no error path at all), so the proposal transitions to `voting` status regardless of whether a session was ever created downstream. Once `HttpVoteSessionRequester` exists this scenario should assert whether the intended behavior is fail-open (proposal advances, orphaned with no session) or fail-closed (advance blocked) — the spec does not currently say. Blocked on: `HttpVoteSessionRequester` not implemented. Level: integration (blocked).

### Data integrity & audit

- **EC-34**: No API response or store structure at any point in the flow (`ballot` create response, `ballot` verify response, or the `Ballot` struct itself) carries a `citizen_id` field or any citizen-identifying value — confirmed structurally: `Ballot` has no such field, `EligibilityToken.CitizenID` never appears in a ballot-scoped response. FR-003. Level: e2e.
- **EC-35**: `GET /voting/ballots/verify` — presenting a `code` that does not match any cast ballot within a real session → 200, `{"found": false}` (not an error); presenting an unknown `session_id` entirely → 404 (`ErrSessionNotFound`). These are two distinct outcomes worth asserting separately. DP-017, FR-004. Level: e2e.
- **EC-36**: `ballot.token_blind` (a fresh random value minted at cast time) shares no derivation or storage key with `eligibility_token.blinded_token_hash` — there is no field or index anywhere in `store.go` that joins a specific ballot back to the eligibility token/citizen that authorized it, satisfying FR-003's "no stored record allows reconstruction of how an identified citizen voted." Level: e2e.
- **EC-37**: The raw per-session AES-256 key is never persisted at any point — only its 5 Shamir shares (3-of-5 threshold) are stored (`store.keyShares`); no session, ballot, or tally response ever exposes key material. Separately: reconstructing with fewer than the 3-share threshold does not error — `shamirCombine` has no way to detect an insufficient share count and silently returns the *wrong* plaintext rather than failing, which is an inherent property of raw Shamir sharing worth calling out explicitly rather than assuming it "just fails safe." ADR-002, ADR-019. Level: e2e.
- **EC-38**: Audit emission only fires on a *successful* certification (`quorum_met=true` inside `CloseSession`); the `open` transition (DP-046) and a quorum-failed `close` (DP-027's failure branch) emit no audit event at all in the current code, despite SRV-008's own spec stating "Emits to: audit-service (DP-036 on every phase transition)." This is a real discrepancy between spec and implementation, not an invented scenario — worth flagging for correction of one side or the other. DP-027. Level: e2e.
- **EC-39**: DP-027's "on quorum failure...triggers DP-039 (result notification) and DP-038 (participation reputation signal)" has no corresponding seam or call anywhere in `service.go` — there is no notification or reputation interface in voting-service at all (only `DelegationResolver` and `AuditEmitter` exist). Documented as a gap versus the data-process spec rather than assumed to work. DP-027, DP-038, DP-039. Level: e2e (blocked — no seam exists to test).

## Status update (2026-08-27)

Two items this doc flagged are resolved:

1. **The DP-041 weighting bug is fixed.** `DelegationResolver.ResolveAndEnqueue` (which discarded its result) is now `ResolveDelegators`, returning the resolved delegator ids; `CastBallot` sets `Ballot.Weight = 1 + len(delegators)`, and `CloseSession` feeds each ballot into the tally once per unit of weight. A delegate's vote now actually counts once for themself and once more per citizen who delegated to them, for all four tally methods (approval, preference_score, ranked_choice, comparative) without needing per-method changes, since each is a linear aggregate over the ballot multiset. EC-31 (delegation chain resolution feeding the tally) can now be written for real.
2. **Both cross-service seams have real HTTP implementations.** `remote.go` adds `httpDelegationResolver` (calls delegation-service's `POST /delegation/resolve`) and `httpAuditEmitter` (calls audit-service's `POST /audit/log`), wired in via `DELEGATION_SERVICE_URL`/`AUDIT_SERVICE_URL`. EC-38/EC-39 (certification audit emission) are no longer `blocked`.

Still open: `VoteSessionRequester` in proposal-service (the seam this doc's HP-1 depends on) is still a no-op, so the proposal→voting-service session-creation trigger itself remains unwired.

## Status update (2026-09-04)

EC-18 is now proven by a real Go test (`services/go/voting-service/abuse_test.go`), ground-truthed in TP-001 as ABUSE-VOTE-3/4. It demonstrates the caller-supplied-eligibility gap is exploitable in both directions from a single fixture: 100 fabricated ids all receive usable tokens (one of which casts a real ballot), while a legitimate, never-listed citizen has no way to vote at all.
